# 1. 摘要

ByteStore is a distributed append-only storage system that serves as the foundational storage layer of the ByteDance infrastructure. Initially, storage services on ByteStore use compaction for garbage collection (GC). Additional writes induced by compaction and the SSD space occupied by stale data result in millions of dollars in extra Total Cost of Ownership (TCO) per month. Aggressive compaction releases the SSD space, but at the cost of more write operations and faster SSD wear, thus failing to reduce TCO.

ByteStore 是字节跳动的底层存储系统, 采用分布式架构, 数据只能追加写入. 最初, 运行在 ByteStore 之上的存储服务依靠 compaction 回收垃圾 (GC). compaction 会产生额外写入, 失效数据又会占用 SSD 空间, 两者使总拥有成本 (Total Cost of Ownership, TCO) 每月增加数百万美元. 更积极地执行 compaction 虽然能释放空间, 却也会增加写入次数, 加快 SSD 磨损, 因而无法降低 TCO.

Based on our analysis of the traces from the block storage service (ByteDrive) deployed on ByteStore, we propose DisCoGC, a Discard-and-Compaction combined Garbage Collection scheme, which employs a discard mechanism to reclaim the space occupied by stale data without moving valid data. Production cluster metrics monitor and offline experiments demonstrate that DisCoGC achieves approximately 20% reduction in TCO, without sacrificing performance.

我们分析了块存储服务 ByteDrive 的 I/O 访问轨迹. ByteDrive 运行在 ByteStore 之上, 这项分析促使我们提出 DisCoGC, 一种结合 discard 与 compaction 的垃圾回收方案 (Discard-and-Compaction combined Garbage Collection). 其中, discard 可以直接回收失效数据占用的空间, 无需搬移有效数据. 生产集群的监控结果和离线实验表明, DisCoGC 能在不牺牲性能的前提下, 将 TCO 降低约 20%.

# 2. 引言

ByteStore is a distributed, SSD-based append-only storage system developed by ByteDance to provide a unified, high-performance, and reliable service for all of its storage requirements. All types of storage services, including Elastic Block Storage (ByteDrive), Tinder Object Storage Service (TOS), Network-Attached Storage (NAS), Distributed Graph Database (ByteGraph), and NewSQL Database (ByteNDB), are built upon ByteStore. In this paper, we focus on the ByteDrive + ByteStore stack. ByteDrive provides a virtual disk service for computing instances, enabling a stable and elastic compute-storage disaggregation architecture.

ByteStore 是字节跳动开发的分布式存储系统, 基于 SSD 构建, 只允许追加写入, 旨在为各类存储需求提供统一, 高性能且可靠的服务. 弹性块存储 ByteDrive, 对象存储服务 TOS, 网络附加存储 NAS, 分布式图数据库 ByteGraph 和 NewSQL 数据库 ByteNDB 等服务均构建于 ByteStore 之上. 本文重点讨论 ByteDrive + ByteStore 这一存储栈. ByteDrive 为计算实例提供虚拟磁盘, 支持稳定运行和弹性扩展的存算分离架构.

ByteStore provides append-only interfaces via LogFiles. As a distributed append-only storage system, ByteStore requires a periodic garbage collection (GC) process to reclaim space occupied by stale data. The GC process is triggered by upper-layer storage services such as ByteDrive. At first, ByteDrive employs a compaction-based GC procedure operating on LogFiles. During compaction, ByteDrive collects the valid data in old LogFiles and writes them to new LogFiles, subsequently deleting the old LogFiles. As a result, the space occupied by stale data is reclaimed.

ByteStore 通过 LogFile 提供只追加接口, 需要定期回收失效数据占用的空间. GC 由 ByteDrive 等上层存储服务触发. 最初, ByteDrive 使用 compaction 回收 LogFile 中的垃圾: 先将旧文件中的有效数据写入新文件, 再删除旧文件, 由此释放失效数据占用的空间.

However, our early works on optimizing compaction present a fundamental trade-off (Fig. 1) between write amplification and space amplification. Write amplification arises from rewriting the valid data to new LogFiles during compaction, and space amplification stems from stale data on the SSD. To lower space amplification, we adopt a more aggressive compaction policy, which leads to higher write amplification and contention for foreground I/O. Ultimately, the space amplification and write amplification increase the Total Cost of Ownership (TCO) of the storage system by millions of dollars per month.

然而, 在早期优化 compaction 时, 我们发现写放大和空间放大之间存在难以兼顾的问题 (图 1). compaction 需要将有效数据重写到新 LogFile, 因而产生写放大; 失效数据留在 SSD 上, 则会造成空间放大. 为减少空间占用而更积极地执行 compaction, 又会增加写放大, 与前台 I/O 争用资源. 在字节跳动, 这两种放大使存储系统的 TCO 每月增加数百万美元.

To motivate a more efficient GC method that improves this trade-off, we analyze the workloads from several representative types of services in ByteDance. We find that the workloads with AI model download/inference, inverted index building/updating, and distributed computing (`e.g.`, Spark) show high write sequentiality. In these cases, over half of the writes modify contiguous ranges exceeding 256KiB. These workloads also show frequent overwrites that occur within seconds. This results in long, contiguous ranges of stale data on the LogFiles.

为找到更高效的 GC 方法, 更好地兼顾这两种开销, 我们分析了字节跳动几类代表性服务的工作负载. AI 模型下载和推理, 倒排索引构建和更新, 以及 Spark 等分布式计算任务, 都包含大量顺序写入. 在这些场景中, 超过一半的写入会修改大于 256 KiB 的连续区间, 并在数秒内频繁覆盖已有数据, 因而在 LogFile 中留下较长的连续失效区间.

Based on these observations, we propose incorporating discard into the garbage collection process. Instead of moving valid data and deleting the entire LogFile, a discard request directly reclaims the space occupied by stale data on LogFiles, efficiently reclaiming long, contiguous ranges of garbage on LogFiles. This reduces space amplification without increasing write amplification, effectively lowering the TCO.

基于这些观察, 我们提出将 discard 纳入 GC. discard 请求直接回收 LogFile 中失效数据占据的空间, 无需搬移有效数据后再删除整个 LogFile. 这种方法能够高效回收长而连续的垃圾区间, 在不增加写放大的情况下降低空间放大, 从而降低 TCO.

However, integrating discard into the multi-layer design of ByteDrive + ByteStore is non-trivial. First, the reclaimed ranges of the discard requests should align with the allocation units of the underlying layer, while they are usually misaligned between adjacent storage layers. For example, in the bottom data layout of ByteStore, each data block needs to store a checksum for data integrity, breaking the data alignment. This prevents discard requests from fully reclaiming garbage at the boundaries. Second, frequent discards trigger frequent metadata updates, consuming disk IOPS and causing contention with foreground I/O. Third, discard punches holes in the LogFiles, making the LogFiles sparse and thereby increasing the number of LogFiles. This increases the size of metadata in ByteStore and ByteDrive. Fourth, trim commands can help discard requests to reclaim physical space on SSD promptly. However, the maximum trim IOPS of SSDs varies across models. Without adequate trim IOPS, the SSD space isn't reclaimed promptly, leading to aggressive SSD GC and degrading SSD foreground service quality.

不过, 将 discard 引入 ByteDrive + ByteStore 的多层存储栈, 还需要解决几个问题. 第一, 回收区间必须与底层分配单元对齐, 而相邻存储层的分配单元往往并不对齐. 例如, ByteStore 最底层的数据块需要附带校验和, 以保证数据完整性, 这会打破原有的数据对齐关系, 使边界处的垃圾无法完全回收. 第二, discard 越频繁, 元数据更新也越频繁, 会占用磁盘 IOPS, 与前台 I/O 争用资源. 第三, discard 在 LogFile 中打洞, 文件随之变得稀疏, 数量也会增加, ByteStore 和 ByteDrive 需要维护的元数据因而更多. 第四, trim 命令有助于及时回收 SSD 物理空间, 但不同型号 SSD 的最大 trim IOPS 不同. 如果 trim 处理能力不足, 空间就无法及时释放, SSD 不得不更积极地执行 GC, 前台服务质量也会下降.

We propose DisCoGC, a Discard-and-Compaction combined Garbage Collection scheme, to address the aforementioned challenges. To reclaim the garbage at the boundaries, DisCoGC extends the discard range to slightly overlap the adjacent, previously discarded range and aligns the allocation unit on LogFiles to the allocation unit on SSDs. To reduce the metadata modification overhead, DisCoGC batches the discard requests in the same LogFile and controls the discard parallelism/IOPS. DisCoGC executes compaction periodically to merge the fragmented LogFiles and chunks. We develop a trim filter to prioritize larger ranges and a trim merger to merge small ranges into large ones. These better utilize the SSD's limited trim IOPS.

DisCoGC 针对这些问题做了几项改进. 为回收边界垃圾, 它稍微扩大当前 discard 区间, 使其与相邻的已处理区间重叠, 同时将 LogFile 的分配单元与 SSD 侧对齐. 为减少元数据更新, 它将同一 LogFile 的 discard 请求批量提交, 并限制并行度和 IOPS. 此外, DisCoGC 定期执行 compaction, 合并碎片化的 LogFile 和 chunk. 我们还实现了 trim 过滤器 (trim filter) 和合并器 (trim merger): 前者优先处理大区间, 后者将小区间合并为大区间, 以充分利用 SSD 有限的 trim 处理能力.

We deployed DisCoGC in our production clusters with mixed workloads. Configured with a 10% lower space amplification, DisCoGC reduces write amplification by 25% compared to the compaction-only GC without performance degradation. The lower space amplification and write amplification result in a 20% TCO reduction. To evaluate its effectiveness across different scenarios, we also tested DisCoGC with three different workloads from ByteDance and with the FIO [13] benchmark. For all workloads, DisCoGC demonstrates a superior trade-off between write amplification and space amplification without incurring a latency penalty, leading to a lower TCO. DisCoGC is particularly effective for highly sequential workloads with frequent overwrites, where it cuts TCO by over 25%. Random and fragmented workloads also benefit from DisCoGC for 2%-5%, demonstrating DisCoGC's robustness and resilience.

我们已将 DisCoGC 部署到运行混合负载的生产集群. 与仅依靠 compaction 回收垃圾相比, 在空间放大降低 10% 的配置下, DisCoGC 将写放大降低了 25%, 且未造成性能下降. 这两项改善使 TCO 降低了 20%. 为评估不同场景下的效果, 我们还测试了字节跳动的三类负载和 FIO [13] 基准负载. 在所有测试负载下, DisCoGC 都能更好地兼顾空间放大与写放大, 且没有增加延迟, 因而降低了 TCO. 对于顺序性强且频繁覆盖写入的负载, TCO 降幅超过 25%; 对于随机且碎片化的负载, 也能节省 2%-5%, 说明它能够适应不同的负载.

Finally, we discuss several practical considerations for deploying DisCoGC. First, we recommend analyzing the write sequentiality and overwrite metrics in I/O traces to determine whether the workload is suitable for DisCoGC. Second, we describe how to tune key parameters to maximize the benefits of DisCoGC. Third, we explain how to configure trim-related optimizations based on the SSD's maximum trim IOPS. Fourth, we share experiences on monitoring DisCoGC.

最后, 我们讨论部署中的几个实际问题: 如何通过 I/O 轨迹中的写入顺序性和覆盖写入情况, 判断负载是否适合 DisCoGC; 如何调整关键参数, 充分发挥其效果; 如何根据 SSD 的最大 trim IOPS 配置相关优化; 以及如何监控 DisCoGC 的运行情况.

In summary, this paper makes the following contributions:

本文贡献如下:

- We characterize the I/O patterns from production traces at ByteDance to guide GC optimization on the space amplification-write amplification trade-off.
- We design and implement DisCoGC, a technique that integrates discard with compaction and addresses the challenges of applying discard in a production append-only storage system.
- We demonstrate the effectiveness of DisCoGC through monitoring the performance on production clusters and replaying traces on testbeds.
- We provide practical guidelines on when and how to apply DisCoGC in distributed append-only storage systems.

# 3. 系统概览

ByteDance employs a hierarchical storage stack, as shown in Fig. 2, to manage all its data. The stack provides several storage services, such as ByteDrive, TOS and NAS, to support its upper-layer applications like DouBao [10], FeiShu [12] and TouTiao [15].

字节跳动使用图 2 所示的分层存储栈管理所有数据. 该存储栈提供 ByteDrive, TOS 和 NAS 等存储服务, 支撑豆包 [10], 飞书 [12] 和今日头条 [15] 等上层应用.

The foundation of these services is ByteStore, a distributed append-only storage system. The append-only storage systems offer several advantages over the in-place update ones. First, it seamlessly supports Erasure Coding (EC) for space-efficient fault tolerance. Second, it simplifies data consistency as committed data remains immutable. Furthermore, preserving the history of changes simplifies implementing features like snapshot, version control, and crash recovery [18].

这些服务都以分布式只追加存储系统 ByteStore 为基础. 相比原地更新, 只追加的设计有几项优势. 它便于支持纠删码 (Erasure Coding, EC), 以较低的空间开销实现容错; 已提交的数据不会再被修改, 因而更容易保证一致性; 保留下来的变更历史, 也便于实现快照, 版本控制和崩溃恢复等功能 [18].

In this paper, we focus on ByteDrive and ByteStore. At ByteDance, ByteDrive is a critical service that manages thousands of clusters with exabyte-scale data. ByteDrive provides virtual disks for cloud computing instances, enabling a compute-storage disaggregated architecture.

本文关注 ByteDrive 和 ByteStore. ByteDrive 是字节跳动的一项关键服务, 管理数千个集群和 EB 级数据. 它为云计算实例提供虚拟磁盘, 支撑存算分离架构.

## 3.1 ByteDrive

ByteDrive exposes virtual block devices (volumes) to users. To leverage the underlying ByteStore's append-only semantics, ByteDrive converts random write requests to append-only writes. It consists of two layers, the Volume layer and the Segment Layer, as shown in the upper part of Fig. 3.

ByteDrive 向用户提供虚拟块设备, 即卷 (volume). 为利用底层 ByteStore 的只追加语义, 它将随机写请求转换为追加写. 如图 3 上半部分所示, ByteDrive 包含 Volume 层和 Segment 层.

The Volume Layer provides simple interfaces for random read, write, and trim operations at a 4KiB block granularity. Users access volumes via the BlockClient library. Internally, to enable parallelism, each volume's Logical Block Address (LBA) space is partitioned into segments across different BlockServers. The mapping from segments to their server locations is managed by BlockMasters and cached in the BlockClients for efficient access. To ensure load balancing, data within a volume is organized into 128KiB stripes and spread across segments using a round-robin policy.

Volume 层以 4 KiB 块为粒度, 提供随机读写和 trim 接口. 用户通过 BlockClient 库访问卷. 为了并行处理请求, 系统将每个卷的逻辑块地址 (Logical Block Address, LBA) 空间划分为多个 segment, 分别交给不同的 BlockServer 处理. BlockMaster 记录各 segment 所在的服务器, BlockClient 缓存这些映射以加快访问. 卷内数据按 128 KiB 条带组织, 以轮询方式分布到各个 segment, 保持负载均衡.

The Segment Layer converts random write requests on a segment to append-only requests on the underlying ByteStore. When handling a write request, this layer first compresses the data at the block level to save storage space. It then adds a header to each compressed block to record compression details (`e.g.`, LZ4 [14] or deflate [23]). Finally, these prepared blocks are written to ByteStore in an append-only manner. To keep track of the latest data location, this layer employs an LSM-Tree to map the LBA on the segment to the newest physical address in the ByteStore.

Segment 层负责将 segment 上的随机写请求转换为对 ByteStore 的追加写请求. 它先按块压缩数据以节省空间, 再为每个压缩块添加头部, 记录所用的压缩方式等信息, 例如 LZ4 [14] 或 deflate [23]. 处理后的数据块随后被追加写入 ByteStore. 该层还维护一棵 LSM-tree, 记录 segment 上每个 LBA 对应的最新物理地址, 以便找到最新版本的数据.

### 3.2.1 LogFile 的布局与访问

LogFiles offer a uniform, append-only view of storage to higher-level services and serve as the basic unit for GC. To enhance GC flexibility, ByteStore proposes limiting the maximum size of LogFiles to 2 GiB. Consequently, each Segment is mapped to one active data LogFile and zero or more sealed data LogFiles. The LogFile is composed of multiple chunks, each of which has multiple replicas by erasure coding or copies. The chunk size is configurable, typically ranging from tens to hundreds of MiB. This size balances two factors: smaller chunks provide greater flexibility for data migration and recovery, while larger chunks reduce metadata management overhead. Replicas of the same chunk are stored in different ChunkServers for data reliability.

LogFile 向上层服务提供统一的只追加存储视图, 也是 GC 的基本单位. 为使 GC 更灵活, ByteStore 建议将单个 LogFile 的大小上限设为 2 GiB. 每个 segment 对应一个正在写入的数据 LogFile, 以及零个或多个已封存的数据 LogFile. 一个 LogFile 由多个 chunk 组成, 每个 chunk 通过纠删码或复制生成冗余副本. chunk 的大小可以配置, 通常为数十到数百 MiB: 较小的 chunk 便于灵活迁移和恢复数据, 较大的 chunk 则能减少元数据管理开销. 同一 chunk 的各个副本存放在不同的 ChunkServer 上, 以保证数据可靠性.

The MetaServers manage two primary types of metadata: (1) the attributes of each LogFile, such as total length, number of chunks, creation time, permissions, and redundancy policy (EC/replication); (2) the attributes of each chunk, such as length and replica locations. The MetaServers also perform background operations for data consistency and reliability, such as reconstructing missing replicas.

MetaServer 管理两类主要元数据: 一是 LogFile 属性, 包括总长度, chunk 数量, 创建时间, 权限和冗余策略 (EC 或复制); 二是 chunk 属性, 包括长度和副本位置. MetaServer 还执行重建缺失副本等后台操作, 保障数据一致性和可靠性.

ByteStore SDK is the client library for accessing ByteStore. To simplify fault tolerance logic on the server side, we adopt a heavyweight client SDK. The SDK is responsible not only for I/O requests processing but also for implementing the EC/replication protocols and handling client-side error recovery, such as request retries and backup reads.

ByteStore SDK 是访问 ByteStore 的客户端库. 为简化服务端的容错逻辑, 我们将更多职责放在客户端: SDK 除了处理 I/O 请求, 还负责执行 EC 或复制协议, 并通过请求重试, 备份读等方式在客户端处理错误和恢复访问.

### 3.2.2 ChunkServer 上的用户态文件系统

ChunkServer is designed to provide a high-performance and high-reliability chunk storage service within a single storage node. To achieve low latency and high throughput [20], we developed a userspace filesystem (UFS) for ChunkServers to replace kernel filesystems like Ext4 and XFS. Specifically, UFS avoids superfluous features (`e.g.`, directory semantics, journaling) that incur additional write amplification, and developing a custom UFS is simpler than modifying an existing filesystem. In the UFS (Fig. 4), each chunk replica is managed as an individual file. The UFS also manages the QoS, concurrency, integrity verification, and buffer/direct I/O processing.

ChunkServer 负责单个存储节点上的 chunk 存储, 需要兼顾性能与可靠性. 为实现低延迟和高吞吐量 [20], 我们为它开发了用户态文件系统 (Userspace Filesystem, UFS), 替代 Ext4 和 XFS 等内核文件系统. UFS 不提供目录语义, 日志机制等在此场景下不必要的功能, 避免了这些功能带来的额外写放大. 开发一个专用 UFS, 也比改造现有文件系统更简单. 如图 4 所示, UFS 将每个 chunk 副本作为独立文件管理, 同时负责 QoS, 并发控制, 完整性校验, 以及缓冲 I/O 和直接 I/O 的处理.

Self-contained chunk replica layout. To ensure both high data integrity and efficiency, the UFS uses a self-contained chunk replica layout. Specifically, each 4KiB sector is a self-contained unit, with the first 32B reserved as a header for verification information (CRCs, data length) and the remaining 4064B for data. This co-location directly provides two advantages. For integrity, the UFS can validate each sector independently upon reads or recovery, ensuring write atomicity. For performance, both data and verification information can be accessed in a single, sequential I/O.

**自包含的 chunk 副本布局.** 为兼顾数据完整性和访问效率, UFS 将数据及其校验信息放在同一个扇区内, 使每个扇区都能独立校验, 即采用自包含布局. 每个扇区大小为 4 KiB, 前 32 B 用作头部, 保存 CRC 和数据长度等校验信息, 剩余 4064 B 存放数据. 这样, 读取或恢复时就能逐个验证扇区, 保证写入原子性; 同时, 一次顺序 I/O 就能读到数据及其校验信息.

Disk layout. The UFS aggregates 4 sectors into a cluster as the allocation unit to balance the overhead of space management against internal fragmentation. The UFS maintains a MetaPage zone on the disk to store cluster allocation information and chunk-to-cluster mapping information.

**磁盘布局.** UFS 将 4 个扇区合为一个分配簇 (cluster), 作为空间分配单元, 兼顾空间管理开销和内部碎片. 磁盘上的 MetaPage 区记录 cluster 的分配情况, 以及 chunk 到 cluster 的映射.

Original footnote 2: Maintaining 4KiB data alignment on the ChunkServer is impractical and unnecessary due to data compression by the BlockServer.

原文脚注 2: BlockServer 会压缩数据, 因此在 ChunkServer 上维持 4 KiB 数据对齐既不现实, 也没有必要.

## 3.3 数据流

This subsection uses an example (Fig. 5) to illustrate the standard data path of a user write request. In this case, the system is configured with 3-replica for fault tolerance.

Volume Layer. (§2.1) (1) A ByteDrive user writes to the range [20KiB, 200KiB) of a volume through the BlockClient. (2) The BlockClient first determines that the range [20KiB, 128KiB) maps to the first segment as range [20KiB, 128KiB), and [128KiB, 200KiB) maps to the second segment as range [0KiB, 72KiB). Then, the BlockClient sends the data of each range to the corresponding segment.

Volume 层 (原文第 2.1 节). (1) 用户通过 BlockClient 写入卷的 [20 KiB, 200 KiB) 区间. (2) BlockClient 将 [20 KiB, 128 KiB) 映射到第一个 segment 的 [20 KiB, 128 KiB), 将 [128 KiB, 200 KiB) 映射到第二个 segment 的 [0 KiB, 72 KiB), 再把各区间的数据发送到对应 segment.

Segment Layer. (§2.1) (3) For the first segment, after compression and the addition of block-level headers, the data size is 80KiB. The SDK then appends this 80KiB data to the end of the segment's unsealed LogFile.

Segment 层 (原文第 2.1 节). (3) 第一个 segment 的数据在压缩并添加块级头部后, 大小为 80 KiB. SDK 将这 80 KiB 数据追加到该 segment 尚未封存的 LogFile 末尾.

LogFile Layer. (§2.2.1) (4) The ByteStore SDK first maps the tail of the LogFile to a target chunk. As a chunk consists of several replicas stored on different ChunkServers, the SDK then locates these servers. Finally, it issues write requests to all corresponding ChunkServers.

LogFile 层 (原文第 2.2.1 节). (4) ByteStore SDK 将 LogFile 尾部映射到目标 chunk. 由于一个 chunk 的多个副本分布在不同 ChunkServer 上, SDK 先定位这些服务器, 再向所有对应 ChunkServer 发出写请求.

Next, the UFS allocates 6 clusters for this chunk. It then writes the data, along with its metadata and CRC, to these clusters and (6) updates the MetaPages.

UFS (原文第 2.2.2 节). (5) 每个目标 ChunkServer 的 UFS 为这 80 KiB 数据添加扇区头部, 即每 4064 B 数据附加 32 B 头部. 数据共占 21 个扇区, 需要 6 个 cluster. UFS 为该 chunk 分配 6 个 cluster, 将数据及其元数据和 CRC 写入这些 cluster, 然后 (6) 更新 MetaPage.

**返回结果.** (7) 写操作的结果逐层返回. Segment 层收到写入确认后, BlockServer 更新该 segment 的 LSM-tree, 使索引指向最新数据.

# 4. 研究动机

In this section, we identify the limitations of the compaction-only GC method used in early versions of ByteDrive + ByteStore. We then analyze ByteDrive volume traces from ByteDance's production environment to guide the design of our GC optimizations.

本节介绍 ByteDrive + ByteStore 早期版本仅依靠 compaction 进行 GC 的局限, 随后分析字节跳动生产环境中的 ByteDrive 卷访问轨迹, 为 GC 优化设计提供依据.

## 4.1 垃圾回收

LogFile compaction. The BlockServer periodically compacts LogFiles with a high garbage ratio. It determines the garbage ratio of each LogFile by scanning the LSM-tree to find stale data ranges. LogFiles will be compacted if their garbage ratio exceeds a preset threshold. This compaction process rewrites valid data from the old LogFiles to new LogFiles, and then deletes the old ones (Fig. 6).

LogFile compaction. BlockServer 定期对垃圾比例较高的 LogFile 执行 compaction. 它通过扫描 LSM-tree 找出失效数据区间, 计算各 LogFile 的垃圾比例. 当比例超过预设阈值时, 将旧 LogFile 中的有效数据重新写入新 LogFile, 再删除旧文件, 如图 6 所示.

Trade-off in compaction. Compaction-only GC has two types of overhead: write amplification and space amplification. Space amplification arises from stale data occupying space. Write amplification has two types: logical and physical. Logical write amplification (LWA) results from rewriting valid data to new LogFiles during compaction. Physical write amplification (PWA) is induced by SSD's internal operations, such as SSD GC and wear leveling. The total write amplification (WA) is their product: WA = LWA * PWA. Write amplification increases data written to NAND flash, consuming bandwidth, increasing latency, and reducing SSD lifespan.

**compaction 中的权衡.** 仅依靠 compaction 回收垃圾会产生空间放大和写放大. 空间放大是因为失效数据仍占据存储空间. 写放大则分为逻辑写放大 (Logical Write Amplification, LWA) 和物理写放大 (Physical Write Amplification, PWA): 前者来自 compaction 对有效数据的重写, 后者来自 SSD 内部的 GC, 磨损均衡等操作. 总写放大等于两者的乘积: WA = LWA * PWA. 写放大越大, 写入 NAND 闪存的数据就越多, 不仅占用带宽, 增加延迟, 还会缩短 SSD 寿命.

Our early attempts at optimizing compaction-only garbage collection revealed a key challenge: write amplification and space amplification are negatively correlated. We tried to optimize space amplification by employing an aggressive GC policy. However, this not only increases Logical write amplification and accelerates SSD wear, but also degrades foreground I/O performance. The write amplification and space amplification cause millions of dollars in additional TCO every month in ByteDance.

早期优化表明, 写放大与空间放大负相关. 更积极的 GC 策略能够降低空间放大, 却会提高逻辑写放大, 加快 SSD 磨损, 同时损害前台 I/O 性能. 在字节跳动, 这两种放大每月带来数百万美元的额外 TCO.

# 5. 设计

In this section, we first present the insight behind the new GC mechanism, discard. A discard request reclaims an invalid range on LogFile in constant time, optimizing the trade-off between space amplification and write amplification during compaction, especially for the workload with large, contiguous garbage. Then, we discuss the challenges in integrating discard into multi-layer storage stacks like ByteDrive + ByteStore. Finally, we propose DisCoGC, a GC mechanism combining discard and compaction to overcome the challenges.

本节先介绍 discard 的设计思路. 它可以在常数时间内回收 LogFile 上的无效区间, 帮助系统更好地兼顾空间放大与写放大, 尤其适合会产生大块连续垃圾的负载. 随后, 我们讨论将 discard 引入 ByteDrive + ByteStore 这类多层存储栈时遇到的问题, 并介绍结合 discard 与 compaction 的 DisCoGC 如何解决这些问题.

## 5.1 LogFile discard 机制

Discard reclaims physical space from specified ranges in a LogFile. With discard, BlockServers avoid reading valid data from old LogFiles and rewriting it to the new ones, reducing space amplification without increasing write amplification.

discard 回收 LogFile 指定区间对应的物理空间. BlockServer 无需从旧 LogFile 读取有效数据并重写到新文件, 就可以降低空间放大, 同时避免增加写放大.

The discard process is top-down and asynchronous, spanning the entire system from the Segment Layer down to the UFS Layer. The process involves five steps (Fig. 11):

discard 从 Segment 层向下传递到 UFS 层, 整个过程异步执行, 共分五步 (图 11):

1. The BlockServer scans the LSM-tree of each segment to identify invalid LogFile ranges that have not yet been discarded.
2. The BlockServer issues discard requests to ByteStore for each range via ByteStore SDK.
3. The SDK maps the LogFile ranges to chunk-level ranges and then locates the chunk's replicas.
4. The SDK notifies the respective ChunkServers to discard these ranges in their UFS. The UFS first locates the cluster corresponding to the ranges. It then modifies the MetaPage to free the clusters.
5. Upon completion, the BlockServer records the successfully discarded ranges to prevent repeated discarding of these ranges. The reclaimed clusters can be allocated to other chunks for newly appended data.

<!-- language-pair -->

1. BlockServer 扫描每个 segment 的 LSM-tree, 找出 LogFile 中尚未通过 discard 回收的无效区间.
2. BlockServer 通过 ByteStore SDK 向 ByteStore 发出这些区间的 discard 请求.
3. SDK 将 LogFile 区间映射为 chunk 级区间, 再定位 chunk 副本.
4. SDK 通知对应的 ChunkServer, 由 UFS 回收这些区间. UFS 先找到对应的 cluster, 再修改 MetaPage, 将这些 cluster 释放.
5. 操作完成后, BlockServer 记录已成功回收的区间, 避免重复处理. 释放的 cluster 可以分配给其他 chunk, 用来存放新追加的数据.

However, deploying discard in a multi-layer storage system introduces several challenges. First, discard requests reclaim ranges aligned to allocation units in each layer. However, the allocation units between adjacent layers are often misaligned, which prevents the system from reclaiming space at the discard boundaries. Second, frequent discard operations require many metadata updates, which causes contention for disk I/O and CPU. Third, discard operations cause fragmentation in LogFiles and chunks, which in turn increases the metadata management overhead. Finally, the trim command enables the UFS to reclaim SSD space promptly. This action reduces space utilization, which in turn leads to less frequent GC and a lower physical write amplification. But the maximum trim IOPS is limited on some SSDs. To address these challenges, we propose DisCoGC, with detailed designs presented in §4.2-§4.5.

在多层系统中使用 discard, 需要解决四个问题. 第一, 每层都只能按自己的分配单元回收空间, 而相邻层的分配单元往往不对齐, 因而会留下无法回收的边界空间. 第二, 频繁执行 discard 会带来大量元数据更新, 与前台请求争用磁盘 I/O 和 CPU. 第三, LogFile 和 chunk 会变得稀疏, 碎片化, 增加元数据管理开销. 第四, trim 可以帮助 UFS 及时释放 SSD 空间, 降低空间占用和 SSD GC 频率, 从而减少物理写放大, 但部分 SSD 的最大 trim IOPS 有限. 原文第 4.2-4.5 节分别介绍 DisCoGC 如何处理这些问题.

## 5.2 缓解边界损失

The problem of boundary loss. Boundary loss arises from inter-layer data misalignments due to mismatched allocation units and compression. It prevents the reclamation of garbage data at boundaries. Over time, such unreclaimed garbage accumulates, leading to non-negligible space waste.

**边界损失问题.** 各层分配单元不匹配, 加上数据压缩的影响, 会使数据在不同层之间无法对齐, 留下不能回收的边界垃圾. 这些垃圾不断积累, 就会浪费相当一部分空间.

Boundary loss occurs in two primary aspects (Fig. 12): (1) EC loss: When employing EC for fault tolerance, the SDK must discard data in units of complete EC stripes (`e.g.`, multiples of 64KiB for a 4+1 EC scheme with 16KiB stripes) on the LogFile. However, discard requests issued by the BlockServer are of arbitrary sizes and may not align with EC stripes. (2) Cluster loss: The UFS must perform discards aligned to its allocation unit (cluster, each contains 4*4064B data). However, the packet size of EC stripes is usually a multiple of 4KiB. As a result, the discard requests issued to the UFS are also of a multiple of 4KiB, which aren't cluster-aligned.

边界损失主要有两类 (图 12). (1) EC 损失: 使用 EC 容错时, SDK 只能按完整 EC 条带对 LogFile 执行 discard. 例如, 在条带单元大小为 16 KiB 的 4+1 EC 配置下, 回收单位必须是 64 KiB 的整数倍. 但 BlockServer 发出的请求大小不固定, 不一定与 EC 条带对齐. (2) cluster 损失: UFS 必须按 cluster 回收空间, 每个 cluster 容纳 4 * 4064 B 数据. EC 条带分片的大小通常是 4 KiB 的整数倍, 发给 UFS 的 discard 区间也随之成为 4 KiB 的整数倍, 因而无法与 cluster 对齐.

<div class="paper-shared">

![图 12: 一次 discard 请求的边界损失](/assets/images/posts/discogc/figure-12.webp)

<span class="paper-caption">图 12: 一次 discard 请求的边界损失.</span>

</div>

The BlockServer cannot detect boundary loss during LSM-tree scans. Moreover, tracking boundary loss information across these two layers incurs substantial memory overhead. For instance, a single EC stripe may contain multiple discarded sub-ranges, making it hard to maintain with a memory-efficient data structure.

BlockServer 扫描 LSM-tree 时无法发现这些边界损失. 如果要跨层跟踪, 又会消耗大量内存. 例如, 一个 EC 条带内可能有多个已执行 discard 的子区间, 很难用占用内存较少的数据结构记录这些状态.

Boundary extension. The discard operation is reentrant on the same discarded range, so the BlockServer extends discard ranges to mitigate EC loss. Specifically, when the BlockServer discards a range on the LogFile, it checks if the range is adjacent to a previously discarded range. If so, the BlockServer extends the current discard range towards the adjacent discarded range by up to a few MiB. This extension not only reclaims boundary garbage from the previous discard, but also prevents a new boundary loss.

**边界扩展.** 同一区间可以重复执行 discard, 因此 BlockServer 可以通过扩大请求范围来减少 EC 损失. 它先检查待回收区间是否与此前处理过的区间相邻. 如果相邻, 就将当前请求向那个区间延伸, 最多延伸数 MiB. 这样既能回收上次遗留的边界垃圾, 也能避免在同一位置留下新的边界垃圾.

Fig. 13 illustrates an example. Two grey ranges, #1 and #3, have been previously discarded. However, this led to boundary loss for both: the right boundary of #1 and the left boundary of #3. Now, a new discard range #2 appears between them. (a) Without boundary extension, discarding range #2 causes new boundary loss on its left and right boundaries, which makes two EC stripes unreclaimable. (b) In contrast, with boundary extension, the discard range is extended to slightly overlap with ranges #1 and #3. This eliminates the boundary losses between range #2 and its neighbors at the LogFile.

图 13 给出了一个例子. 灰色区间 #1 和 #3 已执行 discard, 但 #1 的右边界和 #3 的左边界仍有垃圾残留. 新的待回收区间 #2 位于两者之间. 如果不扩展边界, #2 的左右两端也会留下垃圾, 最终导致两个 EC 条带都无法回收. 扩展后, #2 的回收范围与 #1, #3 略有重叠, 就能一并回收这些边界垃圾.

![图 13: 扩展 discard 区间以消除 EC 损失](/assets/images/posts/discogc/figure-13.webp)

Discard-friendly EC stripes. We eliminate cluster loss by aligning the stripe unit size in EC stripes with the cluster size. Specifically, we configure the stripe unit size to be n * 4 * 4064B. Since LogFiles accommodate arbitrary request sizes, this alignment does not impact the efficiency of write and discard operations. Fig. 14 illustrates the cluster loss caused by misaligned EC stripes (a) and its elimination with cluster-aligned EC stripes (b).

**适合 discard 的 EC 条带.** 要消除 cluster 损失, 我们让 EC 条带单元的大小与 cluster 对齐, 具体设为 n * 4 * 4064 B. LogFile 本来就支持任意大小的请求, 因而这一调整不会影响写入和 discard 的效率. 图 14 展示了 EC 条带未对齐时的 cluster 损失, 以及对齐后消除损失的效果.

## 5.3 discard 批处理与调度

MetaPage update overhead on UFS. Each discard request on the UFS requires modifying the MetaPage, which entails SSD writes and consumes CPU resources. When a burst of discard requests arrives (`e.g.`, the BlockServer issues excessive discard requests during one round of the LSM-tree scan), the foreground throughput and latency will be degraded.

**UFS 的 MetaPage 更新开销.** 每次 discard 都需要更新 MetaPage, 既要写入 SSD, 也会消耗 CPU. 如果短时间内涌入大量请求, 例如 BlockServer 在一轮 LSM-tree 扫描中发出了过多 discard 请求, 前台吞吐量和延迟就会受到影响.

Discard batching. The UFS needs to modify the MetaPage only once when multiple discard requests target the same chunk. Therefore, we introduce discard batching. The BlockServer groups multiple discard ranges of the same LogFile into one discard request to alleviate the MetaPage modification overhead. The maximum number of ranges in one discard request is configurable (between 1 and 64).

**discard 批处理.** 多个请求指向同一 chunk 时, UFS 只需更新一次 MetaPage. 因此, BlockServer 将同一 LogFile 的多个待回收区间放进一个 discard 请求, 减少元数据更新. 每个请求允许携带的最大区间数可以设为 1 到 64.

Discard task scheduling mechanism. To prevent excessive discard requests from degrading overall performance, the BlockServer implements a parallelism-aware discard task scheduler that maximizes space reclamation efficiency while limiting the number of concurrent requests. Discard tasks are generated at the segment granularity, with parallelism capped at P. Periodically, the BlockServer selects the top-k segments with the largest discard ranges, where k is computed based on P and the number of ongoing tasks. For each selected segment, the BlockServer maps discard ranges to their corresponding LogFiles and batches those ranges per LogFile into a single discard request, which is then sent to ByteStore.

**discard 任务调度.** BlockServer 根据当前并行度调度任务, 在限制并发请求数的前提下, 尽量提高回收效率. 每个任务处理一个 segment, 同时运行的任务数最多为 P. BlockServer 定期挑选待 discard 区间最大的前 k 个 segment, k 取决于上限 P 和正在运行的任务数. 对每个选中的 segment, 再按 LogFile 归集待回收区间, 将同一文件的区间合为一个请求, 发给 ByteStore.

Flow control. Despite the use of batching and parallelism control, a large number of discardable ranges in segments still cause a burst of discard requests. We employ a discard flow control mechanism in BlockServer. It limits the maximum discard IOPS to mitigate performance variations.

**流量控制.** 即使限制了并行度并采用批处理, segment 中如果有大量待回收区间, 仍可能在短时间内产生过多请求. 为此, BlockServer 还限制了最大 discard IOPS, 减少请求突发带来的性能波动.

## 5.4 compaction 与 discard 的协作

Metadata overhead from fragmentation. Discard operations lead to sparse and fragmented LogFiles and chunks. While the SSD space usage in ChunkServer remains stable, the number of LogFiles and chunks increases. Consequently, this increases the metadata overhead for the BlockServer's LogFile index, the MetaServer's chunk index, and the UFS's MetaPage management.

**碎片化引起的元数据开销.** discard 会在 LogFile 和 chunk 中留下空洞. 即使 ChunkServer 上的 SSD 空间占用保持稳定, LogFile 和 chunk 的数量也会增加. 随之增大的, 还有 BlockServer 的 LogFile 索引, MetaServer 的 chunk 索引, 以及 UFS 管理 MetaPage 的开销.

Observation: Compaction and discard have complementary effects. Compaction can prevent fragmented LogFiles and chunks by moving data, but incurs write amplification. Discard is the inverse. This observation leads to a coordinated strategy: We use lightweight, high-frequency discard operations as the primary mechanism for garbage reclamation, while employing relatively low-frequency compaction to mitigate fragmentation and alleviate metadata pressure.

compaction 与 discard 恰好可以互补. compaction 通过搬移数据减少 LogFile 和 chunk 的碎片, 代价是写放大; discard 不需要搬移数据, 却会留下碎片. 因此, 我们主要依靠开销较小的 discard 高频回收垃圾, 再以较低频率执行 compaction, 整理碎片并减轻元数据管理压力.

Garbage ratio calculation. We define "Valid Data" as the data in a LogFile that is still referenced by the segment's index. "Total Data" refers to all undiscarded data in the LogFile. In the system with compaction-only GC, the BlockServer calculates the garbage ratio (GR) of a LogFile as:

**垃圾比例计算.** Valid Data 指 LogFile 中仍被 segment 索引引用的数据, Total Data 指该文件中尚未执行 discard 的全部数据. 仅使用 compaction 时, 垃圾比例按以下公式计算:

<div class="paper-shared">

```text
GR = 1 - Valid Data / Total Data
```

</div>

However, discard operations introduce boundary loss. We estimate the loss per boundary (LPB) as half of the EC stripe length and then calculate GR as:

discard 会带来边界损失. 我们将单个边界的损失量 LPB 估计为 EC 条带长度的一半, 并按以下公式计算垃圾比例, 其中 Boundaries 是边界数量:

<div class="paper-shared">

```text
GR = 1 - Valid Data / (Total Data + LPB * Boundaries)
```

</div>

Scheduling compaction. Compaction and discard are scheduled independently in BlockServer. BlockServer schedules compaction tasks using dual-mode, with a scheduling interval on the order of minutes. In typical scenarios, compaction selects the top-k segments with the highest garbage ratio, reclaiming space occupied by boundary losses and small undiscardable garbage fragments to further reduce space amplification. However, when the BlockServer detects that the number of LogFiles reaches a preset threshold, indicating significant metadata overhead, compaction switches to selecting the top-k segments with the most LogFiles. This strategy alleviates metadata overhead while reducing overall fragmentation. The value of k is managed by a parallelism control mechanism, similar to discard scheduling.

**compaction 调度.** BlockServer 分别调度 compaction 和 discard, 两者相互独立. compaction 的调度间隔为分钟量级, 有两种选择任务的方式. 通常, 它挑选垃圾比例最高的前 k 个 segment, 回收边界处的残留垃圾和无法通过 discard 回收的小块垃圾, 进一步降低空间放大. 如果 LogFile 数量达到预设阈值, 说明元数据开销已较大, 就改为挑选 LogFile 数量最多的前 k 个 segment, 优先减少文件数量和碎片. 与 discard 调度一样, k 由并行度控制机制决定.

Compared to compaction-only GC, DisCoGC induces marginally higher fragmentation, leading to more frequent SSD garbage collection and a 2%-10% increase in physical write amplification. However, DisCoGC leverages its discard mechanism to reduce data movement during GC processes. Consequently, despite the higher physical write amplification, the total bytes written to the NAND flash are reduced, thereby extending the device's lifespan.

与仅使用 compaction 相比, DisCoGC 会留下稍多的碎片, 使 SSD 更频繁地执行 GC, 物理写放大增加 2%-10%. 但 discard 减少了上层 GC 需要搬移的数据. 因此, 尽管物理写放大有所增加, 写入 NAND 闪存的总字节数仍然下降, 设备寿命也得以延长.

## 5.5 trim 过滤与合并

Observation: Consistent latency for sub-size-threshold trims. Through empirical observations across various SSD models and discussions with SSD vendors, we find that trim latency remains low (under 1 ms) and consistent when the trim size is below a certain threshold (`e.g.`, 128MiB for SSD Model A in Table 2).

小区间 trim 的延迟较稳定. 通过测试多种 SSD 并与厂商讨论, 我们发现, 只要 trim 区间小于一定阈值, 延迟就能保持稳定, 且低于 1 ms. 例如, 表 2 中型号 A 的阈值为 128 MiB.

This stems from SSDs' two-phase trim implementation. When the trim command arrives, the flash translation layer (FTL) writes the trim log in the foreground, invalidates the corresponding data in the SSD's internal write cache, and signals completion to the host. Then, the FTL updates the LBA-to-PBA Table asynchronously in the background. For larger trim sizes, to avoid conflicts with the write cache, the FTL flushes the write cache before processing trim, resulting in higher latency in the foreground.

这与 SSD 分两阶段处理 trim 有关. 收到命令后, 闪存转换层 (Flash Translation Layer, FTL) 先在前台写入 trim 日志, 将内部写缓存中的对应数据标记为无效, 然后向主机报告完成. LBA 到物理块地址 PBA 的映射表则留到后台异步更新. 对较大的 trim 区间, FTL 为避免与写缓存冲突, 需要先将缓存中的数据写出, 再处理 trim, 因而前台延迟更高.

Challenge: Insufficient trim IOPS of SSD. Despite the efficient handling of small trims, we observed that trim IOPS fails to meet the system demands for frequent GC. As shown in Table 2, the trim IOPS is lower than write IOPS (`e.g.`, 3% for SSD Model B). Two problems arise from this: (1) By default, the space in UFS is marked "released" after the trim command succeeds. Untimely trim delays space reclamation, potentially exhausting UFS capacity and causing system failures. (2) Delayed trim prolongs the retention of invalid data, hampering SSD GC efficiency. It results in a higher SSD space usage, leading to an aggressive SSD GC. Finally, the physical write amplification increases, and the SSD's foreground service quality degrades.

SSD 的 trim 处理能力可能不足. 即使小区间 trim 的延迟较低, 每秒能处理的请求数仍可能跟不上频繁 GC 的需求. 如表 2 所示, trim IOPS 低于写 IOPS, 型号 B 的 trim IOPS 仅为写 IOPS 的 3%. 这会带来两个问题. (1) 默认情况下, UFS 要等 trim 成功后才将空间标记为已释放. 如果 trim 处理不及时, 回收就会延后, 甚至可能耗尽 UFS 容量, 导致系统故障. (2) 失效数据在 SSD 上停留得更久, 会降低 SSD GC 的效率, 使空间占用居高不下, 迫使 SSD 更积极地执行 GC. 结果是物理写放大增加, 前台服务质量下降.

Approach: Trim filter and merger. Based on the observation above, we implement trim filter and merger in the UFS. Trim filter issues trim only for large ranges (`e.g.`, ≥128KiB). This reduces the number of trims without increasing trim latency. Trim merger merges small ranges adjacent in LBA into a large range, which can be trimmed by one command. Overall, trim filter and merger reduce the number of trims at the cost of a slight increase in physical write amplification.

**trim 过滤与合并.** 为此, 我们在 UFS 中实现了两项优化. 过滤器只对较大区间发出 trim, 例如不小于 128 KiB 的区间, 从而减少命令数量, 又不增加单次 trim 延迟. 合并器则将 LBA 相邻的小区间合为一个大区间, 用一条命令处理. 两者以物理写放大略有增加为代价, 减少了 trim 次数.

# 6. 部署与实现

Deployment. Due to data safety implications, we deploy DisCoGC in stages. We start with the offline cluster, where business criticality is lower than online, to ensure manageable risks via progressive rollout. To further ensure data safety, we enable DisCoGC on a per-volume basis. This approach minimizes the impact of potential failures and enables targeted performance monitoring during gradual deployment.

**部署.** 为保证数据安全, 我们分阶段部署 DisCoGC. 先从业务重要性低于在线集群的离线集群开始, 逐步扩大范围, 控制风险. 同时, 按卷开启功能, 既能缩小潜在故障的影响范围, 也便于在上线过程中观察各卷的性能.

During the canary deployment phase, we enabled mock discard in production: unlike regular discard, this mode only logs the discard status in memory without releasing actual data. This approach validated software correctness and ensured data safety. Following the successful completion of this phase, DisCoGC has been deployed on large-scale clusters.

灰度期间, 我们先在生产环境启用 mock discard: 只在内存中记录 discard 状态, 不真正释放数据, 以验证实现是否正确, 是否会影响数据安全. 这一阶段顺利完成后, DisCoGC 已部署到大规模集群.

Crash consistency. In our design, discard related metadata is maintained in the memory of BlockServer. Therefore, the discard mechanism only needs to handle the crash consistency of the metadata in BlockServer. The crash consistency of ByteStore is ensured by its original design.

**崩溃一致性.** discard 相关元数据保存在 BlockServer 内存中, 因而这套机制只需处理 BlockServer 侧这些元数据的崩溃一致性. ByteStore 自身仍由原有设计保证一致性.

BlockServer guarantees the crash consistency by using a per-segment discard LogFile with a Write-Ahead Logging (WAL) mechanism. It maintains the "issued discard ranges" in the memory and persists the ranges to the discard LogFile after step (1) in §4.1. The "successfully discarded ranges" are maintained and persisted in a similar way after step (5). When the system restarts, BlockServer reads logs from the discard LogFile. Then it compares the "issued" and "successfully discarded" ranges to find and retry the interrupted discard.

BlockServer 为每个 segment 设置一个 discard LogFile, 通过预写日志 (WAL) 保证崩溃一致性. 它在内存中记录已发出的 discard 区间, 并在原文第 4.1 节步骤 (1) 之后将其写入 discard LogFile, 持久保存. 已成功回收的区间也以类似方式记录, 在步骤 (5) 后持久化. 重启时, BlockServer 读取这些日志, 比较已发出请求的区间和已成功回收的区间, 找出中断的操作并重试.

Memory management. BlockServers use two bitmaps to track the "issued" and "successfully discarded" ranges for each LogFile. Each bit in these bitmaps represents a 4KiB block of uncompressed data.

**内存管理.** BlockServer 为每个 LogFile 使用两张位图 (bitmap), 分别记录已发出 discard 请求和已成功回收的区间. 每一位对应 4 KiB 未压缩数据.

To decrease memory overhead, we employ two techniques. First, the garbage ranges are long and contiguous, so there are continuous `"0"s` and `"1"s` in the bitmaps. We use roaring bitmap [19] to compress the bitmaps, which reduces the bitmap size by half. Second, instead of tracking "successfully discarded ranges" directly, we record the failed ones in a "failed bitmap". The "successful bitmap (S)" can be easily derived from "issued bitmap (I)" and "failed bitmap (F)" by S = I&(~ F). The discard failure is rare in most cases, thus the "failed bitmap" is sparser and easier to compress. This further decreases the total bitmap size by 25%-45%.

我们用两种方法减少位图的内存占用. 首先, 垃圾区间通常较长且连续, 对应的位图中就会出现连续的 0 和 1. 使用 roaring bitmap [19] 压缩这些位图, 可以将其大小减半. 其次, 改为记录失败区间, 不再直接保存成功区间. 这样, 成功位图 S 就可以由已发出请求的位图 I 和失败位图 F 推导出来: `S = I & (~F)` discard 通常很少失败, 因而失败位图更稀疏, 更容易压缩. 这一调整进一步将位图总大小降低了 25%-45%.

## 7.4 因素分析

We evaluate the individual contribution of each technique in DisCoGC. We replay the three traces using a fixed space amplification for each trace (online: 1.2, SAR: 1.05, offline: 1.2), then measure the logical write amplification and the discard ratio (the proportion of discarded ranges' total size to the discardable data's total size). The baseline is compaction-only GC. Fig. 19 shows the results.

我们逐项评估 DisCoGC 中各项技术的作用. 回放三类轨迹时, 分别将空间放大固定为: 在线 1.2, SAR 1.05, 离线 1.2. 测量指标为逻辑写放大和 discard 回收比例 (discard ratio), 后者等于已通过 discard 回收的区间总大小, 除以可通过 discard 回收的数据总大小. 基线为仅使用 compaction 的 GC, 结果见图 19.

+Discard. Enabling discard and flow control leads to an 8.4%-13.9% reduction in logical write amplification across all traces. The system performs fewer compactions as discard reclaims some garbage. The discard ratio is 0.45-0.88, indicating that the flow control throttles some discard requests.

+Discard. 启用 discard 和流控后, 各轨迹的逻辑写放大下降 8.4%-13.9%. 一部分垃圾由 discard 回收, 需要执行的 compaction 因而减少. 此时 discard 回收比例为 0.45-0.88, 说明仍有一部分请求受到流控限制.

+Batch. Enabling discard batching with a batch size of 64 further drops the logical write amplification by 2.7%-11.7% and increases the discard ratio to nearly 1. Batching reduces the total number of discard requests, allowing nearly all the requests to be processed, thus reducing compaction and optimizing the logical write amplification.

+Batch. 再启用批处理, 将每批区间数上限设为 64, 逻辑写放大进一步下降 2.7%-11.7%, discard 回收比例接近 1. 批处理减少了请求总数, 使几乎所有请求都能得到处理, 因而进一步减少了 compaction 及其写放大.

+BoundExt. Finally, the boundary extension completes the DisCoGC design and decreases the logical write amplification by another 5.5%-16.1%. This is because boundary extension reclaims the garbage at the boundaries, which improves the GC efficiency, thus lowering the logical write amplification at the same space amplification.

+BoundExt. 最后加入边界扩展, 完成 DisCoGC 的全部优化后, 逻辑写放大又下降了 5.5%-16.1%. 边界扩展能够回收残留在边界的垃圾, 提高 GC 效率, 因而在空间放大相同的条件下, 逻辑写放大更低.

In addition, foreground bandwidth and latency remained stable across all configurations for each trace.

此外, 每类轨迹在所有配置下的前台带宽和延迟均保持稳定.

## 7.6 trim

We evaluate the effect of trim-related optimizations on DisCoGC using the FIO benchmark (random writes at 8MiB granularity using 64KiB blocks). The experiments are conducted on the SSD models listed in Table 2 with other optimizations, such as boundary extension, enabled.

我们使用 64 KiB 块, 按 8 MiB 粒度随机写入的 FIO 负载, 评估 trim 相关优化对 DisCoGC 的影响. 实验采用表 2 的 SSD, 并开启边界扩展等其他优化.

### 7.6.1 SSD 型号 A

Trim. Enabling trim reduces the physical write amplification from 1.4 to 1.3 by avoiding unnecessary data movement during the SSD GC. Trim. 只开启 trim 时, 物理写放大和删除延迟都很高. 此时 trim IOPS 已达到 SSD 上限, 空间无法及时释放, SSD 被迫更积极地执行 GC, 影响前台性能, 甚至可能导致系统崩溃 (原文第 4.5 节).

## 7.7 CPU 与内存占用

We observed the CPU and memory usage by replaying the offline trace with 60% SSD space usage and space amplification=1.25. DisCoGC reduces the CPU usage to 82.9% of compaction-only GC, while slightly increasing memory usage to 102.9%. The reduction in CPU usage results from reduced compactions, which are CPU-intensive due to heavy read and write operations. While DisCoGC requires extra memory to maintain discard bitmaps, this overhead is effectively controlled by the methods in §5.

我们在 SSD 空间占用为 60%, 空间放大为 1.25 的条件下回放离线轨迹. DisCoGC 的 CPU 占用降至仅使用 compaction 时的 82.9%, 内存占用略升至 102.9%. CPU 占用下降, 是因为 compaction 减少了. compaction 需要执行大量读写操作, 因而消耗较多 CPU. DisCoGC 虽然需要额外内存保存 discard 位图, 但原文第 5 节的方法有效控制了这部分开销.

# 8. 实践经验

Should we adopt DisCoGC? Trace analysis can determine whether an append-only storage system benefits from DisCoGC. As shown in §3.2 and §6.3, our experience is: (1) If the workload is sequential with frequent overwrites, adopt DisCoGC without hesitation. (2) If the workload is random and fragmented, the benefits do not justify the implementation effort. (3) If the workload is mixed, we can adopt DisCoGC with confidence for its robustness.

是否采用 DisCoGC? 可以先分析 I/O 轨迹, 判断只追加存储系统能否从中受益. 根据原文第 3.2 节和第 6.3 节的经验: (1) 如果写入顺序性强, 又经常覆盖已有数据, 就应采用 DisCoGC. (2) 如果写入随机且零碎, 收益不足以抵消实现成本. (3) 如果运行的是混合负载, DisCoGC 对不同负载的适应能力使其仍然值得采用.

How to set DisCoGC parameters? DisCoGC can be fine-tuned through several key parameters (§4.3), including ranges per discard batch, discard parallelism and maximum discard IOPS (for flow control). First, we tune the maximum batch size to 32 or 64 to prevent CPU usage bursts in ChunkServers. Second, we limit the maximum discard IOPS to ensure that the CPU overhead increases by less than 2% in the worst case. Lastly, while maintaining the average CPU overhead at 1.2%, we maximize the other parameters to the greatest possible.

如何设置参数? 主要参数包括每批 discard 的区间数, discard 任务并行度, 以及用于流控的最大 discard IOPS (原文第 4.3 节). 首先, 将每批区间数的上限设为 32 或 64, 避免 ChunkServer 的 CPU 占用突然升高. 其次, 限制最大 discard IOPS, 让最坏情况下新增的 CPU 开销也小于 2%. 最后, 在平均 CPU 开销保持为 1.2% 的前提下, 尽量调高其他参数.

After tuning, in most cases, the batch size is approximately 10, and the CPU usage of DisCoGC is about 1%. A write burst triggers a large amount of discard requests, causing garbage to initially accumulate due to the parallelism limit. This accumulation increases the stale ranges in each LogFile, which in turn enlarges the batch size to accelerate garbage reclamation. In an extreme burst, the batch size and discard IOPS both increase to the threshold. Then, discard alone cannot reclaim garbage effectively, and the garbage ratio of the LogFiles increases, then the garbage is reclaimed by compaction. Discard batching, parallelism control and flow control work in concert to cap the maximum CPU and SSD usage of DisCoGC. This ensures foreground service quality during bursts.

调优后, 大多数情况下每批约包含 10 个区间, DisCoGC 的 CPU 占用约为 1%. 写入突发时, 会产生大量 discard 请求. 并行度限制使垃圾暂时积累, 每个 LogFile 中待回收的区间随之增多, 一个批次便能处理更多区间, 加快回收. 如果突发过于剧烈, 批量大小和 discard IOPS 都达到上限, 单靠 discard 就来不及回收垃圾. 此时 LogFile 的垃圾比例上升, 再由 compaction 接手回收. 批处理, 并行度控制和流控共同限制 DisCoGC 的 CPU 与 SSD 资源消耗, 保障突发期间的前台服务质量.

Do we need trim optimizations? As observed in §6.6, the effectiveness of the trim command and its related optimizations vary across different SSD models. Therefore, we can choose the target SSD models by comparing their maximum trim IOPS with the workload's demand. If an SSD's maximum trim IOPS can meet the workload's demand without extra optimizations or foreground performance degradation, we can only enable trim and disable other optimizations. For other SSDs, enabling both the trim filter and merger is more effective than using the filter alone. We can enable both optimizations and tune the filter size to constrain the trim IOPS to below 85% of the SSD's maximum trim IOPS, thereby preventing impact on foreground services.

是否需要 trim 优化? 原文第 6.6 节表明, trim 及相关优化的效果取决于 SSD 型号, 因而应先比较设备的最大 trim IOPS 与负载需求. 如果不做额外优化就能满足需求, 且不影响前台性能, 只开启 trim 即可. 对其他 SSD, 同时启用过滤和合并比只启用过滤更有效. 可以调整过滤阈值, 将 trim IOPS 控制在设备最大值的 85% 以下, 避免影响前台服务.

How to monitor DisCoGC? The monitor triggers an alert to the site reliability engineer (SRE) if the discard ratio is below 80% for more than 10 minutes while SSD space usage is above 85% and still increasing. This indicates that discard requests are being throttled by the parallelism and flow controls, and compaction cannot reclaim the garbage promptly. Consequently, the SSD is at risk of running out of space.

如何监控? 如果 discard 回收比例低于 80% 的状态持续超过 10 分钟, 同时 SSD 空间占用超过 85% 且仍在上升, 监控系统就向站点可靠性工程师 (SRE) 告警. 这说明 discard 请求受到了并行度和流控限制, compaction 也来不及回收垃圾, SSD 存在空间耗尽的风险.

The SRE's response depends on system load. If the overall I/O utility is below 70%, the SRE increases the discard task parallelism and maximum discard IOPS. Otherwise, if the cluster has offline workloads, the SRE throttles the offline I/O. If the I/O utility is high and no workload can be throttled, the SRE adds some backup ChunkServers to the ByteStore cluster or migrates some volumes to another ByteDrive cluster.

SRE 根据系统负载采取措施. 如果总体 I/O 利用率低于 70%, 就提高 discard 任务并行度和最大 discard IOPS. 如果利用率较高, 且集群中有离线负载, 就对离线 I/O 限速. 如果没有可以限速的负载, 则向 ByteStore 集群加入备用 ChunkServer, 或将部分卷迁移到其他 ByteDrive 集群.

# 9. 相关工作

Write and space amplification. In flash-based SSDs, the problem of write amplification from the flash translation layer (FTL) gains attention [27], as it degrades flash lifetime. In addition to the device-level write amplification, researchers identify the write amplification from the file system layer [32], which also leads to flash lifetime issues. The write amplification problem has been intensively studied since then in both file systems [30, 31, 40] and key value stores [21, 37-39]. Besides write amplification, the space amplification problem is discussed in different storage systems [22, 24-26, 36].

**写放大与空间放大.** SSD 的闪存转换层 (FTL) 会产生写放大, 缩短闪存寿命, 这一问题受到研究者关注 [27]. 此外, 文件系统层产生的写放大同样会影响闪存寿命 [32]. 此后, 文件系统 [30, 31, 40] 和键值存储 [21, 37-39] 中的写放大得到了广泛研究, 不同存储系统中的空间放大问题也已有讨论 [22, 24-26, 36].

Cross-layer garbage collection. In flash storage, there are a number of research attempts to address the garbage collection redundancy and the conflict between the file system and FTL layers. Researchers have tried to open up the SSD for direct flash management (`a.k.a.`, Software Managed Flash or Open-Channel SSD) with only a single-layer garbage collection [32], and also tried to coordinate the garbage collection operations between different layers [17, 33, 40].

**跨层垃圾回收.** 在闪存存储领域, 许多研究尝试解决文件系统与 FTL 重复执行 GC, 或两层 GC 相互冲突的问题. 一种思路是开放 SSD, 由软件直接管理闪存, 即软件管理闪存或 Open-Channel SSD, 从而只保留一层 GC [32]. 另一种思路是协调各层的 GC 操作 [17, 33, 40].

The extension of the trim or discard command between operating systems and SSD devices was extensively discussed around 2010 [1-6, 34]. The trim or discard command allows filesystems to inform the SSD controller to invalidate an LBA range. After a range is trimmed, the corresponding space on the SSD is freed, and the stale data will no longer be migrated in the GC process, which improves the GC efficiency [28]. Slack Space Recycling [35] allows new writes to reuse the log space of stale data. The stale data is discarded through direct overwriting, a process that avoids compaction. IPLFS [29] virtualizes an unlimited logical address space of filesystems by using discard/trim commands to abandon stale data.

2010 年前后, 研究者广泛讨论了在操作系统与 SSD 之间增加 trim 或 discard 命令支持 [1-6, 34]. 文件系统通过这些命令通知 SSD 控制器, 某个 LBA 区间的数据已经失效. 执行 trim 后, SSD 释放对应空间, GC 也不再搬移这些失效数据, 从而提高回收效率 [28]. Slack Space Recycling [35] 允许新写入直接复用失效数据占据的日志空间, 以覆盖写入的方式丢弃旧数据, 无需执行 compaction. IPLFS [29] 则通过 discard/trim 丢弃失效数据, 为文件系统虚拟出无限的逻辑地址空间.

In comparison, DisCoGC addresses unique challenges of multi-layer garbage collection in cloud storage, and presents experiences of real production usage.

DisCoGC 则着重解决云存储中多层垃圾回收遇到的特有问题, 并介绍了实际生产环境中的应用经验.

# 10. 结论

Guided by production trace analysis in ByteDance, we propose DisCoGC, a GC method that coordinates compaction and discard for multi-layer cloud storage systems. DisCoGC reclaims long, contiguous ranges of stale data efficiently while addressing the challenges of integrating discard into a multi-layer storage system. We deploy it in real cloud storage, and online monitoring demonstrates that DisCoGC improves the space amplification-write amplification trade-off and lowers TCO by about 20% without degrading performance.

通过分析字节跳动的生产 I/O 轨迹, 我们提出了 DisCoGC, 在多层云存储系统中结合 compaction 与 discard 回收垃圾. 它能够高效回收长而连续的失效数据区间, 并解决 discard 应用于多层存储栈时遇到的问题. 实际部署和在线监控表明, DisCoGC 能更好地兼顾空间放大与写放大, 在不影响性能的前提下, 将 TCO 降低约 20%.
