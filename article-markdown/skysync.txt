# 0. 摘要

File synchronization (sync) is of increasing significance for not only intra-cloud but also inter-cloud applications and services, as cloud computing is evolving into the Sky computing paradigm with the illusion of utility computing on an infrastructure of multiple geographically-distributed clouds. However, existing file sync schemes, mainly including fixed-sized chunking (FSC) based sync and content-defined chunking (CDC) based sync, heavily rely on complex algorithms for generating the delta data. These algorithms perform costly processing operations including (i) file chunking, (ii) chunk checksum computation, and (iii) chunk searching, which incur high computational overhead thus lowering sync performance.

云计算正在向 Sky computing 演进: 将多个地理分散的云整合为基础设施, 让用户像使用公共服务一样使用计算资源. 文件同步不仅对云内应用重要, 对跨云应用和服务也愈发关键. 然而, 现有方案主要基于固定大小分块 (FSC) 或内容定义分块 (CDC), 都依赖复杂算法生成增量数据. 文件分块, 块校验和计算以及块查找等操作需要大量计算, 降低了同步性能.

This paper presents SkySync, a novel file sync scheme based on collaborative delta generation. Our insight is that the conventional storage layer has already maintained rich metadata (like checksums and cryptographic digests) for management purpose, `e.g.`, to verify integrity and detect errors. Therefore, we leverage the existent metadata of the storage layer to obtain the chunk checksums with simple adaptation and combination, thus effectively reducing the computational overhead. We further streamline the chunk searching process by reusing checksum data produced during prior computations. We have implemented the FSC-based and CDC-based SkySync schemes by enhancing the communication protocol of the state-of-the-art rsync and dsync, respectively. Evaluation results show that compared to the existing file sync schemes (rsync and dsync), SkySync significantly reduces the computational overhead by up to 89.3% and improves the client and server sync performance by 1.1× ~ 2×, while maintaining a consistent level of network traffic.

本文提出 SkySync, 一种通过协同生成增量数据加速文件同步的方案. 我们观察到, 传统存储层为完整性验证和错误检测等管理功能, 已维护了丰富的校验和与密码学摘要. 通过简单调整和组合这些现有元数据, 即可获得同步所需的块校验和, 减少计算开销. 我们还复用已有校验和, 简化块查找. 基于 rsync 和 dsync 的通信协议扩展, 分别实现了 FSC 和 CDC 两种 SkySync. 实验表明, 相比 rsync 和 dsync, SkySync 最多减少 89.3% 的计算开销, 将客户端和服务器的同步性能提高到原来的 1.1-2 倍, 同时保持相近的网络流量.

# 1. 引言

Many traditional cloud storage services <sup>[15, 21, 27, 30]</sup>, distributed storage systems <sup>[55, 61, 69]</sup>, and backup tools <sup>[6, 29, 53]</sup> provide file synchronization (sync) capabilities for efficient and reliable data processing. Moreover, as cloud computing is evolving into the Sky computing paradigm <sup>[11, 41, 48, 64, 78]</sup> with the illusion of utility computing on an infrastructure of multiple geographically-distributed clouds, file sync is of increasing significance for not only intra-cloud but also inter-cloud applications and services.

许多云存储服务 <sup>[15, 21, 27, 30]</sup>, 分布式存储系统 <sup>[55, 61, 69]</sup> 和备份工具 <sup>[6, 29, 53]</sup> 都支持文件同步, 以实现高效可靠的数据处理. 随着云计算向 Sky computing 演进 <sup>[11, 41, 48, 64, 78]</sup>, 多个地理分散的云被整合成可按需使用的计算基础设施, 文件同步对云内和跨云应用与服务都越来越重要.

Existing file sync schemes employ either full sync or delta sync techniques. Compared to full sync, delta sync is usually more efficient as it only needs to transfer the modified portion of a file. This has recently led to an increasing research emphasis on delta sync, particularly in scenarios involving large-scale file sync operations across multiple regions <sup>[15, 30, 45, 70, 72, 74]</sup>.

现有同步采用全量或增量技术. 增量同步只传输文件修改的部分, 通常比全量同步更高效. 因此, 近期研究越来越重视增量同步, 尤其是跨地域的大规模文件同步 <sup>[15, 30, 45, 70, 72, 74]</sup>.

Existing delta-sync schemes <sup>[42, 44, 45, 56, 66, 67, 70, 71, 74, 76, 79]</sup> use various methods to identify the delta between the client (which has the new file) and the server (which has the old file). Delta generation typically involves the following steps. (i) File chunking: splitting the synchronized file into chunks based on Fixed-Sized Chunking (FSC) <sup>[66, 67]</sup> or Content-Defined Chunking (CDC) <sup>[45, 74]</sup>. (ii) Chunk checksum calculation: computing the weak checksum or the strong checksum for each chunk. (iii) Chunk searching: looking for the weak-/strong-checksum-matched chunks between the new and old files. These three steps of delta generation are crucial to all delta sync schemes.

增量同步方案 <sup>[42, 44, 45, 56, 66, 67, 70, 71, 74, 76, 79]</sup> 用不同方法识别客户端新文件与服务器旧文件的差异. 增量生成通常包括三步: (i) 文件分块, 使用固定大小分块 FSC <sup>[66, 67]</sup> 或内容定义分块 CDC <sup>[45, 74]</sup>; (ii) 计算各块的弱校验和或强校验和; (iii) 查找新旧文件中弱校验和或强校验和相匹配的块. 这三步是所有增量同步方案的核心.

Unfortunately, existing delta generation methods are complex and costly. FSC-based sync schemes, such as rsync <sup>[66, 67]</sup>, spend a considerable amount of time on checksum calculation and chunk searching <sup>[70, 76]</sup>. Although CDC-based sync schemes, such as NetSync <sup>[74]</sup> and dsync <sup>[45]</sup>, use a smaller sliding window and a more lightweight rolling checksum, they still need to calculate weak checksums of all bytes in the file, which results in high overhead. Checksum calculation and chunk searching are time-consuming, occupying substantial CPU cycles when dealing with large files and making substantial modifications to the files.

现有增量生成方法复杂且代价高. rsync <sup>[66, 67]</sup> 等 FSC 方案在校验和计算与块查找上耗时较多 <sup>[70, 76]</sup>. NetSync <sup>[74]</sup> 和 dsync <sup>[45]</sup> 等 CDC 方案虽然采用更小滑动窗口和更轻量的滚动校验和, 仍需为文件的全部字节计算弱校验和. 面对大文件和大量修改, 校验和计算与块查找会消耗大量 CPU 时间.

Inefficient delta generation not only requires cloud vendors to deploy additional computing and storage resources for file sync, but also significantly increases file sync times <sup>[45, 74]</sup>. The high computational overhead of delta generation is the main factor that lowers file sync performance, and thereby limits the applicability of Sky computing. Therefore, it is vital to develop an efficient method for minimizing the computational overhead of delta generation.

低效的增量生成不仅迫使云服务商额外投入计算和存储资源, 也显著延长同步时间 <sup>[45, 74]</sup>. 其计算开销是限制文件同步性能的主要因素, 也限制了 Sky computing 的适用范围, 因而需要更高效的增量生成方法.

We observe that the high overhead of delta generation mainly comes from the calculation of chunk checksums. Our insight is that the conventional storage layer has already maintained rich metadata, such as the checksums and cryptographic digests, in modern storage systems for data integrity, error detection, deduplication, compression, authenticity protection, and other purposes as shown in Table 1 <sup>[10, 19, 25, 28, 32, 39, 40, 62, 69, 80]</sup>. For instance, the fs-verity <sup>[19]</sup> and dm-verity <sup>[14]</sup> are support layers that enable file systems and block devices to seamlessly provide integrity and authenticity protection for files and blocks by using cryptographic digests; BTRFS and ZFS apply checksums to both data and metadata stored within them <sup>[9, 10, 37]</sup>; and deduplication storage systems calculate checksums for identifying duplicated data <sup>[54, 63, 73, 77, 82]</sup>. Many distributed storage systems, such as HDFS <sup>[62]</sup>, BlueStore <sup>[39]</sup>, MooseFS <sup>[25]</sup>, Haystack <sup>[40]</sup>, and OneFS <sup>[28]</sup>, also provide checksums for data protection and error detection. Moreover, major cloud vendors, including Amazon Web Services (AWS) <sup>[7]</sup>, Google Cloud Platform (GCP) <sup>[20]</sup>, Microsoft Azure <sup>[46]</sup>, and Alibaba Cloud <sup>[4, 80]</sup>, have provided checksums for data integrity verification.

我们观察到, 增量生成的主要开销来自块校验和计算. 现代存储系统本就为数据完整性, 错误检测, 去重, 压缩和真实性保护等功能维护校验和及密码学摘要, 如表 1 所示 <sup>[10, 19, 25, 28, 32, 39, 40, 62, 69, 80]</sup>. 例如, fs-verity <sup>[19]</sup> 和 dm-verity <sup>[14]</sup> 分别帮助文件系统与块设备利用密码学摘要保护文件和块的完整性与真实性; BTRFS 和 ZFS 对数据及元数据都使用校验和 <sup>[9, 10, 37]</sup>; 去重存储计算校验和以识别重复数据 <sup>[54, 63, 73, 77, 82]</sup>. HDFS <sup>[62]</sup>, BlueStore <sup>[39]</sup>, MooseFS <sup>[25]</sup>, Haystack <sup>[40]</sup> 和 OneFS <sup>[28]</sup> 等分布式系统也提供校验和用于数据保护与错误检测. AWS <sup>[7]</sup>, GCP <sup>[20]</sup>, Microsoft Azure <sup>[46]</sup> 和阿里云 <sup>[4, 80]</sup> 同样提供数据完整性校验.

Although the storage-layer metadata is originally designed for file and storage management, we argue that it can also be used for delta generation to improve file sync efficiency. With this idea, we propose SkySync, a novel file sync scheme based on collaborative delta generation. Specifically, SkySync inherits the existent checksums or cryptographic digests from the storage layer, and designs a simple but effective method for obtaining file chunk checksums from storage-layer metadata with simple adaptation and combination.

这些元数据原本用于文件和存储管理, 但也能服务于增量生成. 据此, 我们提出协同生成增量数据的 SkySync: 复用存储层已有校验和或密码学摘要, 通过简单有效的调整和组合, 得到文件同步所需的块校验和.

This paper makes the following contributions:

研究从块设备, 文件系统, 去重系统和分布式系统获取不同元数据的方法, 提出快速校验和组合算法, 从现有元数据导出块校验和, 并进一步复用这些结果来简化和加速块查找.

# 2. 背景与动机

## 2.1 Sky computing

Sky computing extends beyond traditional cloud computing by enabling seamless interoperability across multiple, independent cloud providers. In Sky computing, users interact with a cloud service broker <sup>[41, 78]</sup> instead of directly engaging with a specific cloud provider. Users submit their jobs to the broker, which then selects the appropriate clouds to execute different parts of the jobs and manages their execution to optimize for cost, performance, and compliance requirements. For instance, machine learning serving jobs that do not require extensive data transfer during the computation can be moved to different clouds based on pricing or performance considerations. By decoupling workloads from specific cloud providers, Sky computing mitigates vendor lock-in, enhances scalability, and improves fault tolerance.

Sky computing 将传统云计算扩展到多个独立云服务商之间, 实现互操作. 用户不再直接面向特定云, 而是向云服务代理 <sup>[41, 78]</sup> 提交作业. 代理根据成本, 性能和合规要求, 选择合适的云执行作业的不同部分并管理执行. 例如, 计算期间无须大量数据传输的机器学习服务, 可以根据价格或性能在云之间迁移. 工作负载与特定云服务商解耦, 有助于缓解厂商锁定, 改善可扩展性和容错能力.

Despite the advantages, when splitting computation and storage across multiple clouds, Sky computing faces the challenge of decreased processing efficiency caused by inter-cloud data transfer limitations. Hence, delta sync, which only transfers the differences between old and new file versions, is more suitable for data sharing in Sky computing.

不过, 将计算和存储分散到多个云, 会受跨云数据传输限制而降低效率. 只传输新旧文件差异的增量同步, 因而更适合 Sky computing 的数据共享.

However, existing delta sync schemes, including FSC-based sync and CDC-based sync, bring significant computational overhead for both clients and servers, as discussed in Section 2.3. This overhead exacerbates resource contention with primary compute tasks and degrades performance, particularly in scenarios where numerous compute-intensive jobs are being executed on various clouds <sup>[41, 78, 80]</sup>. Therefore, reducing the computational cost of delta sync is essential for minimizing CPU contention and enabling efficient data sharing and processing in Sky Computing.

现有 FSC 和 CDC 增量同步却给客户端与服务器都带来大量计算开销, 详见原文第 2.3 节. 在多个云上运行大量计算密集型作业时, 这会进一步加剧与主要计算任务的资源争用, 降低性能 <sup>[41, 78, 80]</sup>. 因而减少增量同步计算成本, 是降低 CPU 争用, 实现高效跨云共享和处理的关键.

## 2.2 增量同步

Delta sync schemes are classified into FSC-based and CDC-based approaches. Many traditional commercial cloud storage services such as Dropbox <sup>[15]</sup> and Seafile <sup>[30]</sup>, as well as data backup tools such as Duplicacy <sup>[53]</sup>, Attic <sup>[6]</sup>, and Restic <sup>[29]</sup>, adopt FSC-/CDC-based delta sync to update files over Wide Area Networks (WANs).

增量同步分为 FSC 与 CDC 两类. Dropbox <sup>[15]</sup>, Seafile <sup>[30]</sup> 等商业云存储, 以及 Duplicacy <sup>[53]</sup>, Attic <sup>[6]</sup>, Restic <sup>[29]</sup> 等备份工具, 都采用这类方案通过广域网 (WAN) 更新文件.

### 2.2.1 基于 FSC 的同步

The most widely used FSC-based sync method is rsync <sup>[66, 67]</sup>, which has been adopted as the standard sync protocol in GNU/Linux. We now describe the workflow of rsync which consists of three phases, as shown in Figure 1(a):

最广泛使用的 FSC 同步方法是 rsync <sup>[66, 67]</sup>, 在 GNU/Linux 中已被采用为标准同步协议. 如图 1a 所示, 其流程分为三个阶段.

Phase I: Chunking. To synchronize a file f ′, the client initiates a request to the server. Upon receiving the request, the server splits the old file f into fixed-sized chunks, and calculates the weak checksums (Adler32) and strong checksums (MD5) of each chunk. These checksums are included in the checksum list and sent back to the client.

**阶段 1:** 分块. 客户端请求同步新文件 f′. 服务器收到请求后, 将旧文件 f 划为固定大小的块, 为每块计算弱校验和 Adler32 和强校验和 MD5, 汇总成校验和列表返回客户端.

Phase II: Matching. Once the client receives the checksums, it uses a fixed-sized sliding window to calculate the weak checksums of f ′ in a byte-by-byte manner. The client then searches the checksum list for a matched weak checksum. If the current chunk under the sliding window does not match any Adler32 checksums, the window continues sliding until a match is found. When a weak-checksum-matched chunk is found, its strong checksum MD5 is calculated and compared with the corresponding chunk's MD5 in the checksum list to verify that it is a duplicate chunk.

**阶段 2:** 匹配. 客户端收到列表后, 用固定大小的滑动窗口逐字节计算 f′ 的弱校验和, 并在列表中寻找匹配. 若当前窗口不匹配任何 Adler32, 就继续滑动. 找到弱校验和匹配块后, 再计算其 MD5, 与列表中对应块的 MD5 比较, 确认是否重复.

Phase III: Reconstructing. The client then generates matching tokens and literal (delta) bytes based on phase II, which consists of the mismatched chunks and their metadata. These metadata are sent to the server, which will reconstruct file f ′ by combining file f with the delta bytes. Figure 1(b) shows the process of rolling checksum and chunking searching. The sliding window size of rsync is usually set at the kilobyte (KB) level (`e.g.`, 4 or 8 KB). During the process of searching for weak-checksum-matched chunks, rsync employs an additional hash table on the client side to store the weak checksums of the old file. Each entry in this hash table consists of a 16-bit hash code generated from the 32-bit Adler32 checksum. A 16-bit hash code can point to multiple weak and strong checksums. Thereby, the chunk searching mechanism of rsync traverses from the 16-bit hash code to the 32-bit weak checksum and eventually to the strong checksum in order to identify each matched chunk between the old and new files.

**阶段 3:** 重建. 客户端根据匹配结果生成匹配标记和原始增量字节, 包括未匹配块及其元数据, 并发送给服务器. 服务器将旧文件 f 与增量字节组合, 重建 f′. 图 1b 展示滚动校验和与块查找: rsync 的窗口通常为 KB 级, 如 4 或 8 KB. 客户端额外维护哈希表, 保存旧文件弱校验和. 每个表项使用从 32 位 Adler32 生成的 16 位哈希码, 一个哈希码可能对应多个弱校验和与强校验和. 查找因此需要从 16 位哈希码, 到 32 位弱校验和, 再到强校验和, 逐级确定新旧文件的匹配块.

### 2.2.2 基于 CDC 的同步

The state-of-the-art CDC-based sync methods, such as dsync <sup>[45]</sup>, have been proposed to simplify the rolling checksum process. The core workflow of dsync is depicted in Figure 2(a).

dsync <sup>[45]</sup> 等 CDC 方案旨在简化滚动校验和处理, 其核心流程见图 2a.

Phase I: Chunking. The client initially splits the new file f ′ into chunks based on CDC <sup>[75]</sup> technique. For each chunk, the client computes a weak checksum using the FastFP algorithm <sup>[45]</sup>. Along with the chunk metadata, these weak checksums are compiled into a checksum list and transmitted to the server. Upon receiving the checksum list, the server splits the old file f into chunks using CDC technique and calculates weak checksums of the chunks.

**阶段 1:** 分块. 客户端用 CDC <sup>[75]</sup> 划分新文件 f′, 通过 FastFP <sup>[45]</sup> 为各块计算弱校验和, 连同块元数据组成列表发送给服务器. 服务器随后用 CDC 划分旧文件 f, 并计算各块弱校验和.

Phase II: Matching. The server then identifies the weak-checksum-matched chunks and calculates their strong checksums (SHA-1). These strong checksums, along with the corresponding chunk metadata (referred to as matching tokens) are sent back to the client. Upon receiving the matching tokens, the client calculates the strong checksums for the matched chunks and compares them with the strong checksums provided by the server. If the strong checksums align, it confirms that these chunks are duplicates. We omit the third phase of dsync as it is analogous to that of rsync. Dsync leverages a small sliding window (`e.g.`, of 48 bytes) that moves over the file contents as shown in Figure 2(b). The checksum of the window is compared against a predefined value. When a match is found, a chunk boundary is declared. Dsync moves the chunk searching process to the server side, thereby reducing the redundant strong checksum calculations of the weak-checksum-mismatched chunks.

**阶段 2:** 匹配. 服务器识别弱校验和匹配的块, 计算其 SHA-1 强校验和, 连同块元数据, 即匹配标记, 返回客户端. 客户端为这些块计算强校验和并比较, 一致即可确认重复. 第三阶段与 rsync 类似, 此处省略. 如图 2b 所示, dsync 使用较小窗口, 如 48 字节, 在文件上滑动. 窗口校验和满足预定义值时, 就确定一个块边界. dsync 将块查找移到服务器, 避免为弱校验和不匹配的块重复计算强校验和.

## 2.3 动机与挑战

We evaluate the total sync time of rsync and dsync in representative intra-/inter-cloud scenarios. Our testbed, detailed in Section 4.1, reflects typical cloud deployments, consisting of cloud virtual machines (`e.g.`, AWS EC2 <sup>[5]</sup> and Alibaba Cloud ECS <sup>[3]</sup>) which rely on backend cloud storage such as Elastic Block Storage (EBS) <sup>[80]</sup> and object storage services (OSS) like AWS S3 <sup>[7]</sup>. The evaluation is performed on 10MB and 100MB files from public datasets <sup>[35, 74]</sup> under a 500Mbps network, with varying modification sizes.

我们在代表性云内与跨云场景下评估 rsync 和 dsync 的总同步时间. 原文第 4.1 节的测试环境模拟典型云部署: AWS EC2 <sup>[5]</sup>, 阿里云 ECS <sup>[3]</sup> 等虚拟机, 使用 EBS <sup>[80]</sup> 或 AWS S3 <sup>[7]</sup> 等后端云存储. 实验取公共数据集 <sup>[35, 74]</sup> 的 10 MB 和 100 MB 文件, 在 500 Mbps 网络下改变修改量.

Due to result similarities, we only show the "insert" modification in Figure 3. Figure 3(a) and 3(b) detail the time consumed by the client, network, and server within the total sync time. The client and server sync times dominate, accounting for 71.2% to 93.7% of the total sync time. This is primarily due to the computational overhead introduced by checksum calculations and searching operations at both the client and server. For rsync, the client sync time grows significantly with modification size, surpassing the server sync time. In contrast, dsync uses a faster rolling algorithm to identify modified chunks, making its client and server sync time more dependent on the file size than modification size. The network transfer time increases with modification size but remains a relatively small fraction. In modern cloud data centers with high-speed WAN infrastructure (`e.g.`, over 500Mbps), the network transfer time is typically shorter than the client and server sync times.

由于结果相似, 图 3 只展示插入修改. 图 3a, 3b 将总时间分为客户端, 网络和服务器三部分. 两端处理占总时间的 71.2%-93.7%, 主要是校验和计算与查找. rsync 客户端耗时随修改量明显增加, 超过服务器; dsync 使用更快滚动算法识别修改块, 两端耗时更多取决于文件大小而非修改量. 网络传输时间虽随修改量增长, 占比仍较小. 现代云数据中心具有较快广域网, 如超过 500 Mbps, 网络时间通常短于客户端和服务器处理时间.

Figures 3(c)-3(f) further decompose the client and server sync time into checksum calculation (calc), chunk searching (searching), and other operations (others). Remarkably, checksum calculation and searching together account for up to 95% of the total sync time in both rsync and dsync. Specifically, rsync incurs significant computational overhead due to its checksum calculation on the client and server. While dsync's sync times are lower than rsync's, it still faces overhead from calculating weak checksums for all file bytes. Additionally, both rsync and dsync suffer from inefficient chunk searching, requiring traversal from 16-bit hash codes to 32-bit weak checksums and strong checksums. These observations highlight checksum calculation and searching as the primary bottlenecks for both FSC-based and CDC-based sync methods.

图 3c-3f 进一步分解校验和计算 (calc), 块查找 (searching) 和其他操作 (others). 在 rsync 和 dsync 中, 前两者合计最高占总同步时间的 95%. rsync 两端的校验和计算开销很大; dsync 虽然更快, 仍需为文件全部字节计算弱校验和. 两者的块查找还要从 16 位哈希码逐级访问 32 位弱校验和与强校验和, 效率不高. 因而, 校验和计算和查找是 FSC 与 CDC 同步共同的主要瓶颈.

Although high-end CPUs can accelerate checksum/hash calculations with vector instruction sets (like AVX-512 <sup>[1, 58]</sup> and SSE <sup>[2]</sup>), these enhancements are insufficient to effectively reduce the computational overhead of file sync. The challenge lies in the sheer volume of checksum computations required, particularly when processing large files or handling frequent modifications. We use vector instruction sets to accelerate the checksum calculations in rsync and dsync, respectively. Following the methodology of SS-CDC <sup>[58]</sup>, we use AVX-512 gather/scatter instructions to accelerate the Adler32 in rsync and the Gear in dsync. For dsync, we further decouple its rolling hash from boundary detection and use SSE SHA-NI to accelerate its SHA-1 computation. Figure 3 also presents the hardware-accelerated sync times, which corroborate the trends observed without hardware acceleration. Although AVX-based computations yield speedups, the overall computational overhead remains substantial. The underlying irregular access patterns, limited hardware prefetching, and suboptimal cache utilization <sup>[50, 68]</sup> diminish the parallelism benefits of AVX-512, reducing the performance gains.

高端 CPU 可通过 AVX-512 <sup>[1, 58]</sup> 和 SSE <sup>[2]</sup> 等向量指令加速校验和与哈希, 但仍不足以有效消除同步计算开销, 尤其是大文件和频繁修改所需的大量计算. 我们参照 SS-CDC <sup>[58]</sup>, 用 AVX-512 的 gather/scatter 指令加速 rsync 的 Adler32 和 dsync 的 Gear. 对 dsync, 还将滚动哈希与边界检测解耦, 并用 SSE SHA-NI 加速 SHA-1. 图 3 中硬件加速结果与未加速结果趋势一致: AVX 虽带来提速, 总计算开销仍很大. 不规则访问, 有限的硬件预取和不理想的缓存利用 <sup>[50, 68]</sup>, 削弱了 AVX-512 的并行收益.

## 2.4 相关工作及其局限

Recent studies are actively focused on optimizing both FSC-based and CDC-based sync schemes to improve efficiency and effectiveness across diverse scenarios. DeltaCFS <sup>[79]</sup> integrates delta sync with NFS-like file RPC to reduce computational overhead and network traffic. PandaSync <sup>[70]</sup> dynamically selects between full and delta sync based on network conditions and workloads. WebR2sync+ <sup>[76]</sup> offloads chunk search to the server and uses locality-aware chunk matching with a lightweight checksum algorithm to lower computational costs. NetSync <sup>[74]</sup> enhances dsync by dynamically adjusting chunk sizes and compression strategies based on network conditions.

已有研究持续优化 FSC 与 CDC 同步. DeltaCFS <sup>[79]</sup> 将增量同步与类似 NFS 的文件 RPC 结合, 减少计算和流量; PandaSync <sup>[70]</sup> 根据网络和负载动态选择全量或增量同步; WebR2sync+ <sup>[76]</sup> 将块查找移到服务器, 结合局部性感知匹配和轻量校验算法降低成本; NetSync <sup>[74]</sup> 根据网络动态调整块大小和压缩策略, 改进 dsync.

The core sync processes in the studies mentioned above, remain fundamentally aligned with rsync and dsync. Despite extensive optimizations, the fundamental computational bottlenecks at both the client and server sides remain unresolved, as these approaches do not eliminate the need for exhaustive computations during file sync. This motivates us to reuse storage-layer metadata, which provides valuable insights for reducing redundant computations, to optimize sync.

这些方案的核心流程仍与 rsync 和 dsync 一致. 尽管进行了多种优化, 仍未消除同步期间全面计算的需要, 两端的根本瓶颈尚未解决. 因此, 我们希望复用存储层元数据, 减少重复计算.

Cloud storage solutions (like Dropbox <sup>[15]</sup> and Seafile <sup>[30]</sup>) rely on rsync-/dsync-like methods to sync files between the old and new versions. Dropbox employs an rsync-like method to sync files between clients and servers, as discussed in <sup>[16, 52, 76]</sup>; while Seafile utilizes a dsync-like method for file sync, as discussed in <sup>[31, 42, 81]</sup>. As a result, Dropbox and Seafile inevitably suffer from severe computational bottlenecks. Note that although (for deduplication) Dropbox and Seafile have generated fixed-size checksums that can be reused to identify modified parts of local files, they cannot use these existing checksums to generate delta data for file sync due to the boundary-shift problem <sup>[45]</sup>. They still have to adopt rsync-/dsync-like methods to calculate new checksums and generate delta data during the file sync process, even if operating on advanced file systems (such as BTRFS <sup>[9]</sup> and ZFS <sup>[37]</sup>) that already have various checksums.

Dropbox <sup>[15]</sup> 和 Seafile <sup>[30]</sup> 等云存储, 分别使用类似 rsync 和 dsync 的方法同步新旧文件 <sup>[16, 52, 76, 31, 42, 81]</sup>, 也面临严重计算瓶颈. 虽然它们为去重已生成固定大小块的校验和, 可用于识别本地文件修改, 却因边界偏移问题 <sup>[45]</sup>, 不能直接用这些校验和生成同步增量. 即使运行在 BTRFS <sup>[9]</sup> 或 ZFS <sup>[37]</sup> 等已保存校验和的文件系统上, 同步时仍需重新计算校验和并生成增量.

The storage layer has already introduced rich metadata that provides valuable insights to reduce redundant computations and improve overall system efficiency for file sync. However, the metadata and corresponding algorithms used by the storage layer are diverse and cannot be directly applied to the sync process. To address the computational overhead in file sync, we propose a lightweight file sync approach with collaborative delta generation that leverages the appropriate metadata within the storage layer.

存储层丰富的元数据为减少重复计算提供了机会, 但元数据和算法种类繁多, 不能直接套用到同步流程. 我们因此提出协同增量生成, 利用适当的存储层元数据, 实现轻量文件同步.

## 3.1 存储层的丰富元数据

We begin by analyzing the rich metadata exposed by modern storage systems. As shown in Table 1, we categorize these systems into four key classes: block devices, file systems, deduplication systems, and distributed storage systems.

如表 1 所示, 现代存储系统可分为块设备, 文件系统, 去重系统和分布式系统四类.

Block Devices. SkySync can utilize the metadata from block devices, such as dm-verity <sup>[14]</sup>. Dm-verity is a device mapper target that offers data verification for block devices by using a dedicated metadata device to store a hash tree of the data device. Each leaf node in this hash tree contains the cryptographic hash of a data block. User-space tools like cryptsetup <sup>[12]</sup> can be used to compute and dump this hash tree. Dm-verity utilizes the Linux kernel crypto API <sup>[24]</sup> (`e.g.`, SHA-256, SHA-512, etc.) to calculate the hashes.

**块设备.** SkySync 可利用 dm-verity <sup>[14]</sup> 等提供的元数据. dm-verity 是 device mapper 的一种 target, 使用专用元数据设备保存数据设备的哈希树, 叶节点包含各数据块的密码学哈希, 用于验证块设备数据. 用户态工具 cryptsetup <sup>[12]</sup> 可计算和导出该树. 哈希通过 Linux 内核 crypto API <sup>[24]</sup> 计算, 如 SHA-256 和 SHA-512.

File Systems. SkySync can leverage metadata from file systems, such as those supporting fs-verity <sup>[19]</sup>. Fs-verity is a support layer that enables file systems to seamlessly provide integrity and authenticity protection for files. Currently, it is supported by several file systems, including EXT4 <sup>[17]</sup>, F2FS <sup>[51]</sup>, and BTRFS <sup>[9, 10]</sup>. Users can enable fs-verity for a file using the FS_IOC_ENABLE_VERITY ioctl system call and retrieve verity metadata with the FS_IOC_READ_VERITY_METADATA ioctl system call. Moreover, BTRFS automatically applies checksums to both data and metadata. For example, metadata blocks include inline checksums within the B-tree node header, while each data block has a separate checksum stored in the checksum tree. BTRFS supports various hashing algorithms, including CRC32C, XXHASH, SHA-256, and BLAKE2b. ZFS also provides checksums for data and metadata. For each stored block, ZFS calculates and stores a checksum within the block pointer. User-space tools such as btrfs-progs <sup>[34]</sup> and zbd <sup>[36]</sup> can dump the checksums of files. These filesystem-level metadata not only serve the filesystem functionality but also play a vital role in enhancing the delta generation process and improving sync efficiency.

**文件系统.** SkySync 可利用支持 fs-verity <sup>[19]</sup> 的文件系统元数据. fs-verity 为文件提供完整性与真实性保护, 已获 EXT4 <sup>[17]</sup>, F2FS <sup>[51]</sup> 和 BTRFS <sup>[9, 10]</sup> 支持. 用户可通过 FS_IOC_ENABLE_VERITY ioctl 启用, 通过 FS_IOC_READ_VERITY_METADATA ioctl 获取验证元数据. BTRFS 还自动校验数据与元数据: 元数据块的校验和内嵌于 B-tree 节点头, 数据块校验和则单独保存在校验和树中, 支持 CRC32C, XXHASH, SHA-256 和 BLAKE2b. ZFS 同样校验数据和元数据, 在各块的块指针中保存校验和. btrfs-progs <sup>[34]</sup> 和 zbd <sup>[36]</sup> 等用户态工具可导出文件校验和. 这些元数据既服务于文件系统, 也能改善增量生成与同步效率.

Deduplication Systems. SkySync can also benefit from metadata provided by deduplication-based storage and backup systems <sup>[53, 59, 82, 83]</sup>. For instance, MeGA <sup>[82]</sup> uses a fine-grained deduplication framework for backup storage. It identifies and removes identical chunks while employing byte/string-level elimination for similar but non-identical chunks. The 256-bit fingerprints generated by MeGA's deduplication can serve as strong checksums for SkySync. Additionally, MeGA can calculate 32-bit weak checksums for individual chunks post-deduplication. Other deduplication systems can adopt similar approaches to provide checksums for SkySync.

**去重系统.** SkySync 可复用去重存储与备份系统 <sup>[53, 59, 82, 83]</sup> 的元数据. 例如 MeGA <sup>[82]</sup> 提供细粒度备份去重, 识别并消除相同块, 对相似但不同的块进一步消除重复字节或字符串. 其 256 位指纹可用作强校验和, 去重后还可为各块计算 32 位弱校验和. 其他去重系统也可采用类似方式提供校验和.

Distributed Systems. Distributed systems offer diverse metadata that SkySync can utilize. For example, HDFS (The Hadoop Distributed File System) <sup>[62]</sup> generates and stores checksums for each data block of an HDFS file, which are verified by the HDFS client during reads to detect corruption. BlueStore <sup>[8, 39]</sup>, a storage backend for the Ceph distributed storage system, efficiently implements full data checksums by computing a checksum for every write and verifying it on every read. MooseFS <sup>[25]</sup> provides checksums for each data block in the chunk server, designed for managing large files. SeaweedFS <sup>[32]</sup>, based on Facebook's Haystack design <sup>[40]</sup>, is an object store that handles small files efficiently and provides file checksums to ensure data integrity. It chunks files and stores their checksums in volume servers.

**分布式系统.** HDFS <sup>[62]</sup> 为文件各数据块生成并存储校验和, 客户端读取时验证以检测损坏. Ceph 的 BlueStore 后端 <sup>[8, 39]</sup> 每次写入计算校验和, 每次读取验证, 实现完整数据校验. 面向大文件的 MooseFS <sup>[25]</sup> 在 chunk server 中提供各数据块校验和. 基于 Facebook Haystack <sup>[40]</sup> 的 SeaweedFS <sup>[32]</sup> 高效处理小文件, 通过校验和保障完整性, 并将分块文件及其校验和存储在 volume server.

## 3.2 校验和计算与查找

In the case of FSC-based sync methods, SkySync directly leverages metadata of fixed-sized chunks from the storage layer. However, for the CDC-based sync methods like dsync, SkySync follows a two-step process. First, SkySync calculates the weak checksums of the variable-sized chunks, using the metadata acquired from the storage layer. Second, SkySync computes the strong checksums of the weak-checksum-matched chunks. In the following paper, for the sake of clarity and simplicity, we use CRC32C to illustrate the calculation and searching process of the weak checksum, and SHA-256 to represent the strong checksum. Note that, SkySync is not restricted to CRC32C and supports the use of any polynomial checksums that are widely employed in the storage layer.

FSC 同步直接复用存储层固定块的元数据. 对 dsync 等 CDC 方法, SkySync 分两步处理: 先根据存储层元数据计算变长块弱校验和, 再为弱校验和匹配的块计算强校验和. 下文用 CRC32C 说明弱校验和计算与查找, 用 SHA-256 表示强校验和. SkySync 并不限于 CRC32C, 也支持存储层广泛使用的其他多项式校验和.

C′<sub>F<sub>i-1</sub></sub> 是在 C<sub>F<sub>i-1</sub></sub> 后补零构成的序列, 长度与 x 相同, 其 CRC32C 可通过在原块 CRC32C 上施加相应的尾部补零运算得到. 类似地, C<sub>F<sub>i</sub></sub> 与 C<sub>R<sub>i</sub></sub> 的差异由字节段 x 和 y 构成, 因而可按公式 2 计算 C<sub>R<sub>i</sub></sub> 的 CRC32C.

This design for efficient checksum calculation is based on the algebraic properties of CRC32C. The checksum of a data sequence can be computed from the checksums of its constituent parts. Specifically, for a sequence S formed by concatenating subsequences A and B, its checksum is given by CRC(S) = CRC(A · 0<sup>|B|</sup>) ⊕CRC(0<sup>|A|</sup> · B), where · denotes concatenation, |X| is the length of sequence and 0<sup>k</sup> is a sequence of k zero bits. This combination requires inexpensive exclusive-or (XOR) and appending-zeros operations, regardless of the length of the original sequences. This property is a consequence of the linearity of CRC functions over the finite field GF(2) <sup>[49]</sup>.

这一计算方式利用 CRC32C 的代数性质: 序列校验和可由各部分校验和组合. 若 S 由 A 与 B 拼接而成, 则 CRC(S) = CRC(A · 0<sup>|B|</sup>) ⊕ CRC(0<sup>|A|</sup> · B). 其中 · 表示拼接, |X| 为序列长度, 0<sup>k</sup> 为 k 个零比特. 无论原序列多长, 组合只需低成本的异或 (XOR) 与补零操作. 这一性质源于 CRC 函数在有限域 GF(2) 上的线性性质 <sup>[49]</sup>.

Moreover, the calculation of CRC32C of C<sub>R<sub>i</sub></sub> uses the CRC32C of bytes x, which has already been calculated in the process of CRC32C calculation of C<sub>R<sub>i-1</sub></sub> . Thus, only the CRC32C of bytes y needs to be calculated in the process of the CRC32C calculation of C<sub>R<sub>i</sub></sub> . SkySync only calculates the CRC32C for the differing bytes, which are typically less than half of the average chunk size. These partial checksums are then concatenated using multiple exclusive-or operations or by appending zeros to obtain the CRC32C checksum of C<sub>R<sub>i</sub></sub> .

计算 C<sub>R<sub>i</sub></sub> 时, 还可复用前一块 C<sub>R<sub>i-1</sub></sub> 计算过程中得到的 x 的 CRC32C, 只需重新计算 y. 因而 SkySync 仅为边界差异部分计算 CRC32C, 这部分通常小于平均块长的一半. 随后通过若干异或或补零操作组合部分校验和, 得到 C<sub>R<sub>i</sub></sub> 的校验和.

The proposed weak checksum calculation method can be generalized to any checksum algorithm that supports linear combination and possesses a XOR-friendly algebraic structure <sup>[38, 47]</sup>, as exemplified by CRC32C. This provides significant flexibility for SkySync in calculating weak checksums across various systems that apply different chunk sizes.

这种方法可推广到任何支持线性组合且具有适合 XOR 运算的代数结构的校验算法 <sup>[38, 47]</sup>, CRC32C 只是其中一例. 因而 SkySync 能灵活处理不同系统的不同块大小.

### 3.2.2 块查找

The chunk searching mechanism of rsync traverses from the 16-bit hash code to the 32-bit weak checksum and ultimately to the strong checksum. This process requires frequent dereferencing of pointers to locate the matched chunks between the old and new files. Dsync performs a comparison of the FastFP weak checksums between the old and new files on the server side, utilizing an additional hash table similar to rsync. On the client side, it compares the SHA-1 checksums of the weak-checksum-matched chunks based on the matching tokens received from the server.

rsync 从 16 位哈希码逐级访问 32 位弱校验和与强校验和, 需要频繁解引用指针才能定位新旧文件的匹配块. dsync 也使用类似的额外哈希表, 在服务器比较 FastFP 弱校验和; 客户端则根据服务器的匹配标记, 比较弱校验和匹配块的 SHA-1.

In contrast with rsync and dsync, SkySync's hash table is structured as a flat array of pre-allocated buckets as shown in Figure 6. Each bucket is a sub-array capable of storing metadata for multiple chunks. To support different sync modes, a bucket can hold two distinct types of entries: one is dedicated to storing solely the weak checksums of the chunks (Entry1, utilized by CDC-based SkySync in the server side), while the other is designed to accommodate both weak and strong checksums of the chunks (Entry2, utilized by FSC-based SkySync in the client side). To manage chunk placement and lookups, SkySync employs a streamlined Cuckoo hashing scheme <sup>[60, 65]</sup> that assigns two candidate buckets to each chunk. To eliminate the overhead of separate key generation and a second hash function, SkySync derives both bucket locations directly from a chunk's existing CRC32C checksum. The primary bucket position P1, and the secondary position P2, are calculated as follows:

SkySync 的哈希表采用预分配桶的扁平数组, 如图 6 所示. 每个桶是一个子数组, 可容纳多个块的元数据. 两种表项分别用于不同模式: Entry1 只保存弱校验和, 供 CDC 模式的服务器使用; Entry2 保存弱校验和与强校验和, 供 FSC 模式的客户端使用. 为安排位置和查找, 系统采用简化的布谷鸟哈希 <sup>[60, 65]</sup>, 为每块指定两个候选桶. 为省去额外键生成和第二个哈希函数, 两个桶的位置都直接从已有 CRC32C 导出, 主位置 P1 与次位置 P2 如下.

![SkySync 的哈希表.](/assets/images/posts/skysync/figure-06.webp)

</div>

<span class="paper-caption paper-lang-en" lang="en">Figure 6: The hash table used by SkySync.</span>

P<sub>1</sub> = CRC(chunk<sub>i</sub>) mod 2<sup>l</sup> &nbsp; (3)

P<sub>2</sub> = P<sub>1</sub> ⊕ 2<sup>l-1</sup> &nbsp; (4)

</div>

Here, 2<sup>l</sup> is the size of the hash table. As shown in Equation 3, P1 is the checksum modulo the table size. P2 is then derived by flipping the most significant bit of P1 via a single XOR operation (Equation 4). This lightweight, deterministic approach ensures that a chunk's two candidate buckets always reside in different halves of the hash table, which is crucial for resolving collisions. During an insertion, a chunk's entry can be placed in either of these two locations.

哈希表大小为 2<sup>l</sup>. 公式 3 将校验和对表大小取模得到 P1, 公式 4 通过一次 XOR 翻转 P1 的最高有效位, 得到 P2. 这一轻量且确定的方法保证两个候选桶总在哈希表的不同半区, 有助于解决冲突. 插入时, 表项可放在其中任意一个位置.

SkySync pre-allocates each hash bucket with a capacity of four entries. This choice is based on our empirical finding that the table-wide load factor reaches 0.85-0.91 before any bucket overflows, allowing for high memory utilization near the practical limits of Cuckoo hashing <sup>[43, 65, 84, 85]</sup> while minimizing resizing. The overall table size 2<sup>l</sup>, is then calculated to accommodate the total number of chunks (csum_nums) at a target load_factor:

每个桶预留四个表项. 实验观察到, 在任一桶溢出前, 整表装载因子可达 0.85-0.91, 接近布谷鸟哈希的实际极限 <sup>[43, 65, 84, 85]</sup>, 兼顾内存利用率与较少扩容. 给定块总数 csum_nums 和目标装载因子 load_factor, 表大小 2<sup>l</sup> 按下式确定.

<div class="paper-shared">

l = ⌈log<sub>2</sub>((csum_nums / 4) / load_factor)⌉ &nbsp; (5)

</div>

This equation first determines the ideal number of buckets required (csum_nums/4) and then provisions additional space based on the target load_factor. Due to the lower hash collision ratio of CRC32C in comparison to Adler32 and FastFP, as well as the reduced collision ratio of a 32-bit hash value compared to a 16-bit hash value, SkySync encounters fewer entries in each bucket, resulting in a reduced need for resizing operations. Once the hash table is established, SkySync can efficiently locate the respective buckets and continuously compare the weak and strong checksums of the chunks.

公式先用 csum_nums/4 确定理想桶数, 再按目标 load_factor 预留空间. CRC32C 相比 Adler32 和 FastFP 的碰撞率更低, 32 位哈希值相比 16 位也更少碰撞, 因而每桶遇到的表项更少, 扩容需求下降. 建表后, SkySync 可高效定位桶, 连续比较块的弱校验和与强校验和.

## 3.3 通信协议

Given the potential heterogeneity of storage environments between the client and server, variations in chunk size and checksum type can preclude direct utilization of storage layer metadata. To address this challenge, SkySync implements an enhanced communication protocol to negotiate metadata settings during file sync. This negotiation process includes determining the appropriate chunk size and checksum type to be used for delta generation. Regardless of whether rsync or dsync is employed, SkySync requires both the client and server to exchange their respective chunk size and checksum type information in the initial request. Subsequently, they align on a unified setting based on the predefined strategy in Section 3.3.1 and Section 3.3.2. By establishing these parameters upfront, SkySync ensures a seamless sync process across diverse storage environments, while minimizing the need for redundant computations.

两端存储环境可能不同, 块大小和校验和类型差异使元数据无法直接复用. SkySync 通过扩展协议协商增量生成使用的块大小与校验类型. 无论采用 rsync 还是 dsync, 双方都在初始请求中交换这些信息, 再依据原文第 3.3.1 和 3.3.2 节的策略统一配置. 提前协商使不同存储环境能够顺利同步, 并减少重复计算.

### 3.3.1 处理块大小差异

When the client and server have different chunk sizes, SkySync resolves this discrepancy by aligning with the entity responsible for sending the checksum list first. Specifically, in FSC-based sync, SkySync adopts the server's chunk size, while in CDC-based sync, it aligns with the client.

SkySync 采用先发送校验和列表的一方的块大小: FSC 模式对齐服务器, CDC 模式对齐客户端.

FSC-based Alignment. In the FSC-based sync workflow (see Figure 1), the server is responsible for sending the checksum list of the old file to the client upon receiving its sync request. Therefore, in SkySync, the client aligns with the server's chunk size. Despite differing chunk sizes, the client can efficiently compute chunk weak checksums using existing storage metadata with simple adaptation and combination. For instance, if the client uses 4KB chunks while the server uses 8KB chunks, the client can derive the CRC32C checksum of an 8KB chunk S by XORing the CRC32C of two 4KB chunks A and B, `i.e.`, CRC(S) = CRC(A′) ⊕CRC(B). Here, A′ represents an 8KB chunk constructed by concatenating A with a series of zero bits. This approach enables the client to adapt to the server's chunk size using existing storage metadata with minimal computational overhead.

**FSC 模式.** 图 1 中服务器先发送旧文件校验和列表, 因而客户端采用服务器块大小. 即使原块大小不同, 客户端仍可调整组合存储元数据, 高效计算弱校验和. 例如客户端为 4 KB, 服务器为 8 KB, 可将两个 4 KB 块 A, B 的 CRC32C 组合成 8 KB 块 S 的校验和: CRC(S) = CRC(A′) ⊕ CRC(B), 其中 A′ 是 A 后补零到 8 KB 的序列. 这样只需很少额外计算即可适配.

CDC-based Alignment. In CDC-based sync workflow (see Figure 2), the client first splits the file into variable-sized chunks according to its predefined minimum/expected average/maximum chunk sizes. The server then aligns with the client's chunking strategy. Then the weak checksum of each variable-sized chunk is computed by combining the CRC32C checksums of fixed-sized chunks from the storage layer as detailed in Section 3.2.1.

**CDC 模式.** 图 2 中客户端先按预设的最小, 期望平均和最大块长进行变长分块, 服务器采用相同策略. 随后按原文第 3.2.1 节的方法, 组合存储层定长块 CRC32C, 得到各变长块弱校验和.

### 3.3.2 处理校验和类型差异

When the client and server have different checksum types, SkySync resolves this issue by adopting a default strategy that prioritizes widely supported algorithms while maintaining compatibility with existing storage metadata. Weak Checksum Selection. SkySync defaults to CRC32C as the weak checksum due to its widespread adoption in modern storage systems. If either the client or server provides CRC32C checksums, they are used directly. Strong Checksum Selection. For strong checksums, SkySync prefers cryptographic hashes such as SHA-256 or SHA-1. If both the client and the server provide cryptographic hashes, SkySync adopts the server's hash type to minimize computational overhead on the server side. For example, if the client uses SHA-256 and the server uses SHA-1, SkySync defaults to SHA-1 since the server computes the strong checksum first in both FSC and CDC.

类型不同时, 默认优先选择广泛支持的算法, 同时兼容现有元数据. 弱校验和默认 CRC32C, 因为它已被现代存储系统广泛采用; 任一端提供 CRC32C 时即可直接使用. 强校验和优先 SHA-256 或 SHA-1 等密码学哈希. 若双方都提供密码学哈希, 采用服务器类型, 以减少服务器计算. 例如客户端为 SHA-256, 服务器为 SHA-1, 则使用 SHA-1, 因为 FSC 与 CDC 都由服务器先计算强校验和.

## 3.4 提取存储层校验和

As summarized in Table 1, SkySync employs three methods to access the metadata and extract checksums across diverse storage systems, designed to balance broad compatibility with the practicalities of integration.

如表 1 所示, SkySync 通过三类方法获取元数据和校验和, 兼顾兼容性与集成成本.

(1) User-space tools. SkySync utilizes user-space tools like fs-verity and btrfs-progs to directly extract checksums into memory for local file systems such as EXT4 and BTRFS. This method operates without requiring kernel modifications or deep integration into file system, ensuring broad compatibility and ease of deployment. Although fs-verity's hash verification during reads can increase latency for small or random read workloads, it can mitigate this using a Merkle tree-based structure <sup>[19]</sup> for constant-time verification. Our tests on fs-verity-enabled file systems (EXT4, F2FS, BTRFS) using FIO <sup>[18]</sup> show a modest latency increase up to 4.7% for sequential and random read/write operations across different thread counts and block sizes. Throughput remains comparable to non-fs-verity systems. We thus conclude that enabling fs-verity has minimal impact on overall file system performance. This method shifts the integration burden to system administrators, as it requires explicit, per-filesystem configuration.

**(1) 用户态工具.** 对 EXT4, BTRFS 等本地文件系统, 使用 fs-verity 和 btrfs-progs 等工具直接提取到内存, 无须修改内核或深入集成文件系统, 易于部署. fs-verity 读取时的哈希验证可能增加小读或随机读延迟, 但其 Merkle 树结构 <sup>[19]</sup> 可实现常数时间验证, 缓解开销. 我们在启用 fs-verity 的 EXT4, F2FS 和 BTRFS 上用 FIO <sup>[18]</sup> 测试不同线程数和块大小, 顺序及随机读写延迟最多增加 4.7%, 吞吐量与未启用时相近, 因而认为整体性能影响很小. 这一方式仍需要管理员逐个文件系统显式配置.

(2) System APIs. For systems that expose APIs for metadata retrieval, SkySync leverages these interfaces to fetch checksums from metadata files stored on either local or remote servers. This method is exemplified by its use with HDFS NameNode <sup>[62]</sup>, where metadata is centrally managed and accessible via well-defined APIs. Using system APIs leverages existing distributed infrastructure to retrieve metadata quickly but may introduce network latency when accessing remote metadata servers. This latency can be partially mitigated through batched requests <sup>[32, 62]</sup> and the use of high-speed network interconnects. This API-driven method is the most robust and sustainable integration path, as it relies on stable, public interfaces maintained by the underlying system.

**(2) 系统 API.** 对提供元数据接口的系统, 利用 API 从本地或远端元数据文件取得校验和, 例如集中管理元数据且具有明确接口的 HDFS NameNode <sup>[62]</sup>. 它复用分布式基础设施快速获取信息, 但远程访问可能增加网络延迟, 可通过批量请求 <sup>[32, 62]</sup> 和高速互连部分缓解. 依赖底层维护的稳定公开接口, 是较稳健且可持续的集成方式.

(3) Custom functions. For systems lacking suitable tools or APIs, such as the MeGA deduplication system, SkySync implements custom functions to directly parse on-disk metadata formats. To simplify this process, SkySync infers chunk offsets from their sequence number and fixed size, thus avoiding the need to track complex offset maps. SkySync decouples checksum extraction from storage-specific logic, ensuring compatibility across diverse systems without deep integration. However, this approach incurs a significant maintenance burden, as each custom function may require updates to remain compatible with new versions of the target storage system.

**(3) 自定义函数.** 对 MeGA 等缺少合适工具或 API 的系统, 编写函数解析磁盘元数据. 通过序号和固定大小推导块偏移, 避免复杂偏移映射. 将校验和提取与具体存储逻辑解耦, 可减少深度集成, 适配不同系统; 但维护成本较高, 目标系统升级后可能需要同步修改解析函数.

## 3.5 实现

SkySync adopts the same data structures as rsync and dsync for transmitting the checksum list, matching tokens and delta bytes because these data structures are also efficient and suitable for SkySync.

SkySync 沿用 rsync 和 dsync 传输校验和列表, 匹配标记和增量字节的数据结构, 因为这些结构同样高效且适用.

We provide an HTTP-based communication protocol between the client and server (Network Module shown in Figure 4) to facilitate SkySync. For FSC-based SkySync, the client initiates a HTTP(S) GET request to obtain the weak checksum list of the old file from the server. Then the client sends the matching tokens and delta bytes to the server via a HTTP(S) POST request. For CDC-based SkySync, the client first posts the weak checksum list of its file to the server. Subsequently, the server responds with the matching tokens and strong checksum list to the client. Finally, the client posts the matching tokens and delta bytes to the server.

两端通过 HTTP 协议通信, 对应图 4 的网络模块. FSC 模式下, 客户端先用 HTTP(S) GET 获取旧文件弱校验和列表, 再用 POST 发送匹配标记和增量字节. CDC 模式下, 客户端先 POST 本地弱校验和列表, 服务器返回匹配标记和强校验和列表, 客户端最后 POST 匹配标记与增量字节.

We implement the client and server sides of FSC-based SkySync on top of the librsync <sup>[22]</sup> library using about 1100 lines of C++ code. As the original prototype of dsync <sup>[45]</sup> is not open-source, we implement the client and server side of dsync which leverage FastCDC as its chunking algorithm using about 1800 lines of C++ code. The prototype of dsync we implemented is as efficient as the original one. Then we implement the client and server sides of CDC-based SkySync by adding about 1600 lines of C++ code to dsync.

FSC 模式基于 librsync <sup>[22]</sup>, 两端共约 1100 行 C++ 代码. 原始 dsync <sup>[45]</sup> 未开源, 因而我们用约 1800 行 C++ 实现采用 FastCDC 的 dsync 两端, 效率与原型相当. 再增加约 1600 行 C++, 实现 CDC 模式的 SkySync.

## 4.2 微基准测试

Client and Server Sync Time. We first evaluate the client sync time of rsync, dsync, and SkySync across varying modification sizes for four different types of modifications, as illustrated in Figures 7, 8, and 9. The sync time consumed by the client, which is mainly composed of delta generation, can represent the computing overhead and resource occupation of the client during the sync. As we described in Section 2.2, rsync and dsync have different delta generation operations on the client side. Rsync computes the weak checksums of the file using a sliding window byte-by-byte. Therefore, when the modification size becomes larger, the client needs to calculate more weak checksums to find the duplicate chunks, which leads to a significant increase in client sync time. The client of SkySync-F performs 1.2×~2.0× (1.1×~1.8× with HW) faster than rsync while reducing 32.1%~64.9% (20.5%~54.3% with HW) computational overhead, owing to its faster checksum calculation and chunk searching process. The client of SkySync-C performs 1.3×~1.7× (1.2×~1.6× with HW) faster than dsync while reducing 25.7%~42.3% (20.5%~35.3% with HW) computational overhead because SkySync uses the faster exclusive-or and appending-zeros operations to calculate the weak checksums, and the lightweight hashing process to accelerate the chunk searching phase. It is worth noting that the client of SkySync-F performs fastest when the files on both client and server are identical.

**客户端与服务器同步时间.** 图 7-9 比较四种修改类型和不同修改量的客户端耗时. 其主要部分为增量生成, 可反映计算开销与资源占用. 如原文第 2.2 节所述, rsync 在客户端逐字节滑窗计算弱校验和, 修改越多, 寻找重复块所需计算越多, 耗时明显增加. SkySync-F 借助更快的计算与查找, 速度为 rsync 的 1.2-2.0 倍, HW 下为 1.1-1.8 倍, 计算开销减少 32.1%-64.9%, HW 下为 20.5%-54.3%. SkySync-C 通过异或与补零计算弱校验和, 用轻量哈希加速查找, 速度为 dsync 的 1.3-1.7 倍, HW 下为 1.2-1.6 倍; 计算开销减少 25.7%-42.3%, HW 下为 20.5%-35.3%. 两端文件相同时, SkySync-F 客户端最快.

We then evaluate the server sync time for insert modifications as shown in Figures 10 and 11. The results for other modifications are similar to the insert modifications, so we omit them here. Since the rsync server does not perform rolling checksum calculation and chunk searching, its sync time is lower than that of the client. For dsync, the server needs to calculate the weak and strong checksums of the chunks and perform chunk searching to find the weak-checksum-matched chunks. The server of SkySync only needs to read the checksums of files from the storage layer and employs the fast checksum combining and searching process. Therefore, it performs faster than other sync methods and reduces by up to 89.3% (76.5% with HW) computational overhead compared to rsync and dsync.

图 10, 11 展示插入修改的服务器耗时, 其他修改结果相似而省略. rsync 服务器不执行滚动校验和和块查找, 因而比客户端快. dsync 服务器要计算弱强校验和并查找匹配块; SkySync 只需读取存储层校验和并快速组合与查找, 最多减少 89.3% 计算开销, HW 下为 76.5%.

Total Sync Time. We evaluate the total sync time, consisting of client sync time, server sync time, and network transfer time, of different sync methods for insert modifications under 100Mbps and 500Mbps network bandwidths as shown in Figure 12. The total sync time under 100Mbps bandwidth is more than that under 500Mbps bandwidth due to the longer network transfer time, yet it is still dominated by checksum calculation and searching. As a result, we observe similar results as in previous experiments that SkySync outperforms its counterparts in all settings. When the modification size is small, SkySync-F shows the lowest total sync time. For example, SkySync-F reduces 26.7%~72.1% (18.2%~62.9% with HW) sync time compared to rsync and dsync when the modification size is smaller than 2KB (for 10MB file) and 128KB (for 100MB file).

**总同步时间.** 图 12 比较 100 Mbps 和 500 Mbps 下的插入修改, 总时间包括客户端, 服务器和网络. 100 Mbps 网络传输更慢, 但总时间仍由校验和计算与查找主导, SkySync 在各配置下均优于对比方法. 修改量较小时 SkySync-F 最快: 10 MB 文件修改小于 2 KB, 100 MB 文件修改小于 128 KB 时, 相比 rsync 和 dsync, 同步时间减少 26.7%-72.1%, HW 下为 18.2%-62.9%.

Breakdown Sync Time. We further break down the sync time for insert modifications with 100MB file. Figure 13 shows the results of different sync methods with and without hardware acceleration. SkySync-F reduces the checksum calculation time by 23.4%~88.3% (12.6%~81.1% with HW) and the chunk searching time by up to 61.3% compared to rsync, as SkySync-F leverages storage-layer metadata and a lightweight hashing process to expedite the delta generation. Additionally, SkySync-C reduces the checksum calculation time by 24.5%~33.6% (21.7%~29.5% with HW) and the chunk searching time by 65.7% compared to dsync, owing to SkySync-C's faster checksum combining and chunk searching processes. Moreover, the performance difference between hardware-accelerated and non-accelerated results is up to 10.8%, primarily due to reduced total sync time from faster checksum calculations across all three methods include SkySync. Nevertheless, the overall speed-up effect on sync remains modest. SkySync continues to outperform both rsync and dsync, even under hardware acceleration.

**耗时分解.** 图 13 分析 100 MB 文件的插入修改. SkySync-F 复用元数据和轻量哈希, 相比 rsync, 校验和计算时间减少 23.4%-88.3%, HW 下为 12.6%-81.1%, 块查找最多减少 61.3%. SkySync-C 相比 dsync, 计算时间减少 24.5%-33.6%, HW 下为 21.7%-29.5%, 查找减少 65.7%. 加速与未加速结果相差最高 10.8%, 主要来自包括 SkySync 在内各方案的校验和提速, 但整体同步加速仍有限. 即使硬件加速, SkySync 仍优于 rsync 和 dsync.

## 4.3 真实数据集

Multi-threaded Sync Time. We conduct our tests for five real-world datasets with different numbers of threads. Figure 14 shows the results. For a fair comparison, we implement the same multi-threading mechanism for rsync and dsync as used in SkySync. In this setup, upon receiving a sync request, a dedicated thread is assigned to process either an entire file or a specific region of a large file. The number of threads on both the client and server sides is consistent across all sync methods. The enwiki and kernel datasets have longer sync times, primarily due to their larger size than the other datasets. Furthermore, despite the ubuntu dataset being smaller than the nutsnap dataset, it had a significantly higher modification ratio. This resulted in longer sync times for ubuntu, as more bytes and checksums required calculation and comparison. SkySync consistently demonstrates advantages over rsync and dsync for all real-world datasets, achieving speed improvements of approximately 1.2×~1.5× (1.15×~1.4× with HW), due to the fast checksum calculation and chunk searching process.

**多线程同步.** 图 14 展示五个数据集在不同线程数下的结果. 为公平比较, rsync 与 dsync 使用和 SkySync 相同的多线程机制: 每个同步请求分配专用线程, 处理一个完整文件或大文件的一段, 各方法两端线程数一致. enwiki 和 kernel 较大, 耗时更长; ubuntu 虽小于 nutsnap, 修改比例却更高, 需要计算比较更多字节和校验和, 因而耗时更长. SkySync 在全部数据集上都有优势, 速度为对比方案的约 1.2-1.5 倍, HW 下为 1.15-1.4 倍.

Total Sync Time. We then evaluate the total breakdown sync time of different sync methods using a single thread. Figures 15 and 16 show the results without and with hardware acceleration, respectively. The client and server sync times of SkySync are reduced by 19.2%~43.7% (16.2%~36.4% with HW) compared to rsync and dsync, which consistently demonstrates the effectiveness of SkySync in file sync.

**总同步时间.** 图 15, 16 分别给出单线程下未加速与硬件加速的耗时分解. SkySync 两端同步时间比 rsync 和 dsync 少 19.2%-43.7%, HW 下少 16.2%-36.4%, 验证了优化效果.

Network Traffic. Figure 17 shows the network sync traffic of different sync methods. SkySync exhibits a consistent level of network traffic comparable to both rsync and dsync. This is because SkySync adopts 32-bit CRC32C and 256-bit SHA256 checksums and uses the same data structures as rsync and dsync to transmit checksum list, matching tokens, and delta data. The traffic volume of SkySync is slightly more than rsync and dsync due to the inclusion of additional bits for strong checksums. Overall, the network transfer time of SkySync is almost the same as that of rsync and dsync. Furthermore, despite the ubuntu dataset being smaller in size compared to the nutsnap and kernel dataset, it generates more network traffic (delta data) due to its higher modification ratio.

**网络流量.** 图 17 中 SkySync 流量与 rsync, dsync 接近. 它采用 32 位 CRC32C 与 256 位 SHA-256, 传输列表, 标记和增量的数据结构保持一致; 强校验和位数更多, 流量略高, 但网络传输时间基本相同. ubuntu 虽小于 nutsnap 和 kernel, 修改比例更高, 因而产生更多增量流量.

Overhead of Metadata Extraction. We measure the time required to extract metadata from the five real-world datasets across EXT4, F2FS, and BTRFS using user-space tools, and from MeGA using custom functions developed in SkySync. For EXT4 and F2FS, we enable fs-verity and extract SHA256 checksums for each 8KB block. For BTRFS, we utilize its built-in SHA-256 and CRC32C checksums, with fs-verity disabled. For MeGA, we extract SHA-256 and CRC32C checksums, respectively. The results, illustrated in Figure 18, demonstrate that metadata extraction from BTRFS and MeGA is significantly faster than that from EXT4 and F2FS. This discrepancy arises because fs-verity, as an extension to EXT4 and F2FS, requires a more complex metadata extraction process compared to BTRFS, which natively stores checksums within its file system metadata. Additionally, SkySync's custom functions efficiently extract metadata from MeGA due to their known metadata storage structures. We observe that the time of extracting the metadata of each dataset (1.8 sec ~ 119.2 sec) is much less than that of directly calculating the checksums of the same dataset (26 sec ~ 246 sec, not shown in this figure) under the same experimental settings. Furthermore, the extraction time of each dataset accounts for a relatively small proportion of its total sync time in SkySync, ranging from 0.11% to 7.14% for BTRFS. This indicates that the metadata extraction process in SkySync is efficient and does not incur high overhead.

**元数据提取开销.** 图 18 测量五个数据集在 EXT4, F2FS, BTRFS 上通过用户态工具, 以及在 MeGA 上通过自定义函数提取元数据的时间. EXT4 和 F2FS 启用 fs-verity, 提取每个 8 KB 块的 SHA-256; BTRFS 关闭 fs-verity, 使用内置 SHA-256 和 CRC32C; MeGA 分别提取这两种校验和. BTRFS 与 MeGA 明显更快, 因为 fs-verity 是 EXT4/F2FS 的扩展, 提取过程比原生保存校验和的 BTRFS 更复杂; MeGA 的已知格式便于自定义函数高效解析. 提取各数据集耗时 1.8-119.2 秒, 明显短于同环境直接计算的 26-246 秒, 后者未绘图. BTRFS 提取仅占 SkySync 总时间的 0.11%-7.14%, 开销较低.

# 5. 结论

Traditional file sync schemes, such as rsync and dsync, introduce considerable computational burdens on both clients and servers due to their costly delta generation. This is inefficient for not only traditional intra-cloud data sharing and processing but also for the emerging inter-cloud Sky computing. This paper presents SkySync, a lightweight file sync scheme based on collaborative delta generation, which accelerates file sync by leveraging the storage-layer metadata. The evaluation results show that SkySync outperforms state-of-the-art file sync schemes (rsync and dsync) while maintaining a consistent level of network traffic. In future work, we aim to expand metadata extraction to more storage systems. We have open-sourced SkySync at [SkySync](https://github.com/skysync-project/skysync).

rsync 和 dsync 等传统方法的增量生成给两端带来大量计算, 不仅影响云内共享和处理, 也不利于跨云 Sky computing. 本文提出 SkySync, 通过复用存储层元数据协同生成增量, 加速文件同步. 实验中, 它优于 rsync 和 dsync, 同时保持相近流量. 后续将扩展到更多存储系统. 代码已开源于 [SkySync](https://github.com/skysync-project/skysync).
