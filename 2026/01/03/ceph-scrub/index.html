本文系统梳理 Ceph Scrub 的基础概念, 历史演进与内部实现, 说明 shallow scrub, deep scrub 和 repair 的职责与区别, 并围绕 PG 展开调度触发, 资源预约, 状态机协作, 分块扫描, 副本与 EC shard 比较, 错误判定及修复流程的分析. 最后汇总检查周期, 优先级, 读取与延迟控制等关键配置, 以及状态查询, 手动触发, 暂停恢复, 不一致对象排查和 repair 操作的常用命令, 帮助理解后台一致性检查的运行机制及其对集群性能的影响.

1. scrub 基础信息

1.1 scrub 定义

scrub 是 Ceph OSD 对 RADOS 数据执行的后台一致性检查. 它按 PG 扫描对象, 收集各个 OSD 上的对象信息, 再比较副本或 EC shard 的状态, 发现对象缺失, 元数据不一致和数据损坏等问题.

PG (Placement Group) 是 scrub 的基本处理单位. 客户端对象先映射到 PG, CRUSH 再为 PG 选择 acting set. 以三副本 replicated pool 为例, acting set 中有一个 primary OSD 和两个 replica OSD:

primary 负责协调 PG 的 scrub, 其他 OSD 提供本地对象或 shard 的检查结果. EC pool 使用 data shard 和 coding shard 保存对象, scrub 仍以 PG 为单位协调检查.

scrub 按计划周期运行, 主动读取平时很少访问的对象, 及时发现潜在的数据问题.

1.2 scrub 作用

scrub 主要用于三件事:

  1. 检查副本或 shard 是否完整, 一致.
  2. 发现磁盘静默损坏, 对象元数据分叉和快照映射错误.
  3. 为健康告警和 repair 提供依据.

检查结果由 primary 汇总. 发现问题后, Ceph 会记录不一致对象和错误类型, 管理员可以进一步查看并决定是否执行 repair.

scrub 的检查范围是 Ceph 能读取和比较的对象, 元数据, 摘要及 shard 关系. 备份和数据库记录等业务语义校验由其他机制负责.

1.3 shallow scrub, deep scrub 和 repair

操作会做什么主要用途主要成本
shallow scrub检查各副本上是否都能找到该对象, 并比较大小, 版本, 属性和其他元数据发现对象缺失和元数据不一致对象列表和元数据 I/O
deep scrub在 shallow scrub 基础上读取对象内容并比较 data/omap digest发现静默数据损坏和内容摘要不一致对象数据读取和 digest 计算
repair根据 scrub 结果选择修复来源并恢复异常 shard处理已经确认的不一致恢复读取, 写入和可能的回填

shallow scrub 和 deep scrub 是两种检查级别, repair 是根据检查结果采取的修复操作.

scrub 发现差异后, 修复数据源还需要根据对象版本, 摘要和 backend 条件判断. 执行 repair 前应保存不一致对象明细和 OSD 日志.

2. scrub 历史演进

早期 scrub 由几组提交逐步形成. 2008 年完成了从 SnapSet 检查到 primary/replica 比较和 pg repair 的演进 (275a06b39dd, f51348dc8bd, ac6e86a21c5); 2012 年加入 chunky scrub 和 deep scrub (f5046798f4e, 9013efd3a3c); 2013 年 deep scrub 增加 omap digest (2fd8db29ccf). 这些能力随后分别进入 v0.5/v0.6 和 Bobtail v0.56, 构成后续 scrub 版本演进的基础. 早期开发阶段尚未使用现在的 GitHub PR 和 tracker issue 流程.

版本比较采用每条发布线的首个稳定版. 现代版本使用 v19.2.0..v20.2.0 这样的相邻 GA 版本, 早期版本则使用 v0.48argonaut, v0.56 等首发 tag. 表格只比较新发布线 GA 时相对上一发布线已经具备的能力, 稳定周期内的 backport 不单独展开. v0.5 和 v0.6 属于正式稳定系列前的开发版本, 因此从 Argonaut 开始列出版本对比; 发布时间取对应 tag 的创建或标注日期.

3. scrub 具体实现

一次正常的 primary scrub 按以下顺序执行:

scrub 按对象顺序把 PG 划分为多个 chunk, 每次事件处理一个 chunk. 每个 chunk 都会建立一致性边界, 收集 map 并完成比较, 之后状态机再进入下一个 chunk.

一次 scrub session 按以下顺序经过各个模块:

  • 注册 target: PG 成为 active primary 后创建并登记 shallow/deep target.
  • 调度触发: OSD 根据 target 的时间, 优先级和当前环境选择任务.
  • 启动检查: 确认 PG 前置条件, scrub 标记和本地及 replica 资源满足条件.
  • 状态机并发: 用状态机保存 primary, replica, chunk 和等待事件的处理进度.
  • 扫描比较: 按 chunk 收集各 shard 的 ScrubMap, 执行 shallow 或 deep 检查.
  • 数据判定与修复: 汇总比较结果, 选择修复数据源, 触发 replicated 或 EC 数据恢复, 并安排复核.

3.2.1 调度时间

ScrubJob 同时保存 shallow target 和 deep target. 每个 target 有两个时间字段:

  • scheduled_at: 任务原计划执行的时间. 周期任务根据 scrub interval 和随机化参数计算, 手动请求或 repair 任务可以直接设置.
  • not_before: 任务下一次允许尝试的最早时间. 周期任务重新计算调度时间时, 两个字段通常一起更新; 任务暂时无法启动时, 系统会推迟 not_before, 而 scheduled_at 保留原计划时间.

scheduled_at 记录原计划时间, not_before 控制任务最早何时可以再次尝试. 当前时间达到 not_before 后, target 才会进入候选集合.

一个 OSD 上可能同时有很多 PG 的 target. ScrubQueue::pop_ready_entry() 调用 not_before_queue_t::advance_time(), 按照 not_before 将条目分到等待队列和可选队列. 可选队列使用 Scrub::operator<() 排序, 该运算符在 src/osd/scrubber/scrub_queue_entry.h 中调用 cmp_ripe_entries(), 依次比较 urgency, scheduled_at 和 scrub level; 前面字段相同时, 再按 not_before 的时间先后排序. 随后, not_before_queue_t::dequeue_by_pred() 按这个顺序调用 is_sched_target_eligible(), 返回第一个通过当前 OSD 限制的 target. 尚未达到 not_before 的 target 留在等待队列中, 该队列按 not_before 排序.

每个 OSD tick 只取出一个 SchedEntry. 一个 SchedEntry 对应一个 PG 的一个 scrub level, 因此一次只尝试一个 PG 的一个 target, 可能是 shallow target, 也可能是 deep target. OsdScrub::initiate_a_scrub() 将这个 target 交给对应的 PG; 其他 PG 的 target, 以及同一 PG 的另一个 target, 都等待后续 tick. 候选 target 的启动检查和失败重试在下一节处理.

3.3 启动检查

OsdScrub::initiate_a_scrub() 把候选 target 交给 PG, 后续启动检查的调用关系如下:

PG::start_scrubbing() 读取集群和 pool 的 noscrub, nodeep-scrub 标记, 并确认当前 backend 是否支持自动修复, 再把这些结果传给 start_scrub_session(). 后者检查 PG 是否仍由当前 OSD 担任 primary, PG 是否 clean, 是否正在 snap trimming, 以及 target 是否允许绕过对应的 scrub 标记.

如果 PG 仍由当前 OSD 担任 primary, 但暂时不满足启动条件, 例如 PG 尚未 clean, 正在 snap trimming 或本地资源不足, start_scrub_session() 会根据失败原因推迟 target 的 not_before, 再将它放回队列. PG 已不再由当前 OSD 担任 primary 时, 任务会退出当前 OSD 的 scrub 管理. 检查通过后, 函数设置本次 session 的 scrub level, repair 和自动修复标志, 把 PG 放入 scrub 操作队列, 状态机随后进入 Session.

3.3.1 资源检查与预约

启动检查通过后, start_scrub_session() 先调用 reserve_local() 占用 primary 所在 OSD 的 scrub 资源. 需要副本预约的后台 target (periodic_regular 和 must_scrub) 再由 primary 按固定顺序向 acting set 中的其他 OSD 逐个发送预约请求. 每个副本 OSD 通过 AsyncReserver 排队处理请求, 并受本地 scrub 并发上限限制. 任一副本返回 REJECT 时, primary 会释放已经获得的预约, 并将 target 延后重试.

osd_scrub_disable_reservation_queuing=false 是当前默认值, 表示允许副本 reservation 排队. 这个选项用于 mixed-version 集群和调试, 源码说明它会在后续版本删除, 不适合作为长期调优手段.

3.4 状态机并发

scrub 整体是由事件驱动的异步流程. 对一个 PG 来说, 多个 chunk 按顺序处理; 对同一个 chunk 来说, primary 和 replica 可以在各自的 OSD 上同时构建 ScrubMap. 每个 PG 都有一个基于 Boost.Statechart 的 ScrubMachine, 用状态记录当前处理到哪一步, 以及正在等待什么条件.

状态机同时覆盖 primary 和 replica 两种角色. 当 OSD 上下线或 CRUSH 重映射导致 PG 的 primary, acting set 发生变化时, 两条路径都会回到 NotActive. Ceph 会结束当前 scrub session, 清理原副本集合的 reservation 和扫描状态, 并忽略随后到达的旧消息. PG 完成 peering 后, 再按照新的副本集合执行 scrub.

clone 通常排在 head 前面是 hobject_t 的排序约定, 而不是说 clone 一定比 head 更早创建: 比较器在对象名, hash 等身份字段相同后, 最后按 snap 升序比较; 普通 clone 使用普通的 snap ID, head 使用特殊的 CEPH_NOSNAP 哨兵值 (-2 转成无符号数后非常大), 因此正常的 snap ID 会排在 head 前面. CEPH_SNAPDIR 是更大的特殊目录标记, 不属于普通对象扫描范围.

NewChunk 选择范围, WaitPushes 和 WaitLastUpdate 建立一致性边界, BuildMap 构建 primary map, WaitReplicas 等待 replica map. 所有 map 到齐后, maps_compare_n_cleanup() 调用 backend 比较并清理当前 chunk; WaitDigestUpdate 等待相关更新完成, 然后进入下一个 chunk 或结束本次 scrub. 各状态的进入条件和事件处理见 3.4 状态机并发.

3.5.1 shallow scrub

shallow scrub 进入 BuildMap 后, 以 deep=false 调用 build_scrub_map_chunk(). 每个 shard 都在本地扫描相同的 [m_start, m_end), 但不读取完整对象数据:

objects_list_range() 先得到当前 shard 在该范围内实际存在的对象. PGBackend::be_scan_list() 对每个对象执行 stat() 和 getattrs(), 将对象大小, 属性以及属性中的 object_info 等内容写入 ScrubMap::object. 读取失败会记录为 stat_error, 扫描过程中对象消失则从当前 map 删除.

primary 收到所有 map 后, 先合并各 map 中的对象名称, 得到当前 chunk 应检查的对象全集. 随后逐对象检查哪些 shard 缺少对象, 并选择一份有效的对象信息作为比较基准:

ScrubBackend::scrub_compare_maps() 负责 map 比较, 随后 scrub_snapshot_metadata() 和 scan_snaps() 检查 SnapSet, clone, overlap 和 SnapMapper. 对象在各 shard 都存在, 并且 size, 属性, object_info, 版本和快照关系均一致时, shallow scrub 才认为该对象没有 shallow error.

shallow scrub 不读取完整对象数据, 也不计算当前数据内容的 digest. 因此 "没有 shallow error" 只表示各副本都能找到对象, 并且对象元数据一致, 不能证明各副本的用户数据字节一致. 对象缺失, size 或版本不同, 属性分叉, 快照关系错误和 PG 统计不匹配都会计入 shallow error. 若启用了自动修复并且错误数量没有超过阈值, 代码会设置 deep_scrub_on_error, 在 shallow scrub 结束后安排 deep scrub 进一步检查并修复.

3.5.2 deep scrub

deep scrub 复用相同的调度, 启动检查, range 选择和跨 shard map 比较, 但在 build_scrub_map_chunk() 中设置 deep=true. PGBackend::be_scan_list() 完成 stat/getattrs 后, 还会调用具体 backend 的 be_deep_scrub():

以 replicated pool 为例, ReplicatedBackend::be_deep_scrub() 按 osd_deep_scrub_stride 分段读取对象, 默认每次 512_K. 读满一个 stride 时返回 -EINPROGRESS, OSD 将任务重新放入操作队列, 从上次 data_pos 继续读取, 避免单个大对象长期占用线程. 数据读完后生成 data digest.

OMAP 也采用分批处理. backend 先读取 OMAP header, 再按 osd_deep_scrub_keys 每批遍历 key/value, 默认每批 1024 个 key. 遍历完成后生成 OMAP digest, 并记录 key 数量和 value 总字节数. 任一大 OMAP 阈值被超过时, 对象会被计入 large OMAP object.

ObjectStore 读取会同时验证底层存储提供的校验信息. BlueStore checksum 不匹配或读取失败时, backend 在当前 ScrubMap::object 中记录 read_error. replicated 和 EC backend 的 deep scan 不完全相同: replicated pool 计算完整对象内容和 OMAP 的 digest; EC pool 读取本地 shard, 并检查 shard size, chunk hash 和 hinfo 等编码信息.

在同一状态机中, scrub_level_t::deep 会让 PgScrubber::set_op_parameters() 设置 PG_STATE_DEEP_SCRUB. map 比较可能产生需要写回的 digest 更新, 状态机在 WaitDigestUpdate 中等待这些更新完成, 然后才推进 m_start 或结束本次 scrub.

deep scrub 的额外检查包括:

  • 各 shard 当前读取内容的 data digest 是否一致.
  • omap 内容的 digest 是否一致.
  • object_info 中保存的 whole-object digest 是否与当前读取结果一致.
  • BlueStore block checksum 是否报告介质层读取错误.
  • EC pool 的 shard size, EC hash, hinfo 和编码布局是否满足恢复条件.

deep scrub 会受到对象读取量, OMAP key 数, chunk 大小和客户端 I/O 抢占影响. 客户端请求抢占当前 range 后, 本 chunk 的结果会被放弃并重新选择; 每次抢占还会缩小后续 chunk. 抢占次数达到 osd_scrub_max_preemptions 后, scrub 不再允许抢占, 后续冲突 I/O 可能等待当前 range 完成. 缺少历史 digest 时, 代码仍能比较各 shard 当前读取结果, 但不能据此证明某一份内容绝对正确.

3.6.2 修复数据源

ScrubBackend 是按对象选择 authoritative shard, 它首先是 "比较基准", 不等于后续 recovery 必然只从这一个 OSD 读取数据. 选择过程不是多数表决, 而是以下两步:

  1. 过滤候选: possible_auth_shard() 只接受能在 ScrubMap 中找到对象, 没有读取错误, EC hash/size 没有错误, object_info 存在且可解码, object_info.soid 与对象匹配, 逻辑大小与该 shard 的落盘大小相符的候选. 对象是 head 时, 潜在 primary 还必须有可解码的 SnapSet; 需要 hinfo 的 EC 配置还要检查 hinfo. EC 中标记为 non-primary 的 shard 即使数据可读, 也不能作为 authoritative, 因为它可能保存旧版本且不能成为 primary.
  2. 在可用候选中选择: 比较 object_info.version, 版本最大的候选胜出; 版本相同时, 记录了更多 data/omap digest 的候选胜出. 候选按 primary, 其他 shard 的顺序遍历, 所以 primary 只在版本和 digest 数量都相同的平局中优先; 一个有效 replica 如果版本更新, 可以取代 primary 成为比较基准.

这里的 data/omap digest 不是 "多数投票": 候选选择不会因为 digest 值与其他 shard 不同就直接淘汰它. 选出基准后, 代码再把所有 shard 与它比较, 检查对象信息, 属性, SnapSet, data digest 和 OMAP digest, 并把没有错误的 shard 收集为 ok_peers. 因此需要区分:

primary 负责协调并且是第一个候选, 但它不会无条件成为基准. replicated pool 中, 如果 primary 合格且没有更高版本的候选, 通常会选择 primary; EC pool 还要排除不能作为 authoritative 的 non-primary shard.repair 时, 代码把 bad_peers 标记为 missing, 并把基准对象的版本交给 PG recovery; 实际数据可能从任一 ok_peers 恢复, EC 则可能根据编码从多个有效 shard 重建, 并不等于固定从 primary 读取.

如果没有任何候选通过上述检查, ScrubBackend 无法建立比较基准, 也就不能安全地生成修复计划; 该对象会记录为无法选择合适的 object info, PG 保留 inconsistent 状态, 等待人工处理.

3.6.3 修复执行

repair 从比较结果进入 Ceph recovery 流程:

replicated pool 中, repair 通常把错误副本标记为 missing, 后续 recovery 从选定的可信副本重建. repair 负责识别问题并安排恢复, 实际数据恢复仍由 Ceph recovery 流程完成.

EC pool 还要处理 shard index, 编码布局, EC hash, hinfo 和可恢复集合. 某个 data shard 错误时, 恢复内容可能需要由其他多个 data/coding shard 解码得到, 因此修复条件比 replicated pool 更复杂.

3.6.4 自动修复与复核

后台自动修复需要 osd_scrub_auto_repair=true, 并要求 PG backend 支持相应修复. 当前默认关闭.

普通 shallow scrub 发现可修复错误时, 可以设置 deep_scrub_on_error, 结束 shallow scrub 后再启动 deep repair. 对普通后台任务, 如果损坏对象数超过 osd_scrub_auto_repair_num_errors, 默认 5, 代码会取消自动 repair, 保留错误供管理员处理.

管理员手动发起的 scrub 和 must-repair 不受这个对象数阈值限制; after_repair 禁止再次自动修复, 以免复核过程重复进入 repair.

4. 配置和命令

4.1 周期与 pool 覆盖

配置默认值含义
osd_scrub_min_interval1_dayshallow scrub 的期望周期
osd_scrub_max_interval7_dayshallow overdue/健康告警使用的最大周期
osd_deep_scrub_interval7_daydeep scrub 的期望周期
osd_scrub_interval_randomize_ratio0.5shallow target 的均匀随机延迟比例
osd_deep_scrub_interval_cv0.2deep target 正态分布的变异系数
osd_deep_scrub_randomize_ratio0.15已废弃, 对当前调度没有作用

pool 可以用 scrub_min_interval, scrub_max_interval 和 deep_scrub_interval 覆盖对应值, 值为 0 时使用 OSD 级配置值. 还可以设置 scrub_priority, noscrub 和 nodeep-scrub.

这几个 interval 同时被 mgr/Monitor 健康检查使用, 源码要求设置在 global, 或者同时设置到 mgr 和 osd. 只改某个 OSD 可能造成调度和健康告警采用不同数值.

4.2 chunk, 读取与延迟

配置默认值含义
osd_scrub_chunk_min / osd_scrub_chunk_max5 / 15deep scrub 单个 chunk 的对象数范围
osd_shallow_scrub_chunk_min / osd_shallow_scrub_chunk_max50 / 100shallow scrub 单个 chunk 的对象数范围

增大 chunk 可以提高扫描吞吐量, 也会扩大一次锁定和读取的范围. 减小 chunk 或增加 sleep 通常能降低尾延迟, 但会拉长整个集群完成一轮 scrub 的时间. mClock 下应先检查 osd_op_queue 和 profile, 因为两个 sleep 配置会被忽略.

配置默认值含义
osd_scrub_retry_delay30 秒通用 scrub 失败或本地资源不足后的重试间隔
osd_scrub_retry_after_noscrub60 秒遇到 noscrub/nodeep-scrub 后的重试间隔
osd_scrub_retry_pg_state60 秒PG 非 active+clean 时的重试间隔
osd_scrub_retry_trimming10 秒PG 正在 snap trimming 时的重试间隔

mon_warn_pg_not_scrubbed_ratio0.5shallow scrub 超过最大间隔后触发告警的比例
mon_warn_pg_not_deep_scrubbed_ratio0.75deep scrub 超过最大间隔后触发告警的比例

Monitor 对 shallow scrub 的告警 cutoff 大致是 osd_scrub_max_interval * (1 + ratio); deep scrub 使用 pool 或 OSD 的 deep interval 计算. 调大 interval 或 ratio 可以让告警消失, 但不会解决 reservation 被拒, PG 长期不 clean 或队列拥塞.

4.5 状态查看

dump_scrubs 中最有用的字段是 pgid, sched_time, orig_sched_time, level, urgency, eligible 和 last_issue:

  • eligible=false 只表示尚未到 not_before. eligible=true 也不保证立即启动, 时间窗口, load, recovery, 并发限制和 PG 条件会在取任务与启动时另行检查.
  • urgency 说明它是 periodic, repair, operator request 还是其他来源.
  • last_issue 记录最近一次因 flags, PG state, snap trimming, replica 或 local resource 延迟的原因.

4.6 发起 scrub

优先使用公开的 mgr 命令:

单个 PG 也可以通过 ceph tell <pgid> scrub 和 ceph tell <pgid> deep-scrub 直接路由到 PG. 管理员手动发起的任务不会按后台 periodic scrub 的规则执行, 不能用来证明周期调度没有受到时间窗口或资源竞争影响.

源码还注册了 schedule-scrub 和 schedule-deep-scrub, 但 PrimaryLogPG.cc 和 OSD.cc 明确把它们标为 test/debug 命令. 它们通过修改时间戳模拟周期调度, 不应写进生产运维流程.

4.7 暂停和恢复后台 scrub

这些标记主要控制后台任务. 管理员手动发起的 scrub 和高 urgency repair 可能绕过标记. 长时间设置标记会触发 PG_NOT_SCRUBBED 或 PG_NOT_DEEP_SCRUBBED, 所以维护结束后要确认标记已经清除.

4.8 查看 inconsistent 细节

常见错误类型包括 missing, data/omap digest mismatch, size mismatch, object-info mismatch, snapset mismatch 和 EC hinfo/hash 错误. 先确定错误位于哪个 shard, 哪些字段不同, 再判断是否存在可信的修复数据源.

4.9 执行 repair

建议按以下顺序操作:

  1. 保存 ceph pg <pgid> query, inconsistent object/snapset 输出和相关 OSD 日志.
  2. 确认 PG 的 acting set, primary, 错误 shard 和可用 digest.
  3. 评估是否存在多个副本都可能损坏, 没有可信摘要或需要从业务侧恢复的情况.
  4. 执行 ceph pg repair <pgid>.
  5. 等待 recovery/backfill 完成, 再运行 deep scrub 验证.
  6. 如果 PG 进入 failed_repair 或错误仍存在, 停止重复 repair, 转入人工数据恢复分析.

ceph-bluestore-tool repair 是离线 BlueStore 元数据工具, 不能替代 PG scrub repair. 它要求停止 OSD, 处理的是 ObjectStore 层问题, 使用条件和风险完全不同.
