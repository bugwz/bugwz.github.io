Ceph 读路径: 从客户端请求到 OSD 返回

发表于2026-01-10|更新于2026-09-19
|总字数:12.2k|查看 Markdown

一次 Ceph 读请求从发出到返回, 会经过客户端对象映射, 网络传输, OSD 调度, PG 检查和底层存储读取等环节. 文章以传统 OSD, Messenger v2 和 BlueStore 为例, 分析副本池与 EC 池的读取差异, BlueStore 设备 I/O, 完整性校验及结果返回, 同时介绍 RBD, CephFS, RGW 和 librados 如何把上层读取转换为 RADOS 对象读, 并总结缓存层次, 常见故障分支与延迟定位方法.

图中有几处需要注意:

  • 客户端使用本地保存的 OSDMap 和 CRUSH map 计算目标 OSD, 正常读请求不会先发给 MON.
  • 副本池 (replicated pool) 默认只读一个 acting OSD 上的本地副本. 纠删码池 (EC pool) 则由主 OSD (primary) 选择足够的分片 (shard), 从多个 OSD 读取并还原数据.
  • 一次读可能命中客户端或 OSD 的缓存; 如果没有命中, OSD 还可能先查 RocksDB 元数据, 再读 BlueStore 数据盘. EC 读还可能向多个 shard OSD 发起读取, 所以客户端发出一条请求, 并不代表集群内部只做了一次 I/O.

2. 客户端: 把应用读取转换成 RADOS 对象读

块存储, 文件存储和对象存储有不同的入口, 但都需要确定要读哪些 RADOS 对象. 如果数据已经在客户端缓存中, 请求就不会继续往下走. 因此, 应用发起一次读取, 并不代表客户端一定会发送 MOSDOp.

2.1 块存储: RBD

RBD 会把 Ceph 中的镜像 (image) 映射成块设备, 应用或虚拟机可以像访问本地磁盘一样读写. 用户态程序可以直接使用 librbd, 也可以通过 krbd 把镜像映射成内核块设备. 两条调用路径不同, 最后都要把镜像中的地址换算成 RADOS 对象地址.

应用看到的是 image 的连续块地址, RADOS 保存的却是一组独立对象. librbd 会根据 image 的 layout, 把这段块地址换算成对象名, 对象内偏移和读取长度. 先看最简单的情况: 只按 object size 切分时, image 数据会依次落在不同对象中.

例如, object size 为 4 MiB, 应用从 image 偏移 3 MiB 的位置读取 2 MiB. 这次请求会被拆成两段: 第一个对象读取对象内偏移 3 MiB 到 4 MiB 的 1 MiB, 第二个对象读取对象内偏移 0 到 1 MiB 的 1 MiB.librbd 会把这两段分别生成 object extent, RADOS 端只处理对象内的偏移和长度.

启用 striping 后, 映射方式会更细一些. 连续的 image 数据会先按 stripe_unit 切成小块, 再轮流放入 stripe_count 个对象中. 例如, 设置 stripe_unit = 4 KiB, stripe_count = 2 时, image 的前几段数据可以理解为: [0, 4 KiB) 放到对象 0, [4 KiB, 8 KiB) 放到对象 1, [8 KiB, 12 KiB) 又回到对象 0, [12 KiB, 16 KiB) 放到对象 1. 此时, 一次连续的块读取即使没有跨过 object size, 也可能同时访问多个对象. librbd 会为每一段计算对象名, 对象内偏移和长度, 再把它们拆成多个 object extent.

那对象 0 的名字是怎么确定的? 创建 image 时, librbd 会生成一个唯一的 image id, 并据此生成数据对象前缀. 新格式通常是 rbd_data.<image-id>; 如果 image 使用独立的数据池, 前缀中还会包含数据池 id. 随后, librbd 给每个对象分配一个从 0 开始的 object_no, 再把这个序号格式化到前缀后面. 例如, 前缀为 rbd_data.abc123 时, 对象 0 和对象 1 可以表示为 rbd_data.abc123.0000000000000000 和 rbd_data.abc123.0000000000000001.

因此, 读取 image 时不需要扫描数据池来寻找 "第一个对象". 客户端先从 rbd_header.<image-id> 等元数据中取得 image layout 和对象前缀, 再由 Striper::file_to_extents() 根据 image 偏移量算出 object_no, 对象内偏移和长度, 最后由 data_object_name() 生成确定的 RADOS 对象名.

下面先以用户态 librbd 的异步读为主线, 入口函数是 librbd::api::Io::aio_read(). 后面的步骤描述这条用户态路径; 时序图另外画出内核态 krbd, 用于对比两条路径如何汇合到 RADOS/OSD.

  1. 请求先经过 librbd 的请求分发层 (image dispatcher), 由这一层检查镜像缓存, PWL 缓存, 预读, QoS 和加密等处理模块.
  2. ImageReadRequest::send_request() 根据 image 的对象大小, 条带单元大小和条带数量, 计算对象名, 对象内偏移和长度, 把跨对象的范围拆成多个 object extent.
  3. ObjectReadRequest 为每个 object extent 创建一个 RADOS 对象读操作, 再通过 neorados::ReadOp 提交给 Objecter.
  4. 各个对象读完成后, 按照 buffer_extents 指定的位置拼回镜像缓冲区. 如果当前镜像是克隆镜像, 且当前层没有对应对象, 就继续读取父镜像. 启用 copy-on-read 后, 读到的父镜像数据还可能被复制到当前镜像中 (copyup).

图中的两种缓存不是同一层: 用户态 librbd 可能命中 image cache, PWL 或 readahead; krbd 本身没有这套用户态缓存, 但通过文件系统或普通 buffered I/O 访问时, 可能先命中 Linux 页缓存. 两种缓存都未命中时, 请求才会继续进入 RADOS 读路径.

一次 I/O 会访问多少个对象, 取决于它是否跨越条带. 大范围或稀疏区域可能使用 sparse_read. RBD 的副本读取策略也可以把纯读发给 acting set 中的某个副本 OSD. 无论选中哪个 OSD, 请求到达后都会经过 PG 和 ObjectStore.

2.2 文件存储: CephFS

对应用来说, CephFS 是一个可以按连续字节流访问的文件系统, 但文件内容在底层会拆成多个 RADOS 对象. MDS 负责维护文件系统元数据, 并协调多个客户端之间的缓存访问. 客户端获得相应的文件布局 (layout) 和读 capability 后, 会直接从数据池的 OSD 读取文件内容, MDS 不参与文件数据转发.

文件的 layout 包含数据池, object_size, stripe_unit 和 stripe_count 等信息. 客户端根据这些参数, 把文件偏移换算成对象序号, 对象名, 对象内偏移和读取长度. 对象名通常由 inode 号和对象序号组成, 因此同一个文件的第一个数据对象可以理解为 "这个 inode 的 object 0", 而不是一个固定的全局对象名.

先看不使用复杂 striping 的情况. 假设 object_size 为 4 MiB, 应用从文件偏移 3 MiB 的位置读取 2 MiB, 请求会拆成两段: 第一个对象读取对象内偏移 3 MiB 到 4 MiB 的 1 MiB, 第二个对象读取对象内偏移 0 到 1 MiB 的 1 MiB. 启用 striping 后, 客户端还要按照 stripe_unit 和 stripe_count 把连续文件数据分布到多个对象, 再为每个对象生成对应的读取范围.

下面以用户态 ceph-fuse/libcephfs 的 Client::_read() 为例. 内核态 CephFS 会先经过 VFS 和页缓存, 但缓存检查, 根据文件 layout 拆分对象范围, 以及后面的 RADOS/OSD 处理, 逻辑上是相同的:

  1. 客户端检查文件句柄, 权限, 读 capability, 以及文件是否包含可以直接返回的内联数据.
  2. 如果命中页缓存或 ObjectCacher, 直接把缓存中的数据返回给应用.
  3. 缓存未命中或使用 O_DIRECT 时, Striper::file_to_extents() 根据 inode 的 layout, 把文件范围拆成一个或多个 RADOS object extent. 每个 extent 都包含对象名, 对象内偏移和长度.
  4. 客户端通过 Objecter 读取这些对象, 收到结果后按文件偏移重新拼成应用需要的连续数据.

2.3 对象存储: RGW

RGW 是运行在用户态的网关, 对外提供 S3/Swift HTTP 接口. 应用看到的是 bucket 中的一个对象和它的逻辑字节范围, RGW 负责把这个请求转换成一个或多个 RADOS 对象读. RGW 没有类似 krbd 或内核 CephFS 的内核态数据路径, 本节只介绍用户态 RGW.

RGW 保存对象时, 会把对象的元数据, 布局信息和数据分开管理:

  • 小对象通常直接放在一个 head object 中.
  • 大对象通常由一个 head object 和多个 tail stripe 组成, manifest 记录每个部分对应的 RADOS 对象, 逻辑偏移和长度.
  • 收到 GET 或 Range 请求后, RGW 根据 manifest 找到覆盖请求范围的对象部分, 再把逻辑范围换算成每个 RADOS 对象内的读取范围.

例如, 假设一个逻辑对象按 4 MiB 的数据段保存, 应用请求 [3 MiB, 6 MiB) 这段数据. RGW 会读取第一个对象中 [3 MiB, 4 MiB) 的 1 MiB, 再读取下一个对象中 [0, 2 MiB) 的 2 MiB, 最后按逻辑偏移把两段数据拼回 HTTP 响应. 实际使用哪些 head/tail object, 以该对象的 manifest 为准.

以用户态 RGW 的 GET 处理为例, 主要过程如下:

  1. RGW 接收 HTTP 请求, 完成认证, 权限检查, Range 解析, 以及压缩和加密过滤器的准备.
  2. RGWRados::Object::Read::iterate() 读取对象的 manifest, 并由 iterate_obj() 把 HTTP 的逻辑范围拆成一个或多个 RADOS object extent.
  3. get_obj_iterate_cb() 为这些 extent 创建 ObjectReadOperation, 通过 RGW 的异步 I/O 封装提交给 librados/Objecter.
  4. 各个 RADOS 对象读完成后, RGW 按逻辑偏移排序, 把结果拼接起来, 再流式返回给 HTTP 客户端.

2.4 直接使用 librados

业务也可以绕过 RBD, CephFS 和 RGW, 直接使用 librados::IoCtx 读写 RADOS 对象. 此时, 应用自己提供存储池, 命名空间, 对象名以及对象内的 offset 和 length; librados 不会再替应用做 image layout 或文件 layout 的转换.

例如, 应用要读取对象 obj-001 中从 1 MiB 开始的 2 MiB 数据, 客户端会直接构造 "对象名为 obj-001, 对象内偏移为 1 MiB, 长度为 2 MiB" 的 RADOS read. 对象名和对象内范围已经由应用确定, Objecter 接下来只负责把这个对象读请求发到正确的 OSD.

用户态 librados 的读请求可以同步提交, 也可以异步提交:

同步 read() 和异步 aio_read() 走同一条数据路径. 同步接口提交请求后等待完成; 异步接口提交后立即返回, 结果通过 completion 回调通知应用. 一个 ObjectOperation 可以同时包含 read, stat, getxattr 或 cls call 等子操作, 因此一条 MOSDOp 消息可能携带多个子操作.

下面按一次对象读取说明 librados 和 Objecter 的处理过程:

  1. prepare_read_op() 根据应用给出的对象名, offset 和 length 创建读操作, 并准备输出 bufferlist, flags 和 completion.
  2. _op_submit_with_budget() 会限制客户端同时发送的请求数量, 以及已经发出但还没有返回的请求总字节数. 达到限制时, 请求会先在客户端排队, 等已有请求完成后再发送.
  3. _calc_target() 根据存储池, 命名空间, 对象名及 locator, 结合本地 OSDMap 和 CRUSH 计算 raw PG, actual PG, acting set 以及目标 OSD.
  4. _prepare_osd_op() 把读操作编码成 MOSDOp, _send_op() 再通过 AsyncMessenger 发送给目标 OSD.
  5. 收到 MOSDOpReply 后, Objecter 按 tid 找回原请求, 把返回数据交给同步调用方或异步 completion.

3. 服务端入口: 网卡收包和 OSD 调度

3.1 网卡, Messenger 和消息解析

下面以 TCP 上的 Messenger v2 为例, 看看客户端发出的 MOSDOp 怎样进入 OSD 进程:

  1. 网卡收到数据包后, 通过 DMA 把数据写入主机内存. 内核网络栈随后处理这些数据, 并把它们放入 OSD 连接对应的 socket 接收缓冲区. 实际耗时还取决于数据是否需要额外拷贝, 校验和由 CPU 还是网卡处理, 以及 Messenger 是否启用了加密.
  2. OSD 进程中的 AsyncMessenger 从连接读取 msgr2 协议帧, 处理连接认证和会话状态, 检查消息完整性, 再把协议内容解码成 MOSDOp.
  3. 消息解码完成后, OSD 将 MOSDOp 交给 OSD::ms_fast_dispatch(). 请求从这里进入 OSD 的快速分派流程, 随后才会排入对应的 PG 队列.

所以, 从网卡收到数据到请求进入 OSD 队列, 中间包含网络接收, 内核与用户态之间的数据传递, Messenger 连接处理和消息对象创建. 排查延迟时, 应把这段接收时间与后面的 OSD 调度排队时间分开统计.

3.2 OSD 接收消息并分派请求

Messenger 收到 MOSDOp 后, 会进入 src/osd/OSD.cc 中的 OSD::ms_fast_dispatch(). 这个函数主要负责:

  • 在 OpTracker 中创建 OpRequest, 记录请求到达时间和跟踪信息;
  • 读取消息的 sent_epoch, min_epoch 和客户端实例信息 (incarnation);
  • 对正常连接调用 enqueue_op(spg, op, epoch);
  • 如果客户端 map 太旧, 目标 PG 还没有创建, 或者会话需要等待 map, 就让请求进入 waiting_on_map 等等待队列;
  • 如果请求发到了错误的 OSD, 则通过 map 和请求误投 (misdirection) 处理, 让客户端更新目标后重试.

3.3 OSD 分片队列, mClock/WPQ 和排队延迟

OSD 会把 PG 分配到多个调度分片 (shard), 由 ShardedOpWQ 管理请求队列. 每个分片有自己的调度器和工作线程; 这里的调度分片与 EC 的数据分片是两个概念. 常见的调度器是 mClock, 也可以使用 WPQ. 入队时, PGOpItem 会记录请求的开销 (cost), 优先级, 所属客户端, map 版本和接收时间.

请求可能因为这些原因长时间排队:

  • 客户端 I/O 与恢复 (recovery), 回填 (backfill), 校验 (scrub) 争用资源;
  • mClock 的资源保留, 权重和上限设置, 或 WPQ 的优先级设置限制了请求的处理速度;
  • 同一个 PG 需要保持操作顺序, 或者还在等待创建, peering, map 更新;
  • 工作线程不足, 设备队列过深, 或者 OSD 的 CPU 负载已经很高.

工作线程取出请求后, OSD::dequeue_op() 根据 spg_t 找到对应的 PG, 再调用 pg->do_request(op, handle). 请求离开调度队列后才进入 PG 处理, 后面还要经过对象检查和锁等待, 才会调用 BlueStore. 调度排队时间是 osd.op_r_latency 和 osd.op_r_process_latency 差值的主要来源.

4. PG 处理: 检查状态, 定位对象并获取读锁

4.1 PG 状态和请求合法性检查

消息进入 PG 后, 从 PrimaryLogPG::do_request() 开始处理. PG 会结合当前 OSDMap 和自身状态, 检查请求是否可以执行:

  • 当前 map 版本是否满足请求要求, 是否需要等待 map 更新;
  • PG 是否已经创建, 完成 peering 并处于 active, 是否要求客户端暂缓请求 (backoff);
  • 客户端会话和 CephX 权限是否允许这次操作, 客户端是否在 blocklist 中, 是否有访问该存储池和命名空间的权限;
  • 消息中的 hobject_t 是否确实属于当前 PG;
  • 对象是否缺失, 不可读或处于降级状态, 是否需要等待恢复或回填;
  • 缓存分层 (cache tier), manifest, 重定向或 scrub 是否要求代理读取或暂缓处理.

普通 CEPH_MSG_OSD_OP 要等 PG 处于 active 状态后才会进入 do_op(). 如果 PG 尚未就绪, 请求可能停在 waiting for peered, waiting for active 或不可读对象的等待队列中. OSD 不会直接把已知不完整的本地数据返回给客户端.

4.2 对象信息, 快照和读锁

PrimaryLogPG::do_op() 解析消息中的操作列表, 判断当前 OSD 是否可以执行读取, 并取得或创建对象上下文 ObjectContext (OBC):

  • OBC 缓存 object_info_t, SnapSet, watch 和属性信息, 对象版本, 以及等待请求的状态;
  • object_info_t 保存对象逻辑大小, 截断信息, 摘要 (digest) 和 manifest 等 PG 元数据;
  • 快照读取通过 SnapSet, 把快照编号映射到当前对象 (head) 或相应的快照副本 (clone);
  • OBC 上的读写锁负责对冲突请求排序, 普通读一般取得 RWREAD 锁.

如果 OBC 缓存未命中, PG 会从 ObjectStore 读取 OI_ATTR, 再解码出 object_info_t. OBC 和 BlueStore Onode 是两层独立缓存: OBC 保存对象版本, 快照和锁状态等 PG 信息, Onode 保存底层存储需要的对象元数据和数据映射.

5. PG 按 pool 类型读取数据

PG 完成请求检查并拿到对象读锁后, 会根据 pool 的数据布局选择后端. replicated pool 通常读取一个 acting OSD 上的本地副本; EC pool 则由 primary 组织多个 shard 的读取, 并在收集到足够数据后解码还原对象内容. 下面先介绍 replicated pool, 再介绍 EC pool.

5.1 副本池的读取流程

副本池的数据在多个 OSD 上保存完整副本. 普通读通常由 acting primary 处理, 只读取它本地的那份副本; 配置了 balance 或 localize 时, 客户端也可以把纯读发给其他副本. 下面先看默认的主 OSD 读取, 再说明从其他副本读取时的差异和完整性检查.

5.1.1 PG 从主 OSD 读取对象

默认策略下, Objecter 会把 MOSDOp 发给 acting primary, 也就是当前负责这个 PG 的主 OSD.PG 先根据 object_info_t 确定实际读取范围:

  • length == 0 表示读到对象当前 EOF;
  • offset 超过对象大小时, 返回空结果;
  • offset + length 超过 EOF 时, 把范围截到对象末尾;
  • 根据 truncate sequence/size 处理对象曾经被截断的情况.

范围确定后, PG 通过 ReplicatedBackend::objects_read_sync() 调用本机 ObjectStore::read(), 最终进入 BlueStore::read(). objects_read_sync() 会把 PG 使用的 hobject_t 转成当前 shard 的 ghobject_t, 然后读取本机对象. 它不会向其他副本发送读请求, 也不会等待三个副本都返回. 因此, 三副本池的一次普通读通常只读取一个 OSD 的本地副本, 最后返回一份 MOSDOpReply.

5.1.3 副本池读取后的完整性检查

无论请求最终发给主 OSD 还是其他副本, 只要 OSD 实际读取了本地对象, 就会经过相同的存储校验. BlueStore 先在 blob 层校验 checksum; 如果读取的是完整对象, PG 还可能根据 object_info_t 中的 data digest 检查对象的逻辑内容. 副本如果在读取前发现自己可能落后并返回 -EAGAIN, 则不会进入这一步.

这两种校验针对的内容不同:

  • blob checksum 验证物理存储块或压缩 blob;
  • object digest 验证完整 RADOS 对象的逻辑内容.

如果本地 read 返回 -EIO, 或者完整对象的 digest 不匹配, PG 可以进入 rep_repair_primary_object() 等修复流程. 但这不表示所有介质错误都能在当前读请求中自动修复.

5.2 EC 池的读取流程

EC 池不保存完整副本, 而是把一个对象编码成多个数据分片和校验分片, 分别放在 PG acting set 中的多个 OSD 上. 客户端请求首先到达这个 PG 的 acting primary. 它和其他 OSD 一样只保存一个 shard, 同时负责根据读取范围和各分片的状态向相关 OSD 请求数据; 收到足够的分片后, 在本地完成解码, 再把完整数据返回客户端. 下面分别介绍异步读取, 分片选择, 向分片 OSD 请求数据, 以及解码和补读.

5.2.1 启动异步读取

副本池通常可以在一个 OSD 上同步读完对象; EC 读则需要同时向多个 shard OSD 请求数据, 不能在 do_read() 中一次完成. do_read() 会先记录这次待读取的范围, execute_ctx() 再调用 OpContext::start_async_reads() 发起各个分片的读取. 这时还没有足够的数据还原对象, 客户端需要先等待分片读取完成.

当 primary 收集到足够的分片后, 就可以在本地完成解码. finish_read() 会接着处理这批已经返回的数据, 最后由 complete_read_ctx() 组装结果并返回客户端. 每个分片请求都会记录自己的完成状态, 避免后续继续执行时重复发送.

5.2.2 EC 读取范围与分片选择

EC primary 收到读请求后, 不能直接把这段对象范围交给某一个 OSD. 它要先按照 EC 布局, 把请求拆到各个 shard 上, 再判断哪些 shard 能够参与这次读取. ECBackend::objects_read_async() 和 ECCommon::ReadPipeline 主要完成这项工作:

  1. get_want_to_read_shards() 根据对象范围和 EC 布局, 算出每个数据 shard 需要读取的范围.
  2. 检查 acting set 中各 shard 的状态, 排除缺失, 无法读取或状态不完整的 shard.
  3. 通过 EC plugin 的 minimum_to_decode() 判断至少需要哪些 shard 才能还原请求的数据.
  4. 根据 stripe 对齐要求和 osd_ec_partial_reads, 判断是否需要按 stripe 边界多读一部分数据.
  5. 确定每个目标 shard 的读取区间, 并把同一 shard 上相邻的区间合并成一个请求.

在健康的 k+m EC pool 中, 通常需要至少 k 个 shard 才能还原数据. 但实际并不是固定读取 "前 k 个完整 shard": 请求范围, 插件能力, subchunk, 缺失 shard 以及 partial-read 设置, 都会影响要读哪些 shard 和每个 shard 的读取量.

6. ObjectStore 的对象读取流程

PG 只调用 ObjectStore::read(), 不关心后端具体怎样保存数据. 不同后端的实现不同, 生产环境的 OSD 通常使用 BlueStore.

常见后端的读取方式不同, 但它们都实现了 ObjectStore::read() 接口. EC 的分片也可以使用这些后端保存:

后端读行为概览

KStore将对象按 stripe 存在 KeyValueDB 中, 由 _do_read_stripe() 读取并拼接 bufferlist

下面以生产环境最常见的 BlueStore 为例, 展开对象从元数据到物理设备的读取过程.

6.1 读取对象元数据

BlueStore::read() 接收 collection, 对象标识和读取范围. collection 是 BlueStore 用来组织一组对象的内部容器, 通常对应某个 PG 在当前 OSD 上保存的对象集合. 后续处理主要分为四步:

  1. 确认 collection 存在, 并取得它的共享锁.
  2. 通过 Collection::get_onode(oid, false) 查找对象的 Onode.
  3. 把 (offset=0, length=0) 解释为读取整个对象.
  4. 调用 _do_read(), 按照 extent map 读取请求范围.

Onode 可以看作对象在 BlueStore 中的元数据记录, 里面包含对象是否存在, 对象大小, 属性, 以及 extent map 分片和 blob 的映射关系. 命中 OnodeSpace 时不需要查数据库; 没有命中时, BlueStore 会从 RocksDB 的 PREFIX_OBJ 读取并解码 Onode, 这些数据通常由 BlueFS 管理. 因此, 一次冷读可能先访问 RocksDB/BlueFS, 再访问数据盘.

6.2 逻辑范围到物理位置

大对象的 extent map 可能按分片存在 RocksDB 中. _do_read() 调用 o->extent_map.fault_range(db, offset, length), 只加载覆盖目标范围且当前尚未在内存中的映射分片.

6.3 数据缓存检查

_read_cache() 会在 Onode 的 BufferSpace 中查找请求范围:

  • 如果这段数据刚被写入, 最新内容可能还在 writing/dirty buffer 中, 读取时必须优先使用这部分数据;
  • 如果请求范围已经在 clean buffer 中, BlueStore 可以直接从缓存返回;
  • 如果缓存只覆盖了部分范围, 只有未命中的部分需要访问设备;
  • deep scrub 设置 BYPASS_CLEAN_CACHE 后会跳过 clean buffer, 但仍会读取 writing buffer, 因为其中可能包含尚未落盘的最新数据.

bluestore_default_buffered_read=true 中的 buffered, 指是否把设备读结果放进 BlueStore 自己的 clean cache, 不是 Linux page cache.BlueStore 的主数据 fd 通常以 O_DIRECT 打开, 所以即使启用了 buffered read, 底层仍可能使用 direct AIO, 只是结果会留在用户态 cache 中.

6.4 设备 I/O

缓存没有命中时, BlueStore 会把需要访问的数据整理成设备读请求. _prepare_read_ioc() 会根据 blob chunk, checksum 和设备的对齐要求调整读取范围; 同一个 blob 中相邻或重叠的读取会尽量合并, 减少设备请求次数.

对于调用方真正需要的逻辑范围, BlueStore 会同时记录对应的截取位置和补齐信息. extent map 中没有分配物理空间的 hole 不需要访问设备, 返回结果时直接补零. 压缩 blob 则必须先读取完整的压缩数据, 完成校验和解压后, 再截取请求的逻辑范围.

Blob::map() 把 blob offset 映射成物理 extent, 并对每段调用 bdev->aio_read(). 因此, 一个 RADOS object read 可能变成多条 block I/O. 碎片, checksum 对齐, 压缩以及跨 blob 读取, 都会增加实际的设备 I/O.

6.5 校验与结果组装

在传统内核块设备路径中, KernelDevice::aio_read() 准备对齐 buffer 和 preadv AIO, 把请求放进 BlueStore 的 IOContext. bdev->aio_submit() 提交请求后, _do_read() 等待结果. 底层可能使用 io_uring 或 libaio; 如果不满足 direct async 的条件, 也可能退回同步读取. SPDK NVMe 和 PMEM 则有各自的 BlockDevice 实现.

设备 I/O 完成后, _generate_read_result_bl() 会依次完成:

  1. 对 blob read 执行 _verify_csum();
  2. 必要时解压 compressed blob;
  3. 截取调用方请求的逻辑 region;
  4. 根据 buffered policy 写入 BlueStore clean cache;
  5. 按逻辑 offset 拼接 bufferlist, 遇到 hole 就补零.

checksum 出错时, 可以根据 bluestore_retry_disk_reads 配置进行有限次数的重读. 重试仍然失败, 就返回 -EIO. 这只能应对暂时性的读错误, 不能修复真实的介质损坏.

7. OSD 返回读取结果

7.1 组装并发送 OSD 回复

副本池的本地读取或 EC 解码完成后, PG 进入 complete_read_ctx(), 完成以下工作:

  • 扫描每个 OSD 读操作的 rval 和 data;
  • 设置 data offset, 对象 user version, 整体 result 和 bytes_read;
  • 把输出 bufferlist 编码到 MOSDOpReply;
  • 设置协议兼容的 ACK | ONDISK flags;
  • 通过原来的客户端连接交给 Messenger 发送;
  • 释放对象读锁并销毁 OpContext.

读请求中的 ONDISK 只是协议兼容标志, 不表示这次读像写请求一样等待多个副本完成持久化提交. 对于 EC 请求, primary 收到足够的分片数据并完成解码后, 才能构造最终回复.

Objecter::handle_osd_op_reply() 先用 tid 在 session 的 inflight map 中找到原请求, 丢弃旧 attempt 的迟到回复, 然后处理以下情况:

  • redirect 或 PG remap: 更新 locator/OSDMap 后重发;
  • 副本读取返回 -EAGAIN: 清除 balance/localize flags, 改发主 OSD;
  • 正常回复: 提取 object version 和 reply epoch, 把消息中的 data claim 到调用方 bufferlist, 再把每个 OSD 读操作的 rval/output 分发出去;
  • 处理完成后释放请求预算, 从 inflight 列表中移除请求, 并在 completion lock 下调用上层回调.

RBD 要等所有对象请求完成后, 按 image extent 拼回结果; CephFS 把数据交给用户 buffer, 或者放入客户端缓存; RGW 则按 manifest 的逻辑偏移量继续向 HTTP 客户端发送数据.

8.3 延迟分解与计数器

应用看到的读延迟不一定都发生在 OSD. 请求在发出之前, 客户端可能正在检查上层缓存, 等待 Objecter 的请求额度, 拆分 RBD/CephFS/RGW 的逻辑范围, 或者等待更新 OSDMap. 如果 map 过旧, 或者 PG 发生重新映射, 连接被重置, 请求被重定向, Objecter 还会重新计算目标并重发. tid, 重试次数 (attempt) 和 map 版本 (epoch) 用于识别并丢弃旧请求的迟到回复.

各段时间的含义如下:

  • T_upper_split_and_cache: RBD, CephFS 或 RGW 拆分逻辑请求, 检查上层缓存所花的时间. 这里通常没有对应的 OSD 计数器, 需要结合上层客户端的日志或请求统计观察.
  • T_client_budget_and_map: Objecter 等待请求额度, 更新 OSDMap, 并计算 PG 和目标 OSD 所花的时间. objecter.op_latency 从一次 attempt 发出开始计时, 因此不包含上层拆分和缓存等待.
  • T_request_network: 请求从客户端发送到 OSD 主机的网络传输时间, 通常需要结合客户端, Messenger 和主机网络指标判断.
  • T_osd_receive_and_prequeue: OSD 收包, Messenger 解码, 以及请求进入调度队列之前的处理时间, 可以参考 osd.op_before_queue_op_lat.
  • T_osd_scheduler_queue: 请求在 mClock/WPQ 等 OSD 调度队列中等待的时间. osd.op_r_latency 通常包含这段等待, 而 osd.op_r_process_latency 更接近请求出队后的处理时间, 两者的差值可以用来估算排队时间.
  • T_pg_checks_and_locks: PG 检查状态, 对象信息, 权限和对象锁的时间. osd.op_r_prepare_latency 对副本池同步读有参考价值, 但 EC 首轮执行可能只是启动异步分片读取, 不能用它代表完整的 EC 延迟.
  • T_object_metadata: 读取 Onode, extent map 等对象元数据的时间. 可以结合 bluestore.read_onode_meta_lat, bluestore.onode_hits/misses 和 bluestore.onode_shard_hits/misses 判断元数据缓存是否命中.
  • T_data_cache_or_device_io: 命中 BlueStore 缓存, 或从数据设备读取对象内容的时间. bluestore.read_lat 反映 BlueStore read 的总时间, bluestore.read_wait_aio_lat 更接近等待数据设备的时间.
  • T_checksum_decompress: 校验 checksum, 解压数据并整理读取结果的时间, bluestore.csum_lat 可以反映 checksum 的 CPU 和数据处理开销. bluestore.read_eio 和 reads_with_retries 可用于查找设备错误或 checksum 重读.
  • T_ec_subreads_and_decode: EC primary 读取分片, 等待回复和解码的时间, 仅 EC 读取包含这一段; osd.op_r_prepare_latency 不能单独代表这部分完整耗时.
  • T_reply_network: 读取结果从 OSD 返回客户端的网络传输时间. objecter.op_latency 会把这段时间和本次 attempt 的客户端, OSD 处理时间一起统计.
  • T_upper_reassembly: 客户端把对象结果重新拼成 image, 文件或 HTTP 响应的时间, 通常需要结合 RBD, CephFS 或 RGW 的上层请求统计观察.
