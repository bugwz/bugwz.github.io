1. 摘要

I/O efficiency is critical for erasure-coded repair performance in modern distributed storage. We propose LESS, a family of repair-friendly erasure code constructions that reduces both the amount of data accessed and the number of I/O seeks in single-block repairs, while ensuring balanced reductions across blocks. LESS layers multiple extended sub-stripes formed by widely deployed Reed-Solomon coding, and is configurable to balance the trade-off between the amount of data accessed and I/O seeks. Evaluation shows that LESS on HDFS reduces both single-block repair and full-node recovery times compared to state-of-the-art I/O-optimal erasure codes.

现代分布式存储中, I/O 效率是纠删码修复性能的关键. 本文提出 LESS, 一族便于修复的纠删码构造, 在单块修复时同时减少读取的数据量和非连续 I/O 次数, 并使不同数据块获得较均衡的收益. LESS 将多个由广泛使用的 Reed-Solomon 编码构成的扩展子条带叠加, 通过可配置参数权衡数据读取量与 I/O 次数. 在 HDFS 上的评估表明, 相较先进的 I/O 最优纠删码, LESS 缩短了单块修复和整节点恢复时间.

2. 引言

Erasure coding is widely adopted in modern distributed storage systems (e.g., [3, 5, 10, 21]) to ensure fault tolerance with significantly lower storage overhead than traditional replication [37]. However, erasure coding incurs high repair costs. Reconstructing a single failed block needs to access and transfer much more data than the block size, leading to amplified bandwidth and I/O costs. Recent surveys [1, 33] highlight extensive studies, from both coding theory and systems communities, that aim to improve repair efficiency in erasure-coded storage. These studies focus on improving access performance (e.g., optimizing degraded reads [6, 13]) and storage reliability (e.g., reducing mean-time-to-data-loss [9, 10]). In particular, extensive research has proposed repair-friendly erasure code constructions to mitigate bandwidth and I/O costs (see §2.2 for related work).

现代分布式存储广泛采用纠删码 [3, 5, 10, 21], 以明显低于传统多副本的空间开销提供容错 [37]. 但修复代价很高: 重建单个失效块也要读取和传输远多于该块大小的数据, 放大带宽与 I/O 开销. 近期综述 [1, 33] 总结了编码理论与系统领域的大量研究, 涉及优化降级读 [6, 13] 等访问性能, 以及降低数据丢失风险等可靠性指标 [9, 10]. 其中一条主要路线是设计便于修复的编码, 减少带宽和 I/O 成本, 相关工作见原文第 2.2 节.

In modern distributed storage systems, I/O efficiency has become an increasingly critical design factor compared to bandwidth efficiency due to rapid advancements in network technologies (e.g., InfiniBand, RDMA, and CXL) that support high-speed interconnects. However, I/O performance cannot match such network improvements, especially under random-access workloads. This motivates us to construct repair-friendly erasure codes that make I/O efficiency a "first-class citizen" for high repair performance.

InfiniBand, RDMA, CXL 等高速互连发展迅速, 相比之下存储 I/O 性能提升较慢, 随机访问尤其如此. 因而相较网络带宽效率, I/O 效率已成为越来越重要的设计因素. 本文以 I/O 效率为核心, 构造修复性能更好的纠删码.

Existing repair-friendly erasure codes often have suboptimal I/O performance in repairs (§2.2). For example, Clay codes [36] are state-of-the-art minimum-storage regenerating (MSR) codes that provably minimize the amount of data accessed from local storage in single-block repairs, while minimizing storage redundancy for fault tolerance. Their core idea is sub-packetization, which divides an erasure-coded stripe (i.e., a set of blocks encoded together) into smaller sub-stripes composed of sub-blocks at the same block offset. During a single-block repair, Clay codes retrieve a minimum number of sub-blocks across sub-stripes for reconstruction. Despite minimizing data access, Clay codes require exponential sub-packetization for optimality, and issue numerous non-contiguous I/O seeks to retrieve sub-blocks in a repair. This significantly degrades repair performance in I/O-constrained environments due to amplified I/O requests. Locally repairable codes (e.g., Azure's LRC [10]) achieve I/O-efficient repairs, but incur higher storage redundancy. Other erasure codes support small sub-packetization with minimum storage redundancy [15, 16, 29, 35], yet they have various limitations in code constructions that lead to repair inefficiency.

现有便于修复的编码仍常有 I/O 不足, 见原文第 2.2 节. 例如 Clay [36] 是先进的最小存储再生码 (MSR), 在最小容错冗余下, 可证明地最小化单块修复读取量. 其基础是子分块, 将共同编码的一组块, 即条带, 划分为若干子条带, 每个子条带由各块相同偏移的子块组成. 修复时跨子条带取最少子块. 但最优性要求指数级子分块数, 导致大量不连续读取, 放大 I/O 请求, 在 I/O 受限环境中损害性能. Azure LRC [10] 等局部可修复码能改善 I/O, 却增加存储冗余. 其他小子分块 MDS 码 [15, 16, 29, 35] 也因构造限制而存在修复效率问题.

We present LESS, a family of erasure code constructions designed for I/O-efficient repairs, aiming to (i) reduce both the amount of data accessed and the number of I/O seeks with small sub-packetization (as low as two sub-stripes per stripe) and (ii) maintain balanced reductions across all blocks within a stripe (i.e., all blocks have similar data access and I/O seek costs). LESS builds on the notion of layering extended sub-stripes, by strategically stacking multiple extended sub-stripes (each with a longer stripe length) atop a regular stripe, such that a single-block repair (and some cases of multi-block repairs) can be done within an extended sub-stripe. LESS is designed with practicality in mind. It builds on the widely used Reed-Solomon (RS) codes [30] (§2.1) for a readily understandable design, and preserves the practical properties of RS codes. It further allows configurable sub-packetization to balance the trade-off between data access and I/O seeks.

LESS 有两个目标: 一是用较小的子分块数, 最低每条带仅两个子条带, 同时减少读取量和 I/O 次数; 二是使同一条带内所有块的修复代价接近. 核心是叠加扩展子条带: 在普通条带上安排多个更长的扩展子条带, 使单块以及部分多块修复仅在一个扩展子条带内完成. LESS 基于广泛采用的 RS 码 [30], 设计易于理解, 保留其实际应用属性, 并允许配置子分块数, 权衡读取量与 I/O 次数.

We implement and evaluate LESS on HDFS [34] in a local cluster. LESS reduces the single-block repair and full-node recovery times of Clay codes by up to 83.3% and 36.6%, respectively. We release the source code of LESS at: LESS.

我们在本地 HDFS [34] 集群实现 LESS. 相较 Clay, 单块修复和整节点恢复时间最多分别降低 83.3% 与 36.6%. 源代码已公开: LESS.

3. 背景

3.1 纠删码基础

We consider distributed storage systems that organize data in large fixed-size blocks (e.g., 128 MiB in HDFS [34] and 256 MiB in Facebook's f4 [21]) to mitigate I/O overhead. Such systems are typically I/O-bound, where network bandwidth and disk I/Os (on the order of MiB/s) are primary performance bottlenecks, rather than the computation overhead of encoding and decoding, as observed in prior work [6, 9, 18, 19]. Erasure coding ensures fault tolerance against block failures, which is essential for maintaining high data persistence in applications such as archival storage. We focus on RS codes [30], which are widely deployed in production [3, 5, 21, 23]. RS codes are configured by two parameters n and k (where n > k). An (n, k) RS code encodes k uncoded data blocks into n - k coded parity blocks, forming a stripe of n blocks, and ensures that any k out of n blocks can reconstruct all k data blocks (i.e., any n - k failed blocks are tolerable). In distributed storage systems, multiple stripes are independently encoded, with each stripe distributed across n nodes for tolerating any n - k node failures.

本文考虑按固定大小的大块组织数据的分布式系统, 如 HDFS 的 128 MiB [34] 和 Facebook f4 的 256 MiB [21], 以减少 I/O 开销. 这些系统通常受 I/O 限制, 主要瓶颈是网络与磁盘吞吐, 而非编码解码计算, 已有工作也观察到这一点 [6, 9, 18, 19]. 纠删码抵御块失效, 对归档等应用的数据持久性很重要. 本文聚焦生产中广泛部署的 RS 码 [3, 5, 21, 23, 30]. 参数 n > k, 将 k 个原始数据块编码为 n - k 个校验块, 共 n 块形成一个条带. 任取 k 块均可重建数据, 即容忍任意 n - k 块失效. 多个条带独立编码, 每条带分布到 n 个节点, 因而可容忍任意 n - k 节点失效.

RS codes satisfy three practical properties: (i) maximum distance separable (MDS), i.e., the redundancy (n/k times the data size) is minimized for tolerating any n - k failed blocks; (ii) general, i.e., any n and k (where n > k) can construct RS codes for a sufficiently large field size; and (iii) systematic, i.e., each stripe keeps k data blocks for direct access.

RS 码有三个实用属性: 1) 最大距离可分 (MDS), 容忍 n - k 块失效时, 总存储量为数据量的 n/k 倍, 达到最小冗余; 2) 参数通用, 对任意 n > k, 在足够大的有限域上均可构造; 3) 系统码, 保留 k 个原始数据块供直接访问.

RS encoding and decoding use linear combinations over a Galois Field GF(2w) with w-bit words, where n ≤ 2w + 1 [25]. Each block can be expressed as a linear combination of any k blocks under Galois Field arithmetic (see §3.1 for details).

RS 编解码在 w 位字的有限域 GF(2w) 上执行线性组合, 其中 n ≤ 2w + 1 [25]. 每块可表示为任意 k 块的有限域线性组合, 详见原文第 3.1 节.

RS codes incur high repair bandwidth, defined as the amount of data transferred across nodes during a repair. Repairing a single failed block needs to retrieve k blocks of the same stripe from other nodes; we call this process conventional repair, which applies to all (n, k) MDS codes. It also incurs high repair I/O, defined as the amount of data accessed from local storage during a repair. In high-speed networks, repair I/O becomes the dominant bottleneck (§1).

修复带宽指修复期间跨节点传输的数据量. RS 单块修复需从其他节点取同条带的 k 块, 本文称为常规修复, 适用于所有 (n, k) MDS 码. 它也带来较高的修复 I/O, 即从本地存储读取的数据量. 高速网络中, 后者成为主要瓶颈, 见原文第 1 节.

3.2 修复优化相关工作

Prior surveys [1, 33] review extensive research on optimizing single-block repair performance in erasure-coded storage. We review several representative repair-friendly erasure codes and their limitations.

已有综述 [1, 33] 总结了大量单块修复研究. 本节介绍代表性编码及其限制.

Minimum-storage regenerating (MSR) codes. MSR codes [4] minimize repair bandwidth for single-block repairs, while preserving the MDS property (i.e., minimum redundancy). They build on sub-packetization, which divides each block into α > 1 sub-blocks and forms α sub-stripes of n sub-blocks at the same offset across blocks. Each sub-block is a linear combination of other nα - 1 sub-blocks in the stripe over GF(2w). A single-block repair transfers a fraction of sub-blocks, with the minimum repair bandwidth.

最小存储再生码. MSR [4] 在保持 MDS 最小冗余的同时, 最小化单块修复带宽. 每块分成 α > 1 个子块, 各块相同偏移的 n 个子块组成一个子条带, 共 α 个. 每个子块在 GF(2w) 上是同条带其他 nα - 1 个子块的线性组合. 修复只传输部分子块, 达到最小带宽.

Traditional MSR codes [4] require nodes to read and encode all local sub-blocks, leading to high repair I/O. I/O-optimal MSR codes minimize repair I/O, by allowing accessed data to be sent directly without encoding. For example, Functional MSR (F-MSR) codes [6, 8] require n - k = 2 [8] or n - k = 3 [6], with a linear α = n - k, but are non-systematic. PM-RBT codes [27] are systematic but require n ≥ 2k - 1, while Butterfly codes [22] are also systematic but require n - k = 2 and incur an exponential α = 2k-1.

传统 MSR [4] 要求节点读取并编码本地全部子块, 修复 I/O 较高. I/O 最优 MSR 则允许直接发送读出的数据, 无须再编码. 例如 F-MSR [6, 8] 在 n - k 为 2 [8] 或 3 [6] 时, 采用线性 α = n - k, 但不是系统码. PM-RBT [27] 是系统码, 却要求 n ≥ 2k - 1; Butterfly [22] 也是系统码, 但要求 n - k = 2, 且 α = 2k-1 指数增长.

Clay codes [36] are state-of-the-art I/O-optimal MSR codes that are systematic, support general (n, k), and are deployed in Ceph [38]. However, Clay codes impose an exponential α = (n - k)⌈n/(n-k)⌉ (note that exponential sub-packetization is necessary for I/O-optimal MSR codes [2]). Even though Clay codes minimize repair I/O, they access numerous non-contiguous sub-blocks and incur substantial I/O seeks, defined as the number of non-contiguous reads to local storage in a repair. This leads to sub-optimal repair performance due to the overhead of handling extensive I/O requests [35].

Clay [36] 是先进的 I/O 最优 MSR, 支持通用 (n, k), 保持系统码形式, 已部署于 Ceph [38]. 但 α = (n - k)⌈n/(n-k)⌉, 呈指数增长, 而这对 I/O 最优 MSR 是必要条件 [2]. 虽读取量最少, 却要访问大量不连续子块. 本文将修复期间本地非连续读取次数称为 I/O seeks, 大量请求的处理开销会降低实际性能 [35].

Locally repairable codes (LRCs). LRCs [10, 12, 14, 31] reduce repair I/O for single-block repairs. For example, Azure-LRC [10] partitions data blocks into local groups and adds a local parity block per local group. Repairing a failed data or local parity block accesses only the blocks of its local group. However, Azure-LRC encodes all data blocks of a stripe into global parity blocks, whose repairs still rely on conventional repair. Some LRC variants support local repairs for global parity blocks [14], but LRCs are non-MDS and have higher redundancy than RS codes.

局部可修复码. LRC [10, 12, 14, 31] 降低单块修复 I/O. Azure LRC [10] 将数据分为局部组, 各增一个局部校验块, 修复数据块或局部校验块仅访问本组. 但全局校验块仍编码全条带数据, 需常规修复. 一些变体也支持全局校验块局部修复 [14], 但 LRC 不满足 MDS, 冗余高于 RS.

MDS codes with small sub-packetization. To limit I/O seeks, some MDS codes allow a small α with reduced repair I/O. Hitchhiker codes [29] use α = 2 sub-stripes of RS codes by combining sub-blocks across sub-stripes via piggybacking functions, and reduce repair I/O for data blocks by 25-45% compared to RS codes; however, parity-block repairs still follow conventional repair. HashTag codes [16] reduce repair I/O for data blocks with general (n, k) and α ≥ 2; their extended codes [15] reduce repair I/O for both data and parity blocks, but require α ≥ 4 and α as a multiple of n - k.

小子分块 MDS 码. Hitchhiker [29] 用 α = 2 的 RS 子条带和捎带函数组合子块, 将数据块修复 I/O 降低 25%-45%, 校验块仍用常规修复. HashTag [16] 支持通用 (n, k), α ≥ 2, 降低数据块读取量; 扩展版 [15] 同时优化数据和校验块, 但要求 α ≥ 4 且为 n - k 的倍数.

Elastic Transformation (ET) [35] converts an RS code into a repair-friendly code with a configurable α ≥ 2. However, the transformation restricts flexibility in code construction and limits further repair improvements.

弹性变换 ET [35] 将 RS 转为 α ≥ 2 可配置的便于修复编码, 但变换限制了构造灵活性与进一步优化空间.

Repair-efficient algorithms. Our study focuses on erasure code construction, while some studies design repair-efficient algorithms, such as search of minimum-I/O recovery for XOR-based erasure codes [13, 39] or repair parallelization [17, 18, 20, 32]. They do not minimize repair I/O due to constraints from underlying erasure codes.

高效修复算法. 本文研究编码构造; 其他工作研究 XOR 码最小 I/O 恢复搜索 [13, 39], 或修复并行化 [17, 18, 20, 32]. 受底层编码限制, 它们并不能最小化修复 I/O.

The limitations inspire LESS, a family of repair-friendly erasure codes with I/O efficiency in mind. We observe that repair performance depends on both repair I/O and I/O seeks. Minimizing repair I/O introduces an exponential α [2, 36] (and hence high I/O seeks) and can negate repair performance gains. LESS targets near-minimum repair I/O with a small and configurable α to limit I/O seeks. Its design goals include:

修复性能同时取决于读取量与 I/O 次数. 极小化读取量需要指数级 α [2, 36], 从而增加 I/O 次数, 可能抵消收益. LESS 以较小且可配置的 α, 在接近最小读取量的同时限制 I/O 次数. 设计目标如下.

Preserving RS code properties: LESS is MDS, supports general (n, k), and remains systematic, as in RS codes.

保留 RS 属性: 满足 MDS, 支持通用 (n, k), 保持系统码形式.

I/O-efficient repair: LESS achieves I/O-efficient repairs in three aspects: (i) reduced repair I/O, (ii) reduced I/O seeks (e.g., α = 2, 3, or 4); and (iii) balanced reductions (i.e., similar reductions in repair I/O and I/O seeks across data and parity blocks). LESS also allows α to be configurable.

高效修复 I/O: 减少读取量, 减少非连续访问, 如 α 可取 2, 3, 4, 并让数据与校验块收益接近. α 也可配置.

Single- and multi-block repair efficiency: Earlier studies focus on optimizing single-block repairs, which dominate in practice (e.g., 98% of failures in (14, 10)-coded stripes [28]). However, wide-stripe codes (i.e., n and k are large) emerge and make multi-block repairs more common [12]. LESS addresses both scenarios.

兼顾单块与多块修复. 以往主要优化单块失效, 因其占多数, 如 (14, 10) 条带中占 98% [28]. 但 n, k 较大的宽条带逐渐普及, 多块修复更常见 [12]. LESS 同时考虑两类情况.

4. LESS 设计

LESS is constructed with configurable parameters (n, k, α), where k < n and 2 ≤ α ≤ n - k. Its key idea is to layer multiple extended sub-stripes, each constructed from sub-blocks and encoded using Vandermonde-based RS codes, such that a single-block repair always retrieves the sub-blocks from a single extended sub-stripe. LESS also enables I/O-efficient multi-block repairs if the failed blocks share the same extended sub-stripe.

LESS 参数为 (n, k, α), k < n, 2 ≤ α ≤ n - k. 它叠加多个由子块组成, 经 Vandermonde RS 编码的扩展子条带, 使单块修复始终只从一个扩展子条带取数据. 多块失效若属于同一扩展子条带, 也可高效修复.

4.4 修复

LESS supports efficient repair of single-block failures within an extended sub-stripe and certain multi-block failures when the failed blocks reside in the same extended sub-stripe.

LESS 可在一个扩展子条带内高效修复单块失效; 多个失效块处于同一扩展子条带时, 部分情况也可高效修复.

Single-block repair. For a failed block Bi (1 ≤ i ≤ n) in Gz (1 ≤ z ≤ α), we repair Bi using sub-blocks within Xz, which contains all sub-blocks of Gz. Since Xz is an (|Xz|, |Xz| - n + k) RS-coded stripe, it tolerates any n - k ≥ α sub-block failures. The α failed sub-blocks can be reconstructed using the parity-check equation (Equation (5)) for Xz. To reduce accessed blocks, we prioritize transferring |Gz|(α - 1) available sub-blocks from Gz, followed by |Xz| - n + k - |Gz|(α - 1) available sub-blocks from other block groups.

单块修复. 对 Gz 中失效的 Bi, 原文此处写 1 ≤ z ≤ α, 使用包含该组全部子块的 Xz 修复. 其 RS 编码可容忍 n - k ≥ α 个子块失效, 因而可用式 (5) 恢复失效块的 α 个子块. 为减少访问块数, 优先传输本组 |Gz|(α - 1) 个可用子块, 再从其他组传输 |Xz| - n + k - |Gz|(α - 1) 个可用子块.

Multi-block repair. LESS is also beneficial for a multi-block repair, where we simultaneously repair multiple failed blocks on a single stripe. When ⌊(n - k)/α⌋ ≥ 2, LESS can repair any ⌊(n - k)/α⌋ block failures within one extended sub-stripe if all failed blocks reside in the same block group, say Gz (1 ≤ z ≤ α + 1). With all failed sub-blocks in Xz, since α⌊(n - k)/α⌋ ≤ n - k, the failed sub-blocks can be repaired within Xz. For other multi-block failure cases, LESS resorts to conventional repair (which retrieves k blocks). This requires 15 sub-blocks, with 25% less repair I/O than the conventional repair of the (14, 10) RS code.

多块修复. 当 ⌊(n - k)/α⌋ ≥ 2, 且失效块属于同一组 Gz, 1 ≤ z ≤ α + 1, LESS 可在一个扩展子条带内修复任意 ⌊(n - k)/α⌋ 块失效. 因为所有失效子块均在 Xz, 且其数量 α⌊(n - k)/α⌋ ≤ n - k. 其他情况退回读取 k 个完整块的常规修复. 例如图 2 的 (14, 10, 2) 条带, 同组 B₁ 和 B₂ 失效时, 四个失效子块都在 X₁, 可利用其 (19, 15) RS 编码, 只读 15 子块, 比常规修复少 25%.

Implementation. We implement LESS on OpenEC (an erasure coding middleware) [19] atop Hadoop 3.3.4 HDFS [7] and use Jerasure [26] for coding operations. We also include RS, Clay, Hitchhiker, HashTag, and ET in our comparisons. Our prototype adds 8.7 K LoC to OpenEC in C++.

HDFS uses a NameNode for storage management and multiple DataNodes for storage. HDFS organizes data in fixed-size blocks, each further partitioned into multiple packets. The packets at the same block offset are encoded together, allowing pipelined coding operations across packets. Our prototype follows this packet-level pipelined implementation.

Methodology. We conduct testbed experiments in a 15-machine local cluster connected via a 10 Gbps Ethernet switch. We use Wondershaper [11] to configure the network bandwidth of each machine. We use one machine for the NameNode and 14 machines for DataNodes. 6. 结论

LESS is a family of erasure codes designed for I/O-efficient repairs by layering extended sub-stripes, so as to reduce both repair I/O and I/O seeks and ensure balanced reductions across blocks. It has several practical properties: MDS, general parameters, systematic, and configurable sub-packetization. Numerical analysis and testbed experiments show LESS's repair benefits over state-of-the-art repair-friendly codes.

LESS 通过叠加扩展子条带, 同时减少读取量与 I/O 次数, 并让各块收益均衡. 它满足 MDS, 支持通用参数, 保持系统码形式, 且子分块数可配置. 数值分析和集群实验表明, 修复性能优于先进的便于修复编码.

Proof of Theorem 1. To ensure LESS is MDS, we can verify the parity-check matrix of LESS, such that any n - k out of n parity sub-matrices can form an (n - k)α × (n - k)α square invertible matrix. Recall that any invertible square matrix has a non-zero determinant. To ensure that all possible square matrices from the parity-check matrix are invertible, we can multiply the determinants of the square matrices and ensure that the product is non-zero.

定理 1 的证明. 要保证 LESS 满足 MDS, 只需验证从 n 个校验子矩阵中任取 n - k 个, 都能组成 (n - k)α × (n - k)α 可逆方阵. 可逆方阵的行列式非零. 因此, 可以将所有可能方阵的行列式相乘, 只要乘积非零, 就能保证它们全部可逆.

There are C(n, n - k) cases for selecting n - k matrices out of the n parity-check sub-matrices to form a square matrix. The determinant of each square matrix can be viewed as a polynomial over the coding coefficients vi, j (1 ≤ i ≤ n and 1 ≤ j ≤ α). Each vi, j appears in only one parity-check sub-matrix, Hi, and there are C(n - 1, k) possible square matrices that contain Hi. Thus, the degree of vi, j in the determinant of such a square matrix is n - k - 1. By multiplying the determinants of all square matrices, the degree of each vi, j is (n - k - 1) C(n - 1, k). We can choose nα distinct coding coefficients in GF(2w) to ensure the product of determinants is non-zero when 2w ≥ nα + (n - k - 1) C(n - 1, k), which can be proven from Noga Alon's Combinatorial Nullstellensatz.

从 n 个校验子矩阵中选 n - k 个, 共 C(n, n - k) 种. 每个方阵的行列式可视为关于 vi, j 的多项式. 每个系数只出现在 Hi 中, 包含该子矩阵的方阵有 C(n - 1, k) 个. 该系数在每个相应行列式中的次数为 n - k - 1, 因而所有行列式相乘后, 次数为 (n - k - 1) C(n - 1, k). 当 2w ≥ nα + (n - k - 1) C(n - 1, k) 时, 能从 GF(2w) 选出 nα 个互异系数, 使行列式乘积非零. 这一结论可由 Noga Alon 的组合零点定理证明.

10. 附录 B: 实验材料

10.1 摘要

LESS is a family of erasure codes designed to improve repair I/O efficiency by layering extended sub-stripes, aiming to reduce both repair I/O and I/O seeks and maintain balanced reductions across all blocks. We implement LESS on OpenEC, an erasure coding middleware, atop Hadoop 3.3.4 HDFS.

LESS 通过叠加扩展子条带提高纠删码修复的 I/O 效率, 同时减少读取量与非连续 I/O 次数, 并使所有块获得均衡收益. 实现基于 Hadoop 3.3.4 HDFS 上的纠删码中间件 OpenEC.

10.2 范围

The artifact is a research-driven prototype that can be used to validate the concepts, designs, and evaluation results of LESS presented in the paper.

实验材料是研究原型, 用于验证论文提出的 LESS 概念, 设计与评估结果.

10.3 内容

The artifact has the following contents: src/, which includes the implementation of LESS as a patch to the OpenEC codebase; scripts/, which includes the evaluation scripts and configuration files to reproduce our evaluation results; README.md, which overviews the implementation and provides essential information to run the prototype; and AE_INSTRUCTION.md, which includes detailed instructions for artifact evaluation.

材料包括: src/, 以 OpenEC 补丁形式实现 LESS; scripts/, 保存复现实验所需脚本与配置; README.md, 介绍实现及运行原型的基本信息; AE_INSTRUCTION.md, 提供详细评估步骤.

10.4 托管

The artifact is hosted in GitHub at LESS. We use version v1.0.0 for artifact evaluation.

材料托管于 GitHub 的 LESS 仓库, 评估使用 v1.0.0.

10.5 依赖条件

Hardware Dependencies. We recommend 15 machines to run the experiments with our prototype and evaluation scripts. These machines need to be connected via a 10 Gbps network, such that they are reachable from each other. For each machine, we recommend a quad-core CPU, 16 GiB of memory, a 7200 RPM SATA HDD and above. We need a minimum of 15 machines to form a storage cluster for the default erasure coding parameters (n, k) = (14, 10). In particular, we use one machine to run the HDFS NameNode and the other machines to run the HDFS DataNodes.

硬件依赖. 建议使用 15 台机器运行原型与评估脚本, 经 10 Gbps 网络互连且能相互访问. 每台建议至少四核 CPU, 16 GiB 内存和 7200 RPM SATA HDD. 默认 (14, 10) 编码至少需要 15 台机器: 一台运行 HDFS NameNode, 其余运行 DataNode.

Software Dependencies. The artifact is developed and tested on Ubuntu 22.04 LTS with the following software dependencies: OpenEC requires g++, cmake, redis, hiredis, ISA-L, and gf-complete; Hadoop HDFS requires openjdk-8-jdk and maven; scripts require expect, python3, and wondershaper.

软件依赖. 材料在 Ubuntu 22.04 LTS 开发测试. OpenEC 依赖 g++, cmake, redis, hiredis, ISA-L, gf-complete; Hadoop HDFS 依赖 openjdk-8-jdk, maven; 脚本依赖 expect, python3, wondershaper.

Please set up the testbed with the following steps: prepare the hardware dependencies as described; download the artifact, version v1.0.0, from LESS releases; extract the files with tar -zxvf less.tar.gz and run cd less to navigate to the project directory; follow AE_INSTRUCTION.md to set up the testbed and run experiments with our provided evaluation scripts. The testbed setup takes around 5 hours, depending on the hardware specifications.

按以下顺序搭建: 准备上述硬件; 从 LESS 发布页 下载 v1.0.0; 执行 tar -zxvf less.tar.gz 解压, 再用 cd less 进入项目; 按 AE_INSTRUCTION.md 配置集群, 使用配套脚本运行实验. 搭建约需 5 小时, 具体取决于硬件.

10.7 评估目标

Our goal is to demonstrate LESS's effectiveness in improving repair performance. For numerical analysis, Exp#A1 and Exp#A2, we expect the results to match those in our paper. For testbed experiments, Exp#B1 to Exp#B5, we expect that LESS reduces the single-block repair and full-node recovery times compared to the baseline erasure codes. However, the testbed experiment results may vary from those in our paper due to different factors, such as cluster sizes, machine specifications, operating systems, and software packages.

目标是验证 LESS 改善修复性能的效果. 数值分析 Exp#A1, A2 应与论文一致; 集群实验 Exp#B1 至 B5 应体现 LESS 相较基线缩短单块修复和整节点恢复时间. 具体数值可能因集群规模, 机器配置, 操作系统及软件包不同而变化.
