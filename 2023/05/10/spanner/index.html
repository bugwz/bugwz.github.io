0. 摘要

Spanner is Google's scalable, multi-version, globally-distributed, and synchronously-replicated database. It is the first system to distribute data at global scale and support externally-consistent distributed transactions. This paper describes how Spanner is structured, its feature set, the rationale underlying various design decisions, and a novel time API that exposes clock uncertainty. This API and its implementation are critical to supporting external consistency and a variety of powerful features: non-blocking reads in the past, lock-free read-only transactions, and atomic schema changes, across all of Spanner.

Spanner 是 Google 的可扩展多版本数据库, 数据分布于全球, 并采用同步复制. 它是第一个在全球范围分布数据, 同时支持具有外部一致性的分布式事务的系统. 本文介绍 Spanner 的结构, 功能, 各项设计决策的依据, 以及一种显式暴露时钟不确定性的新型时间 API. 这一 API 及其实现是支持外部一致性的关键, 也使整个 Spanner 能够提供多项重要功能: 不阻塞的历史读取, 无锁只读事务和原子模式变更.

1. 引言

Spanner is a scalable, globally-distributed database designed, built, and deployed at Google. At the highest level of abstraction, it is a database that shards data across many sets of Paxos [21] state machines in datacenters spread all over the world. Replication is used for global availability and geographic locality; clients automatically failover between replicas. Spanner automatically reshards data across machines as the amount of data or the number of servers changes, and it automatically migrates data across machines (even across datacenters) to balance load and in response to failures. Spanner is designed to scale up to millions of machines across hundreds of datacenters and trillions of database rows.

Spanner 是 Google 设计, 构建并部署的可扩展全球分布式数据库. 从最高层的抽象看, 它将数据分片到多组 Paxos 状态机 [21] 中, 这些状态机分布在世界各地的数据中心. 复制既用于提供全球可用性, 也用于改善地理局部性; 客户端能够在副本间自动故障转移. 数据量或服务器数量变化时, Spanner 会自动重新分片; 为均衡负载和应对故障, 它还会在机器间自动迁移数据, 甚至跨数据中心迁移. 其设计目标是扩展到数百个数据中心中的数百万台机器, 管理数万亿行数据.

Applications can use Spanner for high availability, even in the face of wide-area natural disasters, by replicating their data within or even across continents. Our initial customer was F1 [35], a rewrite of Google's advertising backend. F1 uses five replicas spread across the United States. Most other applications will probably replicate their data across 3 to 5 datacenters in one geographic region, but with relatively independent failure modes. That is, most applications will choose lower latency over higher availability, as long as they can survive 1 or 2 datacenter failures.

应用可以将数据复制到同一大陆甚至不同大陆, 从而在大范围自然灾害下仍保持高可用. 我们的首个用户是 F1 [35], 即重新实现的 Google 广告后端, 它使用分布于美国各地的 5 个副本. 多数其他应用可能会把数据复制到同一地理区域中故障相对独立的 3-5 个数据中心. 换言之, 只要能承受 1-2 个数据中心故障, 多数应用就会优先选择较低延迟, 而不是更高的可用性.

Spanner's main focus is managing cross-datacenter replicated data, but we have also spent a great deal of time in designing and implementing important database features on top of our distributed-systems infrastructure. Even though many projects happily use Bigtable [9], we have also consistently received complaints from users that Bigtable can be difficult to use for some kinds of applications: those that have complex, evolving schemas, or those that want strong consistency in the presence of wide-area replication. (Similar claims have been made by other authors [37].) Many applications at Google have chosen to use Megastore [5] because of its semi-relational data model and support for synchronous replication, despite its relatively poor write throughput. As a consequence, Spanner has evolved from a Bigtable-like versioned key-value store into a temporal multi-version database. Data is stored in schematized semi-relational tables; data is versioned, and each version is automatically timestamped with its commit time; old versions of data are subject to configurable garbage-collection policies; and applications can read data at old timestamps. Spanner supports general-purpose transactions, and provides a SQL-based query language.

Spanner 的主要任务是管理跨数据中心复制的数据, 但我们也投入了大量时间, 在分布式系统基础设施之上设计和实现重要的数据库功能. 虽然许多项目乐于使用 Bigtable [9], 用户仍不断反映, 某些应用使用它很困难, 特别是模式复杂且持续演进的应用, 以及需要在广域复制下保持强一致性的应用. 其他研究者也提出过类似观点 [37]. Google 的许多应用选择了 Megastore [5], 看重的是其半关系数据模型和同步复制能力, 即使它的写吞吐量相对较低. 因此, Spanner 从类似 Bigtable 的多版本键值存储, 演变为支持时间维度的多版本数据库. 数据存放在具有明确模式的半关系表中, 每个版本自动以提交时间标记; 旧版本按照可配置策略回收, 应用也可以按历史时间戳读取数据. Spanner 支持通用事务, 并提供基于 SQL 的查询语言.

As a globally-distributed database, Spanner provides several interesting features. First, the replication configurations for data can be dynamically controlled at a fine grain by applications. Applications can specify constraints to control which datacenters contain which data, how far data is from its users (to control read latency), how far replicas are from each other (to control write latency), and how many replicas are maintained (to control durability, availability, and read performance). Data can also be dynamically and transparently moved between datacenters by the system to balance resource usage across datacenters. Second, Spanner has two features that are difficult to implement in a distributed database: it provides externally consistent [16] reads and writes, and globally-consistent reads across the database at a timestamp. These features enable Spanner to support consistent backups, consistent MapReduce executions [12], and atomic schema updates, all at global scale, and even in the presence of ongoing transactions.

Spanner 是全球分布式数据库, 有几项值得关注的功能. 首先, 应用可以细粒度地动态配置副本: 指定哪些数据中心保存数据, 数据与用户的距离 (影响读延迟), 副本之间的距离 (影响写延迟), 以及副本数量 (影响持久性, 可用性和读性能). 系统还能在数据中心之间自动迁移数据, 均衡资源, 应用无须介入. 其次, Spanner 支持分布式数据库很难提供的两项功能: 具有外部一致性 [16] 的读写事务, 以及在指定时间戳对整个数据库进行全局一致读取. 因此, 即使仍有事务在执行, 它也能在全球范围支持一致备份, 一致的 MapReduce 执行 [12] 和原子模式更新.

These features are enabled by the fact that Spanner assigns globally-meaningful commit timestamps to transactions, even though transactions may be distributed. The timestamps reflect serialization order. In addition, the serialization order satisfies external consistency (or equivalently, linearizability [20]): if a transaction T1 commits before another transaction T2 starts, then T1's commit timestamp is smaller than T2's. Spanner is the first system to provide such guarantees at global scale.

这些功能依赖于 Spanner 为事务分配具有全局意义的提交时间戳, 即使事务本身是分布式的. 时间戳反映事务的串行化顺序, 且该顺序满足外部一致性, 或等价地说, 线性一致性 [20]: 如果事务 T1 在事务 T2 开始前已经提交, 那么 T1 的提交时间戳小于 T2. Spanner 是第一个在全球规模提供这一保证的系统.

The key enabler of these properties is a new TrueTime API and its implementation. The API directly exposes clock uncertainty, and the guarantees on Spanner's timestamps depend on the bounds that the implementation provides. If the uncertainty is large, Spanner slows down to wait out that uncertainty. Google's cluster-management software provides an implementation of the TrueTime API. This implementation keeps uncertainty small (generally less than 10ms) by using multiple modern clock references (GPS and atomic clocks).

这些性质的关键是一套新的 TrueTime API 及其实现. API 直接暴露时钟不确定性, Spanner 对时间戳的保证取决于该实现提供的不确定性边界. 不确定性越大, Spanner 就需要等待越久, 性能也会下降. Google 的集群管理软件实现了 TrueTime API, 利用 GPS 和原子钟等多种现代时间基准, 将不确定性保持在较小范围内, 通常低于 10 ms.

Section 2 describes the structure of Spanner's implementation, its feature set, and the engineering decisions that went into their design. Section 3 describes our new TrueTime API and sketches its implementation. Section 4 describes how Spanner uses TrueTime to implement externally-consistent distributed transactions, lock-free read-only transactions, and atomic schema updates. Section 5 provides some benchmarks on Spanner's performance and TrueTime behavior, and discusses the experiences of F1. Sections 6, 7, and 8 describe related and future work, and summarize our conclusions.

原文第 2 节介绍 Spanner 的实现结构, 功能及相关工程决策. 第 3 节介绍 TrueTime API 并概述其实现. 第 4 节说明如何利用 TrueTime 实现具有外部一致性的分布式事务, 无锁只读事务和原子模式更新. 第 5 节给出性能及 TrueTime 行为的测试结果, 并讨论 F1 的使用经验. 第 6-8 节依次介绍相关工作, 未来工作和结论.

2. 实现

This section describes the structure of and rationale underlying Spanner's implementation. It then describes the directory abstraction, which is used to manage replication and locality, and is the unit of data movement. Finally, it describes our data model, why Spanner looks like a relational database instead of a key-value store, and how applications can control data locality.

本节介绍 Spanner 的实现结构及其设计依据, 随后介绍 directory 抽象. Directory 用于管理复制和局部性, 也是数据迁移的单位. 最后介绍数据模型, 解释为什么 Spanner 更像关系数据库而非键值存储, 以及应用如何控制数据局部性.

A Spanner deployment is called a universe. Given that Spanner manages data globally, there will be only a handful of running universes. We currently run a test/playground universe, a development/production universe, and a production-only universe.

一次完整的 Spanner 部署称为一个 universe. 由于 Spanner 在全球管理数据, 实际运行的 universe 只会有少数几个. 我们目前运行着一个测试和试验用 universe, 一个开发与生产混用的 universe, 以及一个专用于生产的 universe.

Spanner is organized as a set of zones, where each zone is the rough analog of a deployment of Bigtable servers [9]. Zones are the unit of administrative deployment. The set of zones is also the set of locations across which data can be replicated. Zones can be added to or removed from a running system as new datacenters are brought into service and old ones are turned off, respectively. Zones are also the unit of physical isolation: there may be one or more zones in a datacenter, for example, if different applications' data must be partitioned across different sets of servers in the same datacenter.

Spanner 由一组 zone 组成, 每个 zone 大致相当于一次 Bigtable 服务器集群部署 [9]. Zone 是运维部署单位, 也是可供数据复制到的位置. 随着新数据中心上线或旧数据中心退役, 可以在运行中添加或移除 zone. Zone 也是物理隔离单位: 一个数据中心可以有一个或多个 zone, 例如不同应用的数据必须放在同一数据中心的不同服务器集合中时, 就可划分多个 zone.

Figure 1 illustrates the servers in a Spanner universe. A zone has one zonemaster and between one hundred and several thousand spanservers. The former assigns data to spanservers; the latter serve data to clients. The per-zone location proxies are used by clients to locate the spanservers assigned to serve their data. The universe master and the placement driver are currently singletons. The universe master is primarily a console that displays status information about all the zones for interactive debugging. The placement driver handles automated movement of data across zones on the timescale of minutes. The placement driver periodically communicates with the spanservers to find data that needs to be moved, either to meet updated replication constraints or to balance load. For space reasons, we will only describe the spanserver in any detail.

图 1 展示一个 universe 中的服务器组成. 每个 zone 有一个 zonemaster 和 100 到数千个 spanserver; 前者负责分配数据, 后者为客户端提供数据服务. 每个 zone 的位置代理 (location proxy) 帮助客户端找到负责相应数据的 spanserver. Universe master 和 placement driver 目前都只有一个实例. Universe master 主要提供显示各 zone 状态的控制台, 供交互式调试. Placement driver 以分钟为时间尺度, 自动执行跨 zone 数据迁移; 它定期联系 spanserver, 找出需要迁移的数据, 以满足变更后的复制约束或均衡负载. 限于篇幅, 下面只详细介绍 spanserver.

2.1 Spanserver 软件栈

This section focuses on the spanserver implementation to illustrate how replication and distributed transactions have been layered onto our Bigtable-based implementation. The software stack is shown in Figure 2. At the bottom, each spanserver is responsible for between 100 and 1000 instances of a data structure called a tablet. A tablet is similar to Bigtable's tablet abstraction, in that it implements a bag of the following mappings:

本节聚焦 spanserver, 说明如何在基于 Bigtable 的实现上增加复制和分布式事务. 软件栈如图 2 所示. 在底层, 每个 spanserver 负责 100-1000 个称为 tablet 的数据结构实例. 它类似于 Bigtable 的 tablet, 实现一组如下映射:

(key:string, timestamp:int64) -> string

Unlike Bigtable, Spanner assigns timestamps to data, which is an important way in which Spanner is more like a multi-version database than a key-value store. A tablet's state is stored in set of B-tree-like files and a write-ahead log, all on a distributed file system called Colossus (the successor to the Google File System [15]).

与 Bigtable 不同, Spanner 由系统为数据分配时间戳, 这也是它更像多版本数据库而非键值存储的重要体现. Tablet 的状态保存在一组类似 B 树的文件和一份预写日志中, 全部存储在分布式文件系统 Colossus 上; Colossus 是 Google File System [15] 的后继系统.

Figure 2: Spanserver software stack.

图 2: Spanserver 软件栈.

To support replication, each spanserver implements a single Paxos state machine on top of each tablet. (An early Spanner incarnation supported multiple Paxos state machines per tablet, which allowed for more flexible replication configurations. The complexity of that design led us to abandon it.) Each state machine stores its metadata and log in its corresponding tablet. Our Paxos implementation supports long-lived leaders with time-based leader leases, whose length defaults to 10 seconds. The current Spanner implementation logs every Paxos write twice: once in the tablet's log, and once in the Paxos log. This choice was made out of expediency, and we are likely to remedy this eventually. Our implementation of Paxos is pipelined, so as to improve Spanner's throughput in the presence of WAN latencies; but writes are applied by Paxos in order (a fact on which we will depend in Section 4).

为支持复制, spanserver 在每个 tablet 之上实现一个 Paxos 状态机. 早期版本曾允许每个 tablet 对应多个状态机, 以获得更灵活的复制配置, 但设计过于复杂, 最终被放弃. 每个状态机将元数据和日志保存在对应的 tablet 中. 我们的 Paxos 实现支持长期任职的 leader, 使用默认长度为 10 秒的时间租约. 当前实现对每次 Paxos 写入记录两遍日志, 一遍进入 tablet 日志, 一遍进入 Paxos 日志; 这是出于实现便利的权宜选择, 以后很可能修正. 为改善广域网延迟下的吞吐量, Paxos 采用流水线执行, 但写入仍按顺序应用, 原文第 4 节会依赖这一性质.

The Paxos state machines are used to implement a consistently replicated bag of mappings. The key-value mapping state of each replica is stored in its corresponding tablet. Writes must initiate the Paxos protocol at the leader; reads access state directly from the underlying tablet at any replica that is sufficiently up-to-date. The set of replicas is collectively a Paxos group.

Paxos 状态机实现一组以一致方式复制的映射. 每个副本的键值映射状态保存在其对应的 tablet 中. 写入必须在 leader 上发起 Paxos 协议; 读取可以直接访问任意足够新的副本所持有的底层 tablet. 这一组副本统称为一个 Paxos 组.

At every replica that is a leader, each spanserver implements a lock table to implement concurrency control. The lock table contains the state for two-phase locking: it maps ranges of keys to lock states. (Note that having a long-lived Paxos leader is critical to efficiently managing the lock table.) In both Bigtable and Spanner, we designed for long-lived transactions (for example, for report generation, which might take on the order of minutes), which perform poorly under optimistic concurrency control in the presence of conflicts. Operations that require synchronization, such as transactional reads, acquire locks in the lock table; other operations bypass the lock table.

对于本机上担任 leader 的每个副本, spanserver 都维护一张锁表来实现并发控制. 锁表记录两阶段锁的状态, 将键范围映射到锁状态. 长期稳定的 Paxos leader 对高效管理锁表至关重要. Bigtable 和 Spanner 都考虑了长事务, 例如耗时数分钟的报表生成; 存在冲突时, 乐观并发控制对这类事务效果较差. 需要同步的操作, 如事务性读取, 会在锁表中加锁; 其他操作则绕过锁表.

At every replica that is a leader, each spanserver also implements a transaction manager to support distributed transactions. The transaction manager is used to implement a participant leader; the other replicas in the group will be referred to as participant slaves. If a transaction involves only one Paxos group (as is the case for most transactions), it can bypass the transaction manager, since the lock table and Paxos together provide transactionality. If a transaction involves more than one Paxos group, those groups' leaders coordinate to perform two-phase commit. One of the participant groups is chosen as the coordinator: the participant leader of that group will be referred to as the coordinator leader, and the slaves of that group as coordinator slaves. The state of each transaction manager is stored in the underlying Paxos group (and therefore is replicated).

对于每个 leader 副本, spanserver 还维护事务管理器, 以支持分布式事务. 它实现参与者 leader (participant leader) 的职责, 同组其他副本称为参与者从副本 (participant slave). 多数事务只涉及一个 Paxos 组, 此时锁表与 Paxos 已能提供事务性, 无需经过事务管理器. 涉及多个组时, 各组 leader 协同执行两阶段提交. 其中一个参与组被选为协调者, 其 leader 称为协调者 leader, 从副本称为协调者从副本. 各事务管理器的状态保存在底层 Paxos 组中, 因而也会复制.

2.2 Directory 与数据放置

On top of the bag of key-value mappings, the Spanner implementation supports a bucketing abstraction called a directory, which is a set of contiguous keys that share a common prefix. (The choice of the term directory is a historical accident; a better term might be bucket.) We will explain the source of that prefix in Section 2.3. Supporting directories allows applications to control the locality of their data by choosing keys carefully.

在键值映射之上, Spanner 提供名为 directory 的分桶抽象: 一组具有共同前缀的连续键. Directory 这一名称是历史遗留, bucket 可能更贴切. 前缀的来源将在原文第 2.3 节解释. 应用可以通过合理选键, 借助 directory 控制数据局部性.

A directory is the unit of data placement. All data in a directory has the same replication configuration. When data is moved between Paxos groups, it is moved directory by directory, as shown in Figure 3. Spanner might move a directory to shed load from a Paxos group; to put directories that are frequently accessed together into the same group; or to move a directory into a group that is closer to its accessors. Directories can be moved while client operations are ongoing. One could expect that a 50MB directory can be moved in a few seconds.

Directory 是数据放置单位, 其中所有数据采用相同复制配置. 数据在 Paxos 组之间逐 directory 迁移, 如图 3 所示. 迁移可能是为减轻某个组的负载, 将经常一起访问的 directory 放到同一组, 或使数据更接近访问者. 迁移期间客户端操作可继续执行; 一个 50 MB 的 directory 通常可在几秒内迁完.

Figure 3: Directories are the unit of data movement between Paxos groups.

图 3: Directory 是 Paxos 组之间的数据迁移单位.

The fact that a Paxos group may contain multiple directories implies that a Spanner tablet is different from a Bigtable tablet: the former is not necessarily a single lexicographically contiguous partition of the row space. Instead, a Spanner tablet is a container that may encapsulate multiple partitions of the row space. We made this decision so that it would be possible to colocate multiple directories that are frequently accessed together.

一个 Paxos 组可包含多个 directory, 这意味着 Spanner tablet 与 Bigtable tablet 不同: 它不一定对应行空间中一个按字典序连续的分区, 而是可以容纳多个分区. 这一设计使经常一起访问的多个 directory 能够放在同一位置.

Movedir is the background task used to move directories between Paxos groups [14]. Movedir is also used to add or remove replicas to Paxos groups [25], because Spanner does not yet support in-Paxos configuration changes. Movedir is not implemented as a single transaction, so as to avoid blocking ongoing reads and writes on a bulky data move. Instead, movedir registers the fact that it is starting to move data and moves the data in the background. When it has moved all but a nominal amount of the data, it uses a transaction to atomically move that nominal amount and update the metadata for the two Paxos groups.

Movedir 是在 Paxos 组之间迁移 directory 的后台任务 [14]. 因为 Spanner 尚不支持在 Paxos 协议内部变更配置, 它也用于给 Paxos 组添加或移除副本 [25]. 为避免大规模数据迁移阻塞读写, movedir 不作为单个事务执行. 它先登记迁移开始, 再在后台搬运数据; 只剩少量数据时, 才用一个事务原子地迁移余下数据并更新两个 Paxos 组的元数据.

A directory is also the smallest unit whose geographic-replication properties (or placement, for short) can be specified by an application. The design of our placement-specification language separates responsibilities for managing replication configurations. Administrators control two dimensions: the number and types of replicas, and the geographic placement of those replicas. They create a menu of named options in these two dimensions (e.g. North America, replicated 5 ways with 1 witness). An application controls how data is replicated, by tagging each database and/or individual directories with a combination of those options. For example, an application might store each end-user's data in its own directory, which would enable user A's data to have three replicas in Europe, and user B's data to have five replicas in North America.

Directory 也是应用能够指定地理复制属性, 简称 placement, 的最小单位. 我们的放置描述语言将复制配置管理职责分开: 管理员控制副本的数量与类型, 以及地理位置, 为这两个维度提供一组命名选项, 例如在北美部署 5 个副本, 其中 1 个为仲裁副本 (witness). 应用为数据库或各个 directory 标注选项组合, 决定数据如何复制. 例如, 每个终端用户的数据分别存入一个 directory, 就可以为用户 A 在欧洲保留 3 个副本, 为用户 B 在北美保留 5 个副本.

For expository clarity we have over-simplified. In fact, Spanner will shard a directory into multiple fragments if it grows too large. Fragments may be served from different Paxos groups (and therefore different servers). Movedir actually moves fragments, and not whole directories, between groups.

为便于说明, 前面的描述有所简化. 实际上, directory 过大时, Spanner 会把它拆成多个 fragment (片段), 可由不同 Paxos 组, 也就是不同服务器提供服务. Movedir 在组间迁移的实际单位是 fragment, 而非整个 directory.

2.3 数据模型

Spanner exposes the following set of data features to applications: a data model based on schematized semi-relational tables, a query language, and general-purpose transactions. The move towards supporting these features was driven by many factors. The need to support schematized semi-relational tables and synchronous replication is supported by the popularity of Megastore [5]. At least 300 applications within Google use Megastore (despite its relatively low performance) because its data model is simpler to manage than Bigtable's, and because of its support for synchronous replication across datacenters. (Bigtable only supports eventually-consistent replication across datacenters.) Examples of well-known Google applications that use Megastore are Gmail, Picasa, Calendar, Android Market, and AppEngine. The need to support a SQL-like query language in Spanner was also clear, given the popularity of Dremel [28] as an interactive data-analysis tool. Finally, the lack of cross-row transactions in Bigtable led to frequent complaints; Percolator [32] was in part built to address this failing. Some authors have claimed that general two-phase commit is too expensive to support, because of the performance or availability problems that it brings [9, 10, 19]. We believe it is better to have application programmers deal with performance problems due to overuse of transactions as bottlenecks arise, rather than always coding around the lack of transactions. Running two-phase commit over Paxos mitigates the availability problems.

Spanner 向应用提供基于显式模式的半关系表, 查询语言和通用事务. 支持这些功能有多方面原因. Megastore [5] 的普及说明了半关系表和同步复制的需求: 尽管性能相对较低, Google 仍有至少 300 个应用使用它, 因为它的数据模型比 Bigtable 更易管理, 并支持跨数据中心同步复制; Bigtable 只支持跨数据中心最终一致复制. Gmail, Picasa, Calendar, Android Market 和 AppEngine 都是其知名用户. Dremel [28] 作为交互式分析工具的普及, 也说明了类 SQL 查询语言的必要性. 此外, Bigtable 缺少跨行事务一直受到用户抱怨, Percolator [32] 就部分源于这一需求. 一些研究者认为通用两阶段提交的性能或可用性代价太高 [9, 10, 19]. 我们认为, 与其要求开发者始终绕过事务缺失带来的限制, 不如让他们在过度使用事务确实造成瓶颈后再处理性能问题. 在 Paxos 之上执行两阶段提交, 也能缓解可用性问题.

The application data model is layered on top of the directory-bucketed key-value mappings supported by the implementation. An application creates one or more databases in a universe. Each database can contain an unlimited number of schematized tables. Tables look like relational-database tables, with rows, columns, and versioned values. We will not go into detail about the query language for Spanner. It looks like SQL with some extensions to support protocol-buffer-valued fields.

面向应用的数据模型建立在按 directory 分桶的键值映射之上. 应用在一个 universe 中创建一个或多个数据库, 每个数据库可包含不限数量的有模式表. 表与关系数据库相似, 包含行, 列和多版本值. 本文不展开查询语言细节; 它类似 SQL, 并扩展支持以 protocol buffer 为值的字段.

Spanner's data model is not purely relational, in that rows must have names. More precisely, every table is required to have an ordered set of one or more primary-key columns. This requirement is where Spanner still looks like a key-value store: the primary keys form the name for a row, and each table defines a mapping from the primary-key columns to the non-primary-key columns. A row has existence only if some value (even if it is NULL) is defined for the row's keys. Imposing this structure is useful because it lets applications control data locality through their choices of keys.

Spanner 的模型并非纯关系模型, 因为行必须具有名称. 更准确地说, 每张表都必须指定由一列或多列组成的有序主键. 这一点仍类似键值存储: 主键构成行名, 每张表定义从主键列到非主键列的映射. 只有为一组行键定义了某个值, 即使值为 NULL, 该行才存在. 这样的结构约束使应用能通过选键控制数据局部性.

Client applications declare the hierarchies in database schemas via the INTERLEAVE IN declarations. The table at the top of a hierarchy is a directory table. The underlying time references used by TrueTime are GPS and atomic clocks. TrueTime uses two forms of time reference because they have different failure modes. GPS reference-source vulnerabilities include antenna and receiver failures, local radio interference, correlated failures (e.g. design faults such as incorrect leap-second handling and spoofing), and GPS system outages. Atomic clocks can fail in ways uncorrelated to GPS and each other, and over long periods of time can drift significantly due to frequency error.

TrueTime 底层使用 GPS 和原子钟作为时间基准, 因为两者的故障模式不同. GPS 的薄弱点包括天线和接收器故障, 本地无线电干扰, 相关性故障 (例如闰秒处理错误等设计缺陷以及欺骗攻击), 还有 GPS 系统中断. 原子钟可能发生与 GPS 及其他原子钟无关的故障, 并可能因频率误差在较长时间内产生明显漂移.

TrueTime is implemented by a set of time master machines per datacenter and a timeslave daemon per machine. The majority of masters have GPS receivers with dedicated antennas; these masters are separated physically to reduce the effects of antenna failures, radio interference, and spoofing. The remaining masters (which we refer to as Armageddon masters) are equipped with atomic clocks. An atomic clock is not that expensive: the cost of an Armageddon master is of the same order as that of a GPS master. All masters' time references are regularly compared against each other. Each master also cross-checks the rate at which its reference advances time against its own local clock, and evicts itself if there is substantial divergence. Between synchronizations, Armageddon masters advertise a slowly increasing time uncertainty that is derived from conservatively applied worst-case clock drift. GPS masters advertise uncertainty that is typically close to zero.

每个数据中心部署一组时间主服务器 (time master), 每台机器运行一个 timeslave 守护进程, 共同实现 TrueTime. 多数主服务器配备带独立天线的 GPS 接收器, 并在物理上分散放置, 减少天线故障, 无线电干扰和欺骗攻击的影响. 其余主服务器配备原子钟, 我们称之为 Armageddon master. 原子钟并没有那么昂贵, 这类服务器的成本与 GPS 主服务器处于同一数量级. 所有主服务器定期相互比较时间基准, 还将基准的时间推进速率与本地时钟交叉核对, 偏差过大时将自身移出服务. 两次同步之间, Armageddon master 根据保守采用的最坏时钟漂移, 报告缓慢增大的不确定性; GPS 主服务器报告的不确定性通常接近零.

Every daemon polls a variety of masters [29] to reduce vulnerability to errors from any one master. Some are GPS masters chosen from nearby datacenters; the rest are GPS masters from farther datacenters, as well as some Armageddon masters. Daemons apply a variant of Marzullo's algorithm [27] to detect and reject liars, and synchronize the local machine clocks to the non-liars. To protect against broken local clocks, machines that exhibit frequency excursions larger than the worst-case bound derived from component specifications and operating environment are evicted.

每个守护进程轮询多个主服务器 [29], 降低单个主服务器出错的影响. 其中一些是附近数据中心的 GPS 主服务器, 另一些来自较远数据中心, 还包括部分 Armageddon master. 守护进程使用 Marzullo 算法 [27] 的变体识别并排除错误时间源, 再依据其余时间源同步本地时钟. 为防范本地时钟故障, 如果机器的频率偏离超过由器件规格和运行环境确定的最坏边界, 就会将其移出服务.

Between synchronizations, a daemon advertises a slowly increasing time uncertainty. ε is derived from conservatively applied worst-case local clock drift. ε also depends on time-master uncertainty and communication delay to the time masters. In our production environment, ε is typically a sawtooth function of time, varying from about 1 to 7 ms over each poll interval. ε̄ is therefore 4 ms most of the time. The daemon's poll interval is currently 30 seconds, and the current applied drift rate is set at 200 microseconds/second, which together account for the sawtooth bounds from 0 to 6 ms. The remaining 1 ms comes from the communication delay to the time masters. Excursions from this sawtooth are possible in the presence of failures. For example, occasional time-master unavailability can cause datacenter-wide increases in ε. Similarly, overloaded machines and network links can result in occasional localized ε spikes.

两次同步之间, 守护进程报告的不确定性缓慢增加. ε 根据保守采用的最坏本地时钟漂移计算, 同时取决于主服务器自身的不确定性和通信延迟. 在生产环境中, ε 通常呈锯齿形变化, 每个轮询周期内从约 1 ms 增长到 7 ms, 因而多数情况下 ε̄ 为 4 ms. 当前轮询间隔为 30 秒, 采用的漂移速率为每秒 200 微秒, 两者对应 0-6 ms 的锯齿幅度; 余下约 1 ms 来自与主服务器的通信延迟. 故障时可能偏离这一模式: 主服务器偶尔不可用会使整个数据中心的 ε 增大, 机器或链路过载则会产生局部尖峰.

4. 并发控制

This section describes how TrueTime is used to guarantee the correctness properties around concurrency control, and how those properties are used to implement features such as externally consistent transactions, lock-free read-only transactions, and non-blocking reads in the past. These features enable, for example, the guarantee that a whole-database audit read at a timestamp t will see exactly the effects of every transaction that has committed as of t.

本节介绍如何用 TrueTime 保证并发控制的正确性, 以及如何据此实现具有外部一致性的事务, 无锁只读事务和不阻塞的历史读取. 例如, 在时间戳 t 上审计整个数据库时, 能保证恰好看到截至 t 已提交的所有事务的效果.

Going forward, it will be important to distinguish writes as seen by Paxos (which we will refer to as Paxos writes unless the context is clear) from Spanner client writes. For example, two-phase commit generates a Paxos write for the prepare phase that has no corresponding Spanner client write.

下面需要区分 Paxos 所看到的写入与 Spanner 客户端写入; 除非上下文明确, 前者称为 Paxos 写入. 例如, 两阶段提交的准备阶段会产生一次 Paxos 写入, 却没有对应的 Spanner 客户端写入.

A read-only transaction is a kind of transaction that has the performance benefits of snapshot isolation [6]. A read-only transaction must be predeclared as not having any writes; it is not simply a read-write transaction without any writes. Reads in a read-only transaction execute at a system-chosen timestamp without locking, so that incoming writes are not blocked. The execution of the reads in a read-only transaction can proceed on any replica that is sufficiently up-to-date (Section 4.1.3).

只读事务具有快照隔离 [6] 的性能优势, 但必须预先声明不会写入, 而不是一个恰好没有写入的读写事务. 其中所有读取都在系统选定的时间戳上执行, 无需加锁, 因而不阻塞新写入. 读取可在任意足够新的副本上执行, 详见原文第 4.1.3 节.

A snapshot read is a read in the past that executes without locking. A client can either specify a timestamp for a snapshot read, or provide an upper bound on the desired timestamp's staleness and let Spanner choose a timestamp. In either case, the execution of a snapshot read proceeds at any replica that is sufficiently up-to-date.

快照读取是在历史时间点上执行的无锁读取. 客户端可以直接指定时间戳, 也可以给出数据陈旧程度的上限, 让 Spanner 选择时间戳. 两种情况下, 都可以从任意足够新的副本读取.

For both read-only transactions and snapshot reads, commit is inevitable once a timestamp has been chosen, unless the data at that timestamp has been garbage-collected. As a result, clients can avoid buffering results inside a retry loop. When a server fails, clients can internally continue the query on a different server by repeating the timestamp and the current read position.

无论只读事务还是快照读取, 一旦选定时间戳, 只要该时间点的数据尚未被垃圾回收, 就一定能提交. 因而客户端无需在重试循环中缓冲结果. 服务器故障时, 客户端内部只需带上相同时间戳和当前读取位置, 就能在另一台服务器继续查询.

4.1.1 Paxos Leader 租约

Spanner's Paxos implementation uses timed leases to make leadership long-lived (10 seconds by default). A potential leader sends requests for timed lease votes; upon receiving a quorum of lease votes the leader knows it has a lease. A replica extends its lease vote implicitly on a successful write, and the leader requests lease-vote extensions if they are near expiration. Define a leader's lease interval as starting when it discovers it has a quorum of lease votes, and as ending when it no longer has a quorum of lease votes (because some have expired). Spanner depends on the following disjointness invariant: for each Paxos group, each Paxos leader's lease interval is disjoint from every other leader's. Appendix A describes how this invariant is enforced.

Spanner 的 Paxos 实现通过默认 10 秒的时间租约维持长期 leader. 候选 leader 请求副本为租约投票, 收到法定多数票后即确认拥有租约. 成功写入会隐式延长副本的租约投票; 临近到期时, leader 也会主动请求续期. Leader 的租约区间从它确认获得法定多数票开始, 到因部分投票到期而不再拥有法定多数票结束. Spanner 依赖如下不相交不变量: 同一 Paxos 组中, 任意两个 leader 的租约区间不重叠. 附录 A 说明如何保证这一点.

The Spanner implementation permits a Paxos leader to abdicate by releasing its slaves from their lease votes. To preserve the disjointness invariant, Spanner constrains when abdication is permissible. Define smax to be the maximum timestamp used by a leader. Subsequent sections will describe when smax is advanced. Before abdicating, a leader must wait until TT.after(smax) is true.

Spanner 允许 leader 通过解除从副本的租约投票来主动退位. 为维持租约区间不相交, 退位时机受到限制. 记 leader 已使用的最大时间戳为 smax, 后文将说明何时推进它. 退位前, leader 必须等到 TT.after(s_max) 为 true.

4.1.2 为读写事务分配时间戳

Transactional reads and writes use two-phase locking. As a result, they can be assigned timestamps at any time when all locks have been acquired, but before any locks have been released. For a given transaction, Spanner assigns it the timestamp that Paxos assigns to the Paxos write that represents the transaction commit.

事务性读写使用两阶段锁, 因而可以在取得全部锁之后, 释放任何锁之前的任意时刻分配时间戳. Spanner 将表示事务提交的那次 Paxos 写入的时间戳, 作为该事务的时间戳.

Spanner depends on the following monotonicity invariant: within each Paxos group, Spanner assigns timestamps to Paxos writes in monotonically increasing order, even across leaders. A single leader replica can trivially assign timestamps in monotonically increasing order. This invariant is enforced across leaders by making use of the disjointness invariant: a leader must only assign timestamps within the interval of its leader lease. Note that whenever a timestamp s is assigned, smax is advanced to s to preserve disjointness.

Spanner 依赖单调性不变量: 同一 Paxos 组内, Paxos 写入的时间戳单调递增, 即使 leader 发生切换也不例外. 单个 leader 很容易维持递增; 跨 leader 则利用租约区间不相交来保证, 即 leader 只能分配落在自身租约区间内的时间戳. 每次分配 s 时, 都将 smax 推进到 s, 以维持不相交性.

Spanner also enforces the following external-consistency invariant: if the start of a transaction T2 occurs after the commit of a transaction T1, then the commit timestamp of T2 must be greater than the commit timestamp of T1. Define the start and commit events for a transaction Ti by eistart and eicommit; and the commit timestamp of a transaction Ti by si. The invariant becomes tabs(e1commit) < tabs(e2start) ⇒ s1 < s2. The protocol for executing transactions and assigning timestamps obeys two rules, which together guarantee this invariant, as shown below. Define the arrival event of the commit request at the coordinator leader for a write Ti to be eiserver.

Spanner 还保证外部一致性不变量: 如果 T2 在 T1 提交之后才开始, 则 T2 的提交时间戳必须更大. 用 eistart 和 eicommit 表示 Ti 的开始与提交事件, si 表示其提交时间戳, 则要求 tabs(e1commit) < tabs(e2start) ⇒ s1 < s2. 事务执行和时间戳分配协议遵循下面两条规则, 二者共同保证这一性质. 将写事务 Ti 的提交请求到达协调者 leader 的事件记为 eiserver.

Start. The coordinator leader for a write Ti assigns a commit timestamp si no less than the value of TT.now().latest, computed after eiserver. Note that the participant leaders do not matter here; Section 4.2.1 describes how they are involved in the implementation of the next rule.

开始. 协调者 leader 在 eiserver 之后调用 TT.now().latest, 为写事务 Ti 选择不小于该值的提交时间戳 si. 这里不涉及参与者 leader; 原文第 4.2.1 节会说明它们如何参与下一条规则的实现.

Commit Wait. The coordinator leader ensures that clients cannot see any data committed by Ti until TT.after(s_i) is true. Commit wait ensures that si is less than the absolute commit time of Ti, or si < tabs(eicommit). The implementation of commit wait is described in Section 4.2.1. Proof:

提交等待. 协调者 leader 保证, 在 TT.after(s_i) 为 true 之前, 客户端看不到 Ti 提交的任何数据. 因而 si 小于事务的绝对提交时间, 即 si < tabs(eicommit). 实现详见原文第 4.2.1 节. 证明如下:

s1 < tabs(e1commit)   (commit wait)(提交等待)

tabs(e1commit) < tabs(e2start)   (assumption)(假设)

tabs(e2start) ≤ tabs(e2server)   (causality)(因果关系)

tabs(e2server) ≤ s2   (start)(开始规则)

s1 < s2   (transitivity)(传递性)

4.1.3 按时间戳提供读取

The monotonicity invariant described in Section 4.1.2 allows Spanner to correctly determine whether a replica's state is sufficiently up-to-date to satisfy a read. Every replica tracks a value called safe time tsafe which is the maximum timestamp at which a replica is up-to-date. A replica can satisfy a read at a timestamp t if t ≤ tsafe.

原文第 4.1.2 节的单调性不变量, 使 Spanner 能正确判断副本是否足够新, 可以满足某次读取. 每个副本跟踪安全时间 tsafe, 即其状态已经追上的最大时间戳. 当 t ≤ tsafe 时, 副本可提供时间戳 t 的读取.

Define tsafe = min(tsafePaxos, tsafeTM), where each Paxos state machine has a safe time tsafePaxos and each transaction manager has a safe time tsafeTM. tsafePaxos is simpler: it is the timestamp of the highest-applied Paxos write. Because timestamps increase monotonically and writes are applied in order, writes will no longer occur at or below tsafePaxos with respect to Paxos.

定义 tsafe = min(tsafePaxos, tsafeTM), 两项分别是 Paxos 状态机和事务管理器的安全时间. 前者较简单, 就是已应用的 Paxos 写入中的最大时间戳. 因为时间戳单调递增, 写入按顺序应用, 所以 Paxos 层不会再出现时间戳小于或等于该值的新写入.

tsafeTM is ∞ at a replica if there are zero prepared (but not committed) transactions--that is, transactions in between the two phases of two-phase commit. (For a participant slave, tsafeTM actually refers to the replica's leader's transaction manager, whose state the slave can infer through metadata passed on Paxos writes.) If there are any such transactions, then the state affected by those transactions is indeterminate: a participant replica does not know yet whether such transactions will commit. As we discuss in Section 4.2.1, the commit protocol ensures that every participant knows a lower bound on a prepared transaction's timestamp. Every participant leader (for a group g) for a transaction Ti assigns a prepare timestamp si, gprepare to its prepare record. The coordinator leader ensures that the transaction's commit timestamp si ≥ si, gprepare over all participant groups g. Therefore, for every replica in a group g, over all transactions Ti prepared at g, tsafeTM = mini(si, gprepare) - 1 over all transactions prepared at g.

如果副本没有已准备但尚未提交的事务, 即没有处于两阶段提交两个阶段之间的事务, 则 tsafeTM 为 ∞. 对参与者从副本而言, 这里实际指其 leader 的事务管理器状态, 可从 Paxos 写入携带的元数据推断. 若存在这类事务, 其影响的状态尚未确定, 因为参与副本还不知道事务是否会提交. 如原文第 4.2.1 节所述, 提交协议让每个参与者知道已准备事务时间戳的下界: 组 g 的参与者 leader 为事务 Ti 的准备记录分配准备时间戳 si, gprepare, 协调者确保提交时间戳 si 不小于所有参与组的准备时间戳. 因而, 对组 g 的每个副本, 在该组全部已准备事务上取最小值, 有 tsafeTM = mini(si, gprepare) - 1.

4.1.4 为只读事务分配时间戳

A read-only transaction executes in two phases: assign a timestamp sread [8], and then execute the transaction's reads as snapshot reads at sread. The snapshot reads can execute at any replicas that are sufficiently up-to-date.

只读事务分两个阶段: 先分配时间戳 sread [8], 再将事务内的所有读取作为该时间戳上的快照读取执行. 快照读取可在任意足够新的副本上完成.

The simple assignment of sread = TT.now().latest, at any time after a transaction starts, preserves external consistency by an argument analogous to that presented for writes in Section 4.1.2. However, such a timestamp may require the execution of the data reads at sread to block if tsafe has not advanced sufficiently. (In addition, note that choosing a value of sread may also advance smax to preserve disjointness.) To reduce the chances of blocking, Spanner should assign the oldest timestamp that preserves external consistency. Section 4.2.2 explains how such a timestamp can be chosen.

最简单的办法是在事务开始后的任意时刻令 sread = TT.now().latest. 按照与原文第 4.1.2 节写入证明类似的论证, 这样满足外部一致性. 但如果 tsafe 尚未推进到该值, 读取就可能阻塞. 此外, 为维持租约不相交, 选择 sread 也可能需要推进 smax. 为减少阻塞, 应选择仍满足外部一致性的最早时间戳, 具体方法见原文第 4.2.2 节.

4.2 实现细节

This section explains some of the practical details of read-write transactions and read-only transactions elided earlier, as well as the implementation of a special transaction type used to implement atomic schema changes. It then describes some refinements of the basic schemes as described.

本节补充前文省略的读写事务和只读事务实现细节, 介绍用于原子模式变更的特殊事务, 并说明基本方案的一些改进.

4.2.1 读写事务

Like Bigtable, writes that occur in a transaction are buffered at the client until commit. As a result, reads in a transaction do not see the effects of the transaction's writes. This design works well in Spanner because a read returns the timestamps of any data read, and uncommitted writes have not yet been assigned timestamps.

与 Bigtable 一样, 事务中的写入先缓存在客户端, 直到提交才发出. 因而, 事务内的读取看不到该事务自身尚未提交的写入. 这一设计适合 Spanner, 因为读取会返回数据的时间戳, 而未提交写入尚未分配时间戳.

Reads within read-write transactions use wound-wait [33] to avoid deadlocks. The client issues reads to the leader replica of the appropriate group, which acquires read locks and then reads the most recent data. While a client transaction remains open, it sends keepalive messages to prevent participant leaders from timing out its transaction. When a client has completed all reads and buffered all writes, it begins two-phase commit. The client chooses a coordinator group and sends a commit message to each participant's leader with the identity of the coordinator and any buffered writes. Having the client drive two-phase commit avoids sending data twice across wide-area links.

读写事务中的读取使用 wound-wait [33] 避免死锁. 客户端向相应组的 leader 发起读取, leader 获取读锁后读取最新数据. 事务保持打开期间, 客户端发送保活消息, 防止参与者 leader 将事务判为超时. 完成全部读取并缓冲好全部写入后, 客户端开始两阶段提交: 选择协调者组, 向每个参与者 leader 发送提交消息, 携带协调者身份及相应的缓冲写入. 由客户端驱动两阶段提交, 可以避免数据在广域链路上发送两遍.

A non-coordinator-participant leader first acquires write locks. It then chooses a prepare timestamp that must be larger than any timestamps it has assigned to previous transactions (to preserve monotonicity), and logs a prepare record through Paxos. Each participant then notifies the coordinator of its prepare timestamp.

非协调者的参与者 leader 首先取得写锁, 再选择准备时间戳. 为维持单调性, 该值必须大于它此前为事务分配的所有时间戳. 随后通过 Paxos 记录准备日志, 并将准备时间戳通知协调者.

The coordinator leader also first acquires write locks, but skips the prepare phase. It chooses a timestamp for the entire transaction after hearing from all other participant leaders. The commit timestamp s must be greater or equal to all prepare timestamps (to satisfy the constraints discussed in Section 4.1.3), greater than TT.now().latest at the time the coordinator received its commit message, and greater than any timestamps the leader has assigned to previous transactions (again, to preserve monotonicity). The coordinator leader then logs a commit record through Paxos (or an abort if it timed out while waiting on the other participants).

协调者 leader 同样先取得写锁, 但跳过准备阶段. 收到所有其他参与者 leader 的回复后, 它为整个事务选择提交时间戳 s. 这个值必须不小于所有准备时间戳 (满足原文第 4.1.3 节的约束), 大于协调者收到提交消息时的 TT.now().latest, 也大于该 leader 之前分配的所有事务时间戳 (保持单调性). 接着, 协调者通过 Paxos 记录提交日志; 如果等待其他参与者超时, 则记录中止日志.

Before allowing any coordinator replica to apply the commit record, the coordinator leader waits until TT.after(s), so as to obey the commit-wait rule described in Section 4.1.2. Because the coordinator leader chose s based on TT.now().latest, and now waits until that timestamp is guaranteed to be in the past, the expected wait is at least 2 × ε̄. This wait is typically overlapped with Paxos communication. After commit wait, the coordinator sends the commit timestamp to the client and all other participant leaders. Each participant leader logs the transaction's outcome through Paxos. All participants apply at the same timestamp and then release locks.

按照原文第 4.1.2 节的提交等待规则, 协调者 leader 必须等到 TT.after(s) 为 true, 才允许协调者组的任何副本应用提交记录. 因为 s 根据 TT.now().latest 选择, 又要等到能确定 s 已经过去, 预期等待至少为 2ε̄. 这段等待通常与 Paxos 通信重叠. 等待结束后, 协调者将提交时间戳发送给客户端和其他参与者 leader. 各参与者再通过 Paxos 记录事务结果, 全部参与者在同一时间戳应用更新, 然后释放锁.

4.2.2 只读事务

Assigning a timestamp requires a negotiation phase between all of the Paxos groups that are involved in the reads. As a result, Spanner requires a scope expression for every read-only transaction, which is an expression that summarizes the keys that will be read by the entire transaction. Spanner automatically infers the scope for standalone queries.

分配时间戳需要读取所涉及的各 Paxos 组参与协商. 因而, Spanner 要求每个只读事务提供范围表达式 (scope expression), 概括整个事务将读取哪些键. 对独立查询, 系统会自动推断范围.

If the scope's values are served by a single Paxos group, then the client issues the read-only transaction to that group's leader. (The current Spanner implementation only chooses a timestamp for a read-only transaction at a Paxos leader.) That leader assigns sread and executes the read. For a single-site read, Spanner generally does better than TT.now().latest. Define LastTS() to be the timestamp of the last committed write at a Paxos group. If there are no prepared transactions, the assignment sread = LastTS() trivially satisfies external consistency: the transaction will see the result of the last write, and therefore be ordered after it.

如果范围内的数据由单个 Paxos 组提供, 客户端就将只读事务发往该组 leader. 当前实现只在 Paxos leader 上为只读事务选择时间戳, 由 leader 分配 sread 并执行读取. 对单组读取, Spanner 通常能选择比 TT.now().latest 更合适的值. 记 LastTS() 为该组最后一次已提交写入的时间戳. 若没有已准备事务, 令 sread = LastTS() 就能满足外部一致性: 读取会看到最后一次写入的结果, 因而在顺序上位于它之后.

If the scope's values are served by multiple Paxos groups, there are several options. The most complicated option is to do a round of communication with all of the groups's leaders to negotiate sread based on LastTS(). Spanner currently implements a simpler choice. The client avoids a negotiation round, and just has its reads execute at sread = TT.now().latest (which may wait for safe time to advance). All reads in the transaction can be sent to replicas that are sufficiently up-to-date.

如果数据由多个 Paxos 组提供, 则有几种选择. 最复杂的方式是与所有组的 leader 通信一轮, 根据 LastTS() 协商 sread. 当前 Spanner 采用更简单的方案: 客户端省去协商, 直接在 sread = TT.now().latest 上执行读取, 必要时等待安全时间推进. 事务中的全部读取都可以发送给足够新的副本.

4.2.3 模式变更事务

TrueTime enables Spanner to support atomic schema changes. It would be infeasible to use a standard transaction, because the number of participants (the number of groups in a database) could be in the millions. Bigtable supports atomic schema changes in one datacenter, but its schema changes block all operations.

TrueTime 使 Spanner 能够支持原子模式变更. 用普通事务实现并不可行, 因为参与者数量, 即数据库中的 Paxos 组数, 可能达到数百万. Bigtable 支持单个数据中心内的原子模式变更, 但会阻塞所有操作.

A Spanner schema-change transaction is a generally non-blocking variant of a standard transaction. First, it is explicitly assigned a timestamp in the future, which is registered in the prepare phase. As a result, schema changes across thousands of servers can complete with minimal disruption to other concurrent activity. Second, reads and writes, which implicitly depend on the schema, synchronize with any registered schema-change timestamp at time t: they may proceed if their timestamps precede t, but they must block behind the schema-change transaction if their timestamps are after t. Without TrueTime, defining the schema change to happen at t would be meaningless.

Spanner 的模式变更事务是普通事务的一种通常不阻塞操作的变体. 首先, 它显式选择一个未来时间戳, 并在准备阶段登记. 这样, 跨数千台服务器的模式变更只会对其他并发操作造成很小干扰. 其次, 隐式依赖模式的读写要与已登记的模式变更时间戳 t 同步: 时间戳早于 t 的操作可以继续, 晚于 t 的操作则必须等待模式变更事务完成. 如果没有 TrueTime, 将模式变更定义为在 t 发生就没有明确意义.

4.2.4 进一步优化

tsafeTM as defined above has a weakness, in that a single prepared transaction prevents tsafe from advancing. As a result, no reads can occur at later timestamps, even if the reads do not conflict with the transaction. Such false conflicts can be removed by augmenting tsafeTM with a fine-grained mapping from key ranges to prepared-transaction timestamps. This information can be stored in the lock table, which already maps key ranges to lock metadata. When a read arrives, it only needs to be checked against the fine-grained safe time for key ranges with which the read conflicts.

前面定义的 tsafeTM 有一个弱点: 单个已准备事务就会阻止 tsafe 推进, 使更晚时间戳上的全部读取都无法执行, 即使读取与该事务并不冲突. 可以增加从键范围到已准备事务时间戳的细粒度映射, 消除这些虚假冲突. 锁表本来就将键范围映射到锁元数据, 因而可以保存这些信息. 新读取只需检查与自己冲突的键范围所对应的细粒度安全时间.

LastTS() as defined above has a similar weakness: if a transaction has just committed, a non-conflicting read-only transaction must still be assigned sread so as to follow that transaction. As a result, the execution of the read could be delayed. This weakness can be remedied similarly by augmenting LastTS() with a fine-grained mapping from key ranges to commit timestamps in the lock table. (We have not yet implemented this optimization.) When a read-only transaction arrives, its timestamp can be assigned by taking the maximum value of LastTS() for the key ranges with which the transaction conflicts, unless there is a conflicting prepared transaction (which can be determined from fine-grained safe time).

LastTS() 也有类似问题: 某事务刚提交后, 即使后来的只读事务与它不冲突, 分配的 sread 也必须排在它之后, 从而可能延迟读取. 同样可以在锁表中增加从键范围到提交时间戳的细粒度映射来解决, 但我们尚未实现这一优化. 只读事务到来时, 如果没有冲突的已准备事务, 就可以取其涉及键范围的 LastTS() 最大值作为时间戳; 是否存在冲突的已准备事务, 可由细粒度安全时间判断.

tsafePaxos as defined above has a weakness in that it cannot advance in the absence of Paxos writes. That is, a snapshot read at t cannot execute at Paxos groups whose last write happened before t. Spanner addresses this problem by taking advantage of the disjointness of leader-lease intervals. Each Paxos leader advances tsafePaxos by keeping a threshold above which future writes' timestamps will occur: it maintains a mapping MinNextTS(n) from Paxos sequence number n to the minimum timestamp that may be assigned to Paxos sequence number n + 1. A replica can advance tsafePaxos to MinNextTS(n) - 1 when it has applied through n.

前面定义的 tsafePaxos 在没有 Paxos 写入时无法推进. 因而, 若某组最后一次写入早于 t, 就不能在该组执行时间戳为 t 的快照读取. Spanner 利用 leader 租约区间不相交来解决. 每个 leader 维护未来写入时间戳的下界, 借此推进安全时间: MinNextTS(n) 将 Paxos 序号 n 映射到序号 n + 1 可使用的最小时间戳. 副本应用完截至 n 的所有写入后, 可以将 tsafePaxos 推进到 MinNextTS(n) - 1.

A single leader can enforce its MinNextTS() promises easily. Because the timestamps promised by MinNextTS() lie within a leader's lease, the disjointness invariant enforces MinNextTS() promises across leaders. If a leader wishes to advance MinNextTS() beyond the end of its leader lease, it must first extend its lease. Note that smax is always advanced to the highest value in MinNextTS() to preserve disjointness.

单个 leader 很容易兑现 MinNextTS() 的承诺. 由于承诺的时间戳位于其租约内, 不相交不变量又保证该承诺跨 leader 切换仍成立. 若想将 MinNextTS() 推进到当前租约终点之后, leader 必须先续租. 为维持不相交性, smax 始终要推进到 MinNextTS() 中的最大值.

A leader by default advances MinNextTS() values every 8 seconds. Thus, in the absence of prepared transactions, healthy slaves in an idle Paxos group can serve reads at timestamps greater than 8 seconds old in the worst case. A leader may also advance MinNextTS() values on demand from slaves.

默认情况下, leader 每 8 秒推进一次 MinNextTS(). 因而, 没有已准备事务时, 即使在最坏情况下, 空闲 Paxos 组中的健康从副本也能提供距当前超过 8 秒的历史读取. Leader 还可以应从副本请求按需推进该值.

延迟测试中, 客户端只发出少量操作, 避免服务器排队. 从单副本结果可见, 提交等待约为 5 ms, Paxos 延迟约为 9 ms. 副本数增加时, 延迟基本不变, 标准差反而减小, 因为 Paxos 在各副本上并行执行, 获得法定多数响应所需的时间对单个慢从副本也不那么敏感.

For the throughput experiments, clients issued sufficiently many operations so as to saturate the servers' CPUs. Snapshot reads can execute at any up-to-date replicas, so their throughput increases almost linearly with the number of replicas. Single-read read-only transactions only execute at leaders because timestamp assignment must happen at leaders. Read-only-transaction throughput increases with the number of replicas because the number of effective spanservers increases: in the experimental setup, the number of spanservers equaled the number of replicas, and leaders were randomly distributed among the zones. Write throughput benefits from the same experimental artifact (which explains the increase in throughput from 3 to 5 replicas), but that benefit is outweighed by the linear increase in the amount of work performed per write, as the number of replicas increases.

吞吐量测试中, 客户端发出足够多的操作以用满服务器 CPU. 快照读取可由任意足够新的副本执行, 所以吞吐量随副本数近似线性增长. 只包含一次读取的只读事务只能在 leader 上执行, 因为时间戳必须由 leader 分配. 它的吞吐量也随副本数增加, 原因是实际参与服务的 spanserver 数量增加了: 实验中 spanserver 数等于副本数, 各组 leader 随机分布在不同 zone. 写吞吐量也受益于这一实验配置, 解释了从 3 副本到 5 副本时的增长. 但总体而言, 副本越多, 每次写入的工作量也线性增加, 这一代价超过了上述收益.

终止 Z2 对读吞吐量没有影响. 终止 Z1 前若允许 leader 移交到其他 zone, 影响也很小, 吞吐量仅下降约 3%-4%, 图中几乎看不出来. 如果毫无预警地终止 Z1, 完成速率则几乎降到零. 随着新 leader 陆续选出, 吞吐量升至每秒约 10 万次读取. 这是由实验中的两个因素造成的: 系统还有额外容量, 而 leader 不可用期间请求会排队. 因而系统会先以较高吞吐量处理积压, 再回到稳态速率.

We can also see the effect of the fact that Paxos leader leases are set to 10 seconds. When we kill the zone, the leader-lease expiration times for the groups should be evenly distributed over the next 10 seconds. 5.3 TrueTime

Two questions must be answered with respect to TrueTime: is ε truly a bound on clock uncertainty, and how bad does ε get? For the former, the most serious problem would be if a local clock's drift were greater than 200us/sec: that would break assumptions made by TrueTime. Our machine statistics show that bad CPUs are 6 times more likely than bad clocks. That is, clock issues are extremely infrequent, relative to much more serious hardware problems. As a result, we believe that TrueTime's implementation is as trustworthy as any other piece of software upon which Spanner depends.

关于 TrueTime, 需要回答两个问题: ε 是否确实界定了时钟不确定性, 以及 ε 最坏会有多大. 对前者, 最严重的情况是本地时钟漂移超过每秒 200 微秒, 从而破坏 TrueTime 的假设. 机器统计表明, CPU 故障发生的可能性是时钟故障的 6 倍, 即相比更严重的硬件问题, 时钟问题极少发生. 因此, 我们认为 TrueTime 的实现与 Spanner 依赖的其他软件一样值得信赖.

Figure 6 presents TrueTime data taken at several thousand spanserver machines across datacenters up to 2200 km apart. It plots the 90th, 99th, and 99.9th percentiles of ε, sampled at timeslave daemons immediately after polling the time masters. This sampling elides the sawtooth in ε due to local-clock uncertainty, and therefore measures time-master uncertainty (which is generally 0) plus communication delay to the time masters.

图 6 给出数千台 spanserver 的 TrueTime 数据, 它们分布在最远相隔 2200 km 的数据中心. 图中绘制 ε 的第 90, 99 和 99.9 百分位, 在 timeslave 刚轮询完主服务器时采样. 这样排除了本地时钟不确定性增长造成的锯齿波, 测到的是主服务器不确定性 (通常为零) 加上通信延迟.

5.4 F1

Spanner started being experimentally evaluated under production workloads in early 2011, as part of a rewrite of Google's advertising backend called F1 [35]. This backend was originally based on a MySQL database that was manually sharded many ways. The uncompressed dataset is tens of terabytes, which is small compared to many NoSQL instances, but was large enough to cause difficulties with sharded MySQL. The MySQL sharding scheme assigned each customer and all related data to a fixed shard. This layout enabled the use of indexes and complex query processing on a per-customer basis, but required some knowledge of the sharding in application business logic. Resharding this revenue-critical database as it grew in the number of customers and their data was extremely costly. The last resharding took over two years of intense effort, and involved coordination and testing across dozens of teams to minimize risk. This operation was too complex to do regularly: as a result, the team had to limit growth on the MySQL database by storing some data in external Bigtables, which compromised transactional behavior and the ability to query across all data.

2011 年初, 随着 Google 广告后端重写项目 F1 [35] 推进, Spanner 开始在生产负载下接受试验性评估. 原后端基于手动分成大量分片的 MySQL. 未压缩数据有数十 TB, 相比许多 NoSQL 实例并不大, 却已足以让分片 MySQL 遇到困难. 原方案把每个客户及其相关数据放在一个固定分片, 能按客户使用索引和复杂查询, 但业务逻辑必须了解部分分片信息. 随客户数和数据增长, 对这个直接关系收入的数据库重新分片代价极高. 上一次重分片持续了两年多, 需要数十个团队协调和测试以降低风险. 由于操作太复杂, 无法经常执行, 团队只能把部分数据转移到外部 Bigtable, 限制 MySQL 增长, 却牺牲了事务性和跨全部数据查询的能力.

The F1 team chose to use Spanner for several reasons. First, Spanner removes the need to manually reshard. Second, Spanner provides synchronous replication and automatic failover. With MySQL master-slave replication, failover was difficult, and risked data loss and downtime. Third, F1 requires strong transactional semantics, which made using other NoSQL systems impractical. Application semantics requires transactions across arbitrary data, and consistent reads. The F1 team also needed secondary indexes on their data (since Spanner does not yet provide automatic support for secondary indexes), and was able to implement their own consistent global indexes using Spanner transactions.

F1 选择 Spanner 有几个原因. 首先, 不再需要手动重新分片. 其次, 它提供同步复制和自动故障转移; MySQL 主从复制下的故障转移很困难, 还可能丢失数据或停机. 第三, F1 需要强事务语义, 因而其他 NoSQL 系统并不适用: 应用需要跨任意数据的事务和一致读取. F1 也需要二级索引, 而 Spanner 尚未自动支持, 团队便利用 Spanner 事务自行实现了一致的全局索引.

All application writes are now by default sent through F1 to Spanner, instead of the MySQL-based application stack. F1 has 2 replicas on the west coast of the US, and 3 on the east coast. This choice of replica sites was made to cope with outages due to potential major natural disasters, and also the choice of their frontend sites. Anecdotally, Spanner's automatic failover has been nearly invisible to them. Although there have been unplanned cluster failures in the last few months, the most that the F1 team has had to do is update their database's schema to tell Spanner where to preferentially place Paxos leaders, so as to keep them close to where their frontends moved.

现在, 所有应用写入默认都经 F1 发送到 Spanner, 不再使用基于 MySQL 的应用栈. F1 在美国西海岸部署 2 个副本, 东海岸部署 3 个, 既考虑潜在重大自然灾害, 也考虑前端站点位置. 据团队反馈, 自动故障转移几乎无需他们介入. 过去几个月虽发生过计划外集群故障, F1 最多只需更新数据库模式, 告诉 Spanner 优先将 Paxos leader 放到哪些位置, 以靠近迁移后的前端.

Spanner's timestamp semantics made it efficient for F1 to maintain in-memory data structures computed from the database state. F1 maintains a logical history log of all changes, which is written into Spanner itself as part of every transaction. F1 takes full snapshots of data at a timestamp to initialize its data structures, and then reads incremental changes to update them.

Spanner 的时间戳语义, 使 F1 能高效维护由数据库状态计算而来的内存数据结构. F1 将全部变更写入逻辑历史日志, 并把日志作为每个事务的一部分保存到 Spanner 本身. 它先按某个时间戳获取完整快照来初始化数据结构, 再读取增量变更持续更新.

6. 相关工作

Consistent replication across datacenters as a storage service has been provided by Megastore [5] and DynamoDB [3]. DynamoDB presents a key-value interface, and only replicates within a region. Spanner follows Megastore in providing a semi-relational data model, and even a similar schema language. Megastore does not achieve high performance. It is layered on top of Bigtable, which imposes high communication costs. It also does not support long-lived leaders: multiple replicas may initiate writes. All writes from different replicas necessarily conflict in the Paxos protocol, even if they do not logically conflict: throughput collapses on a Paxos group at several writes per second. Spanner provides higher performance, general-purpose transactions, and external consistency.

Megastore [5] 和 DynamoDB [3] 已提供跨数据中心的一致复制存储服务. DynamoDB 提供键值接口, 只在一个 region 内复制. Spanner 沿用了 Megastore 的半关系数据模型, 模式语言也相似. Megastore 的性能不高: 它构建在 Bigtable 之上, 通信成本较高, 也不支持长期 leader, 因而多个副本都可发起写入. 即使逻辑上不冲突, 不同副本的写入在 Paxos 中仍必然冲突, 使每组吞吐量达到每秒几次写入后就急剧恶化. Spanner 则提供更高性能, 通用事务和外部一致性.

Pavlo et al. [31] have compared the performance of databases and MapReduce [12]. They point to several other efforts that have been made to explore database functionality layered on distributed key-value stores [1, 4, 7, 41] as evidence that the two worlds are converging. We agree with the conclusion, but demonstrate that integrating multiple layers has its advantages: integrating concurrency control with replication reduces the cost of commit wait in Spanner, for example.

Pavlo 等人 [31] 比较了数据库与 MapReduce [12] 的性能, 并列举多项在分布式键值存储上构建数据库功能的研究 [1, 4, 7, 41], 认为两个领域正在融合. 我们认同这一结论, 同时表明整合多个层次也有优势, 例如将并发控制与复制整合, 能减少 Spanner 中提交等待的代价.

The notion of layering transactions on top of a replicated store dates at least as far back as Gifford's dissertation [16]. Scatter [17] is a recent DHT-based key-value store that layers transactions on top of consistent replication. Spanner focuses on providing a higher-level interface than Scatter does. Gray and Lamport [18] describe a non-blocking commit protocol based on Paxos. Their protocol incurs more messaging costs than two-phase commit, which would aggravate the cost of commit over widely distributed groups. Walter [36] provides a variant of snapshot isolation that works within, but not across datacenters. In contrast, our read-only transactions provide a more natural semantics, because we support external consistency over all operations.

在复制存储上构建事务的思路, 至少可以追溯到 Gifford 的博士论文 [16]. 较新的 Scatter [17] 是基于 DHT 的键值存储, 在一致复制之上实现事务; Spanner 则侧重提供比它更高层的接口. Gray 和 Lamport [18] 提出基于 Paxos 的非阻塞提交协议, 但其消息成本高于两阶段提交, 会进一步增加广域分布组之间的提交开销. Walter [36] 提供一种快照隔离变体, 只在数据中心内部成立, 不跨数据中心. 相比之下, 我们的只读事务语义更自然, 因为所有操作都支持外部一致性.

There has been a spate of recent work on reducing or eliminating locking overheads. Calvin [40] eliminates concurrency control: it pre-assigns timestamps and then executes the transactions in timestamp order. H-Store [39] and Granola [11] each supported their own classification of transaction types, some of which could avoid locking. None of these systems provides external consistency. Spanner addresses the contention issue by providing support for snapshot isolation.

近期有许多工作尝试降低或消除锁开销. Calvin [40] 通过预先分配时间戳, 再按时间戳顺序执行事务, 消除了并发控制. H-Store [39] 和 Granola [11] 各自划分事务类型, 其中一些无需加锁. 这些系统都不提供外部一致性. Spanner 通过支持快照隔离来缓解争用.

VoltDB [42] is a sharded in-memory database that supports master-slave replication over the wide area for disaster recovery, but not more general replication configurations. It is an example of what has been called NewSQL, which is a marketplace push to support scalable SQL [38]. A number of commercial databases implement reads in the past, such as MarkLogic [26] and Oracle's Total Recall [30]. Lomet and Li [24] describe an implementation strategy for such a temporal database.

VoltDB [42] 是分片内存数据库, 支持用于灾难恢复的广域主从复制, 但不支持更通用的复制配置. 它属于所谓 NewSQL, 即市场上推动可扩展 SQL 的一类系统 [38]. MarkLogic [26] 和 Oracle Total Recall [30] 等商业数据库也支持历史读取. Lomet 和 Li [24] 描述了这类时态数据库的一种实现策略.

Farsite derived bounds on clock uncertainty (much looser than TrueTime's) relative to a trusted clock reference [13]: server leases in Farsite were maintained in the same way that Spanner maintains Paxos leases. Loosely synchronized clocks have been used for concurrency-control purposes in prior work [2, 23]. We have shown that TrueTime lets one reason about global time across sets of Paxos state machines.

Farsite 相对于可信时间基准推导时钟不确定性边界 [13], 但远比 TrueTime 宽松; 它维护服务器租约的方式与 Spanner 维护 Paxos 租约相同. 过去也有研究将松散同步的时钟用于并发控制 [2, 23]. 我们则表明, TrueTime 允许系统在多组 Paxos 状态机之间依据全局时间进行推理.

7. 未来工作

We have spent most of the last year working with the F1 team to transition Google's advertising backend from MySQL to Spanner. We are actively improving its monitoring and support tools, as well as tuning its performance. In addition, we have been working on improving the functionality and performance of our backup/restore system. We are currently implementing the Spanner schema language, automatic maintenance of secondary indices, and automatic load-based resharding. Longer term, there are a couple of features that we plan to investigate. Optimistically doing reads in parallel may be a valuable strategy to pursue, but initial experiments have indicated that the right implementation is non-trivial. In addition, we plan to eventually support direct changes of Paxos configurations [22, 34].

过去一年, 我们的大部分时间都与 F1 团队合作, 将 Google 广告后端从 MySQL 迁往 Spanner. 我们正改进监控和支持工具, 调优性能, 并完善备份恢复系统的功能与性能. 当前正在实现 Spanner 模式语言, 二级索引自动维护, 以及按负载自动重新分片. 更长期的探索包括乐观地并行读取; 初步实验表明, 正确实现并不简单. 此外, 我们最终计划支持直接修改 Paxos 配置 [22, 34].

Given that we expect many applications to replicate their data across datacenters that are relatively close to each other, TrueTime ε may noticeably affect performance. We see no insurmountable obstacle to reducing ε below 1ms. Time-master-query intervals can be reduced, and better clock crystals are relatively cheap. Time-master query latency could be reduced with improved networking technology, or possibly even avoided through alternate time-distribution technology.

我们预计许多应用会在相距较近的数据中心间复制, 因而 TrueTime 的 ε 可能明显影响性能. 将 ε 降到 1 ms 以下, 看起来没有不可克服的障碍. 可以缩短时间主服务器查询间隔, 更好的时钟晶振也相对便宜. 改进网络技术可降低查询延迟, 或者利用其他时间分发技术完全避免这部分延迟.

Finally, there are obvious areas for improvement. Although Spanner is scalable in the number of nodes, the node-local data structures have relatively poor performance on complex SQL queries, because they were designed for simple key-value accesses. Algorithms and data structures from DB literature could improve single-node performance a great deal. Second, moving data automatically between datacenters in response to changes in client load has long been a goal of ours, but to make that goal effective, we would also need the ability to move client-application processes between datacenters in an automated, coordinated fashion. Moving processes raises the even more difficult problem of managing resource acquisition and allocation between datacenters.

还有一些明显的改进空间. 虽然 Spanner 能扩展节点数量, 节点内部的数据结构却是为简单键值访问设计的, 执行复杂 SQL 时性能较差. 数据库文献中的算法和结构可以显著改善单节点性能. 其次, 按客户端负载变化在数据中心之间自动迁移数据, 一直是我们的目标. 要真正发挥作用, 还需能自动协调迁移客户端应用进程; 而进程迁移又带来了更难的数据中心间资源获取和分配问题.

8. 结论

To summarize, Spanner combines and extends on ideas from two research communities: from the database community, a familiar, easy-to-use, semi-relational interface, transactions, and an SQL-based query language; from the systems community, scalability, automatic sharding, fault tolerance, consistent replication, external consistency, and wide-area distribution. Since Spanner's inception, we have taken more than 5 years to iterate to the current design and implementation. Part of this long iteration phase was due to a slow realization that Spanner should do more than tackle the problem of a globally-replicated namespace, and should also focus on database features that Bigtable was missing.

Spanner 结合并扩展了两个研究领域的思想. 数据库领域提供了熟悉易用的半关系接口, 事务和基于 SQL 的查询语言; 系统领域提供了可扩展性, 自动分片, 容错, 一致复制, 外部一致性和广域分布. 从项目启动到目前的设计与实现, 我们已经迭代了 5 年多. 过程漫长的部分原因是, 我们逐渐意识到, Spanner 不应只解决全球复制命名空间的问题, 还应补足 Bigtable 缺少的数据库功能.

One aspect of our design stands out: the linchpin of Spanner's feature set is TrueTime. We have shown that reifying clock uncertainty in the time API makes it possible to build distributed systems with much stronger time semantics. In addition, as the underlying system enforces tighter bounds on clock uncertainty, the overhead of the stronger semantics decreases. As a community, we should no longer depend on loosely synchronized clocks and weak time APIs in designing distributed algorithms.

设计中最关键的一点是 TrueTime, 它支撑了 Spanner 的整套功能. 我们表明, 在时间 API 中显式表达时钟不确定性, 就能够构建具有更强时间语义的分布式系统. 底层对不确定性的约束越严格, 提供强语义的开销就越低. 分布式算法的设计不应再局限于松散同步时钟和能力薄弱的时间 API.

11. 附录 A: Paxos Leader 租约管理

The simplest means to ensure the disjointness of Paxos-leader-lease intervals would be for a leader to issue a synchronous Paxos write of the lease interval, whenever it would be extended. A subsequent leader would read the interval and wait until that interval has passed.

保证 Paxos leader 租约区间不相交的最简单方法, 是每次延长租约时都通过同步 Paxos 写入记录新区间. 后续 leader 读出该区间, 等待其结束即可.

TrueTime can be used to ensure disjointness without these extra log writes. The potential ith leader keeps a lower bound on the start of a lease vote from replica r as vi, rleader = TT.now().earliest, computed before ei, rsend (defined as when the lease request is sent by the leader). Each replica r grants a lease at ei, rgrant, which happens after ei, rreceive (when the replica receives a lease request); the lease ends at ti, rend = TT.now().latest + 10, computed after ei, rreceive. A replica r obeys the single-vote rule: it will not grant another lease vote until TT.after(ti, rend) is true. To enforce this rule across different incarnations of r, Spanner logs a lease vote at the granting replica before granting the lease; this log write can be piggybacked upon existing Paxos-protocol log writes.

TrueTime 可以在不增加这些日志写入的情况下保证不相交. 第 i 个候选 leader 在向副本 r 发送租约请求的事件 ei, rsend 之前, 计算 vi, rleader = TT.now().earliest, 作为该副本租约投票开始时间的下界. 副本 r 收到请求的事件记为 ei, rreceive, 随后在 ei, rgrant 授予租约. 租约终点为 ti, rend = TT.now().latest + 10, 在收到请求之后计算. 副本遵循单票规则: 只有 TT.after(t_end) 为 true, 才能再授予另一份租约投票, 其中 t_end 指该副本上述租约终点. 为使这一规则在副本重启后仍有效, Spanner 要求副本在授予租约前记录投票日志; 该日志可附带在已有 Paxos 日志写入中.

When the ith leader receives a quorum of votes (event eiquorum), it computes its lease interval as leasei = [TT.now().latest, minr(vi, rleader) + 10]. The lease is deemed to have expired at the leader when TT.before(minr(vi, rleader) + 10) is false.
