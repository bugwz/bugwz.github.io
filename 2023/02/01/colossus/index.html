译 - Colossus under the hood: a peek into Google's scalable storage system

|总字数:10.9k|查看 Markdown

本文翻译 Google Cloud 关于 Colossus 文件系统的文章, 介绍其元数据服务, 数据路径, 后台维护机制, 以及共享存储池如何支持大规模工作负载并提高存储效率.

原文: Colossus under the hood: a peek into Google's scalable storage system, Dean Hildebrand 和 Denis Serenyi. Google Cloud 页面显示的发布日期为 2021-04-19; 用户提供的文本标注为 2021-04-20. 本文博客发布日期按指定日期记录.

1. Colossus 简介

You trust Google Cloud with your critical data, but did you know that Google also relies on the same underlying storage infrastructure for its other businesses as well? That's right, the same storage system that powers Google Cloud also underpins Google's most popular products, supporting globally available services like YouTube, Drive, and Gmail.

你把重要数据托付给 Google Cloud. 但你知道吗, Google 的其他业务也依赖同一套底层存储基础设施? 支撑 Google Cloud 的存储系统, 同样为 YouTube, Drive 和 Gmail 等面向全球的产品提供支持.

That foundational storage system is Colossus, which backs Google's extensive ecosystem of storage services, such as Cloud Storage and Firestore, supporting a diverse range of workloads, including transaction processing, data serving, analytics and archiving, boot disks, and home directories.

这套基础存储系统就是 Colossus. 它支撑着包括 Cloud Storage 和 Firestore 在内的 Google 存储服务生态, 承载事务处理, 数据服务, 分析与归档, 启动盘和主目录等多种工作负载.

In this post, we take a deeper look at the storage infrastructure behind your VMs, specifically the Colossus file system, and how it helps enable massive scalability and data durability for Google services as well as your applications.

本文将深入介绍虚拟机背后的存储基础设施, 尤其是 Colossus 文件系统, 以及它如何为 Google 服务和你的应用提供大规模扩展能力与数据持久性.

2. Google Cloud 的扩展能力源于 Google 的基础设施

Before we dive into how storage services operate, it's important to understand the single infrastructure that supports both Cloud and Google products. Like any well-designed software system, all of Google is layered with a common set of scalable services. There are three main building blocks used by each of our storage services:

在了解存储服务的运作方式之前, 先要认识同时支撑 Google Cloud 和 Google 产品的统一基础设施. 与设计良好的软件系统一样, Google 的各层都建立在一组可扩展的通用服务之上. 每项存储服务都使用三个核心组件:

  • Colossus is our cluster-level file system, successor to the Google File System (GFS).
  • Spanner is our globally-consistent, scalable relational database.
  • Borg is a scalable job scheduler that launches everything from compute to storage services. It was and continues to be a big influence on the design and development of Kubernetes.
  • Colossus 是集群级文件系统, 是 Google File System (GFS) 的继任者.
  • Spanner 是具有全球一致性且可扩展的关系数据库.
  • Borg 是可扩展的作业调度器, 负责启动从计算到存储的各种服务. 它过去和现在都对 Kubernetes 的设计与开发产生了重要影响.

These three core building blocks are used to provide the underlying infrastructure for all Google Cloud storage services, from Firestore to Cloud SQL to Filestore, and Cloud Storage. Whenever you access your favorite storage services, the same three building blocks are working together to provide everything you need. Borg provisions the needed resources, Spanner stores all the metadata about access permissions and data location, and then Colossus manages, stores, and provides access to all your data.

从 Firestore, Cloud SQL 到 Filestore 和 Cloud Storage, 所有 Google Cloud 存储服务都以这三个组件为基础. 每次使用这些服务时, 三者都会协同工作: Borg 分配所需资源, Spanner 保存访问权限和数据位置等元数据, Colossus 则管理, 存储并提供数据访问.

Google Cloud takes these same building blocks and then layers everything needed to provide the level of availability, performance, and durability you need from your storage services. In other words, your own applications will scale the same as Google products because they rely on the same core infrastructure based on these three services scaling to meet your needs.

Google Cloud 在这些组件之上构建服务, 提供存储所需的可用性, 性能和持久性. 换言之, 你的应用与 Google 产品依赖同一套核心基础设施, 这三个组件可以随需求扩展, 因而应用也能获得相应的扩展能力.

3. Colossus 概览

Now, let's take a closer look at how Colossus works.

下面具体看看 Colossus 如何工作.

But first, a little background on Colossus:

先了解一些背景:

  • It's the next-generation of the GFS.
  • Its design enhances storage scalability and improves availability to handle the massive growth in data needs of an ever-growing number of applications.
  • Colossus introduced a distributed metadata model that delivered a more scalable and highly available metadata subsystem.
  • Colossus 是 GFS 的下一代系统.
  • 它的设计提高了存储的扩展能力和可用性, 以应对越来越多应用快速增长的数据需求.
  • Colossus 引入分布式元数据模型, 使元数据子系统更易扩展, 可用性也更高.

But how does it all work? And how can one file system underpin such a wide range of workloads? Below is a diagram of the key components of the Colossus control plane:

它具体如何工作? 一个文件系统又如何支撑如此多样的工作负载? 下图展示了 Colossus 控制面的主要组件:

Colossus control plane components and data path.

Colossus 控制面组件与数据路径.

3.1 客户端库

Client library. The client library is how an application or service interacts with Colossus. The client is probably the most complex part of the entire file system. There's a lot of functionality, such as software RAID, that goes into the client based on an application's requirements. Applications built on top of Colossus use a variety of encodings to fine-tune performance and cost trade-offs for different workloads.

客户端库. 应用或服务通过客户端库与 Colossus 交互. 客户端可能是整个文件系统中最复杂的部分. 根据应用需求, 软件 RAID 等许多功能都在客户端实现. 构建在 Colossus 之上的应用采用不同编码方式, 针对各类工作负载细调性能与成本之间的取舍.

3.2 控制面

Colossus Control Plane. The foundation of Colossus is its scalable metadata service, which consists of many Curators. Clients talk directly to curators for control operations, such as file creation, and can scale horizontally.

Colossus 控制面. Colossus 的基础是由多个 Curator 组成的可扩展元数据服务. 客户端直接与 Curator 通信, 完成创建文件等控制操作; Curator 可以横向扩展.

3.3 元数据数据库

Metadata database. Curators store file system metadata in Google's high-performance NoSQL database, BigTable. The original motivation for building Colossus was to solve scaling limits we experienced with Google File System (GFS) when trying to accommodate metadata related to Search. Storing file metadata in BigTable allowed Colossus to scale up by over 100x over the largest GFS clusters.

元数据数据库. Curator 将文件系统元数据存储在 Google 的高性能 NoSQL 数据库 BigTable 中. 开发 Colossus 最初是为了解决 GFS 在容纳搜索相关元数据时遇到的扩展限制. 将文件元数据存入 BigTable, 使 Colossus 的规模能够达到最大 GFS 集群的 100 多倍.

3.4 D 文件服务器

D File Servers. Colossus also minimizes the number of hops for data on the network. Data flows directly between clients and "D" file servers (our network attached disks).

D 文件服务器. Colossus 还尽量减少数据在网络中的跳数. 数据直接在客户端与 "D" 文件服务器 (Google 的网络连接磁盘) 之间传输.

3.5 Custodian

Custodians. Colossus also includes background storage managers called Custodians. They play a key role in maintaining the durability and availability of data as well as overall efficiency, handling tasks like disk space balancing and RAID reconstruction.

Custodian. Colossus 还包含名为 Custodian 的后台存储管理组件. 它们负责磁盘空间均衡, RAID 重建等任务, 对维持数据持久性, 可用性和整体效率至关重要.

4. Colossus 如何提供可靠且可扩展的存储

To see how this all works in action, let's consider how Cloud Storage uses Colossus. You've probably heard us talk a lot about how Cloud Storage can support a wide range of use cases, from archival storage to high throughput analytics, but we don't often talk about the system that lies beneath.

要看这些组件如何协同工作, 可以从 Cloud Storage 使用 Colossus 的方式入手. 我们经常介绍 Cloud Storage 如何支持从归档存储到高吞吐量分析的各种场景, 却很少谈到它背后的系统.

Typical clusters sharing a Colossus storage pool.

共享 Colossus 存储池的典型集群.

With Colossus, a single cluster is scalable to exabytes of storage and tens of thousands of machines. In the example above, for example, we have instances accessing Cloud Storage from Compute Engine VMs, YouTube serving nodes, and Ads MapReduce nodes - all of which are able to share the same underlying file system to complete requests. The key ingredient is having a shared storage pool that is managed by the Colossus control plane, providing the illusion that each has its own isolated file system.

借助 Colossus, 单个集群可以扩展到 EB 级存储容量和数万台机器. 如上图所示, Compute Engine 虚拟机, YouTube 服务节点和广告业务的 MapReduce 节点都能访问 Cloud Storage, 并共享同一个底层文件系统来完成请求. 关键在于由 Colossus 控制面管理的共享存储池: 对每类工作负载而言, 它看起来都像一套独立的文件系统.

Disaggregation of resources drives more efficient use of valuable resources and lowers costs across all workloads. For instance, it's possible to provision for the peak demand of low latency workloads, like a YouTube video, and then run batch analytic workloads more cheaply by having them fill in the gaps of otherwise idle time.

资源解耦提高了资源利用率, 也降低了各类工作负载的成本. 例如, 可以按 YouTube 视频等低延迟工作负载的峰值需求配置资源, 再让批量分析任务利用其余时段的空闲容量, 从而降低运行成本.

Let's take a look at a few other benefits Colossus brings to the table.

下面再看看 Colossus 的其他优势.

4.1 简化硬件复杂性

As you might imagine, any file system supporting Google services has fairly daunting throughput and scaling requirements that must handle multi-TB files and massive datasets. Colossus abstracts away a lot of physical hardware complexity that would otherwise plague storage-intensive applications.

支撑 Google 服务的文件系统, 必须满足很高的吞吐量和扩展要求, 还要处理数 TB 的文件及海量数据集. Colossus 将大量物理硬件细节抽象出来, 减轻了存储密集型应用原本需要面对的复杂性.

Google data centers have a tremendous variety of underlying storage hardware, offering a mix of spinning disk and flash storage in many sizes and types. On top of this, applications have extremely diverse requirements around durability, availability, and latency. To ensure each application has the storage it requires, Colossus provides a range of service tiers. Applications use these different tiers by specifying I/O, availability, and durability requirements, and then provisioning resources (bytes and I/O) as abstract, undifferentiated units.

Google 数据中心使用多种底层存储硬件, 包括容量与类型各异的机械硬盘和闪存. 同时, 应用对持久性, 可用性和延迟的要求也各不相同. 为满足这些需求, Colossus 提供多个服务层级. 应用指定 I/O, 可用性和持久性要求后, 便能以抽象, 无差别的单位来配置容量 (字节) 与 I/O 资源.

In addition, at Google scale, hardware is failing virtually all the time - not because it's unreliable, but because there's a lot of it. Failures are a natural part of operating at such an enormous scale, and it's imperative that its file system provide fault tolerance and transparent recovery. Colossus steers I/O around these failures and does fast background recovery to provide highly durable and available storage.

此外, 在 Google 的规模下, 几乎随时都有硬件发生故障. 原因并非硬件不可靠, 而是设备数量庞大. 故障是这种规模下的运行常态, 因此文件系统必须具备容错和透明恢复能力. Colossus 让 I/O 绕开故障设备, 并在后台快速恢复, 从而提供高持久性和高可用性的存储.

The end result is that the associated complexity headaches of dealing with hardware resources are significantly reduced, making it easy for any application to get and use the storage it requires.

这样一来, 应用处理硬件资源时面临的复杂性显著降低, 更容易获取和使用所需的存储.

4.2 提高存储效率

Now, as you might imagine it takes some management magic to ensure that storage resources are available when applications need them without overprovisioning. Colossus takes advantage of the fact that data has a wide variety of access patterns and frequencies (that is, hot data that is accessed frequently) and uses a mix of flash and disk storage to meet any need.

要在应用需要时提供存储资源, 又避免过量配置, 需要精细管理. Colossus 利用数据访问模式和频率的差异 (例如频繁访问的热数据), 组合使用闪存与磁盘来满足不同需求.

The hottest data is put on flash for more efficient serving and lower latency. We buy just enough flash to push the I/O density per gigabyte into what disks can typically provide and buy just enough disks to ensure we have enough capacity. With the right mix, we can maximize storage efficiency and avoid wasteful overprovisioning.

访问最频繁的数据放在闪存中, 以提高服务效率并降低延迟. 我们只采购足够的闪存, 将每 GB 的 I/O 密度降到磁盘通常能够承受的水平; 同时只采购足够的磁盘, 确保容量充足. 通过合理搭配两者, 就能提高存储效率, 避免浪费性的过量配置.

For disk-based storage, we want to keep disks full and busy to avoid excess inventory and wasted disk IOPs. To do this, Colossus uses intelligent disk management to get as much value as possible from available disk IOPs. Newly written data (i.e. hotter data) is evenly distributed across all the drives in a cluster. Data is then rebalanced and moved to larger capacity drives as it ages and becomes colder. This works great for analytics workloads, for example, where data typically cools off as it ages.

对于磁盘存储, 我们希望磁盘既装有足够的数据, 又保持忙碌, 以避免设备闲置和磁盘 IOPS 浪费. 为此, Colossus 通过智能磁盘管理, 尽可能利用现有磁盘的 I/O 能力. 新写入的数据通常较热, 会均匀分布到集群中的所有磁盘. 随着数据变旧, 访问频率下降, 系统会重新均衡数据, 并将其移到容量更大的磁盘. 对于数据往往随时间逐渐冷却的分析工作负载, 这种方式尤其合适.

5. 经大规模实践检验

So, there you have it - Colossus is the secret scaling superpower behind Google's storage infrastructure. Colossus not only handles the storage needs of Google Cloud services, but also provides the storage capabilities of Google's internal storage needs, helping to deliver content to the billions of people using Search, Maps, YouTube, and more every single day. When you build your business on Google Cloud you get access to the same super-charged infrastructure that keeps Google running. We'll keep making our infrastructure better, so you don't have to.

Colossus 是 Google 存储基础设施实现大规模扩展的关键. 它不仅满足 Google Cloud 服务的存储需求, 也支撑 Google 的内部存储, 每天帮助搜索, 地图, YouTube 等产品向数十亿用户提供内容. 当你在 Google Cloud 上开展业务时, 也能使用支撑 Google 自身业务的基础设施. 我们会继续改进这套基础设施, 减少你在这方面的投入.

To learn more about Google Cloud's storage architecture, check out the Next '20 session from which this post was developed, "A peek at the Google Storage infrastructure behind the VM." And check out the cloud storage website to learn more about all our storage offerings.

Within our population of disks, as I mentioned earlier, we're going to have a wide variety of disk sizes. To maximize efficiency, we'll want to do two things. Because each cluster has roughly the same I-O bandwidth, because each disk has roughly the same I-O bandwidth, what this means is that we'll have to keep hotter data evenly spread across all the drives in the cluster. 如前面所说, 磁盘群中有许多不同容量的磁盘. 为提高效率, 我们希望做到两点: 让磁盘装满, 因为空闲字节意味着多余的库存; 让磁盘保持忙碌, 以免浪费磁盘的 I/O 能力. 每块磁盘的 I/O 带宽大致相同, 这意味着需要将较热的数据均匀分布到集群的所有磁盘上, 再用冷数据填满每块磁盘的剩余空间. 为实现这一目标, Colossus 解决的关键问题是如何智能地放置数据.

Turns out, newly written data is typically hotter. So Colossus spreads new writes evenly across all the disks, leading to a pretty even balance of hot data.
